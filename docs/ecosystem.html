HMR：热更新原理

改模板不刷新页面、改状态秒生效 —— HMR 是你使用频率最高却最少被讲原理的功能。 它是编译器（38.2）、运行时（38.3）与 Vite（38.4）的三方握手，本章把整条链拆开。

38.1 先把现象翻译成问题

你改的东西你看到的行为背后的问题
<template>页面不刷新，视图直接变render 函数被替换 + 组件就地重渲染 —— 状态怎么保住的？
<script setup>整页刷新（组件重建）为什么这个不能热替换？setup 的响应式依赖关系变了
<style>样式立即更新style 模块独立成文件，只换样式不碰组件

38.2 编译侧：SFC 拆成带热边界的模块

// App.vue?vue&type=script   ← script 模块
import __sfc_main__ from "App.vue?vue&type=script&lang.ts"
import __style__ from "App.vue?vue&type=style&index=0&lang.css"
import { exportDefaultComponent as __export } from "App.vue?vue&type=template"

__sfc_main__.render = __render            // 模板编译出的 render 挂上去

// ⭐ 热边界声明：这个模块「能被谁热替换、替换时调谁」
import.meta.hot.accept(mod => {
  __VUE_HMR_RUNTIME__.rerender(__sfc_main__.__hmrId, mod.render)  // 模板变了
})
import.meta.hot.accept("App.vue?vue&type=style", () => { ... })   // 样式变了
💡 __hmrId 是关键线头
每个 SFC 编译时都会生成唯一 id（文件路径哈希），挂到组件的 __hmrId 上。运行时的 HMR API 按 id 找组件 —— 「文件」与「运行中的组件实例」靠这根线连起来。

38.3 运行侧：__VUE_HMR_RUNTIME__ 的三个动作

export function hmrRerender(id, newRender) {
  // 模板热替换：找到该 id 的所有运行中实例
  const registered = hmrIdToInstancesMap.get(id);
  for (const instance of registered) {
    instance.render = newRender;          // ⭐ 换渲染函数
    instance.update();                    // 立即重渲染（走 23 章队列）
  }
}

export function hmrReload(id, newComponent) {
  // script 热替换：实例的 type 整个换新 —— 响应式依赖关系可能全变
  const registered = hmrIdToInstancesMap.get(id);
  for (const instance of registered) {
    newComponent.__hmrId = id;
    instance.type = newComponent;         // ⭐ 就地换心
    // 保留 instance/props/el，但 setup 需要重跑 → 官方选择「整棵子树重挂」保正确性
    // rerender 约束不满足时 → reload = 卸载重挂
  }
}
// 另有 createRecord / getRecord 等登记表辅助：hmrId → 组件集合

38.4 Vite 的角色：WebSocket 快递员

保存文件 → Vite 编译变更模块 → WebSocket 推送 { file, timestamp } → 浏览器端 import() 拉新模块 → 执行 hot.accept 回调 → rerender/reload
Vite 只负责「把新模块送到浏览器」，组件怎么换是 Vue 运行时的事 —— 职责边界干净
自测一下：HMR

1. 为什么改 template 能保住组件状态，改 script 不行？
2. HMR 和 SSR 有什么相似的架构思想？

答案：
1. template 变化 = render 函数变化，组件实例和它的响应式状态不动，rerender 重跑 render 即可； script 变化意味着 setup 逻辑/依赖声明可能全变，旧实例的响应式连接不可信 —— 只能整树重挂（reload）。
2. 都是「同一套运行时，两套驱动」：SSR 是字符串驱动 vs DOM 驱动（第 36 章）， HMR 是新模块驱动旧实例。框架核心保持中立，边界协议可插拔 —— 大型框架的通用生存策略。

vue-devtools 协议

你调试时看到的组件树、响应式状态、时间旅行 —— 都不是 Vue 内置的， 而是运行时通过一个全局钩子把内部数据「广播」出去。读完本章，你可以自己写一个调试插件。

39.1 钩子：一条全局广播通道

// window.__VUE_DEVTOOLS_GLOBAL_HOOK__ 由 devtools 扩展预先注入
// Vue 运行时启动时「认领」它：
export function setDevtoolsHook(hook, target) {
  devtools = hook;
  if (hook) {
    // Vue 侧声明自己支持的能力
    hook.emit("init", {
      Vue, app instances map, version,
      highlightElement / unhighlightElement,   // 给 devtools 的高亮回调
    });
  }
}
// 组件挂载/更新/卸载时（dev 模式）：
if (__DEV__ && devtools) {
  devtools.emit("component:mounted", vnode.component);   // 广播事件
  devtools.emit("component:updated", instance);
}
🧠 为什么用事件广播而不是直接暴露？
解耦：devtools 扩展可能比页面晚加载（刷新扩展不刷页面），双向事件让「晚到的一方」也能 通过 flush 事件补齐全部已存在的实例。协议即契约 —— 双方各自实现契约，互不 import。

组件树subTree 递归 + parent 链（第 19/22 章的实例树）
State / Setup 面板instance.setupState（proxyRefs 代理）、props、data

Vue Router 源码导览

你已经能猜到 Router 的一半：currentRoute 是个 reactive 对象，改它组件就重渲染。 本章补另一半：history 监听怎么接、matcher 怎么把路径变成组件、导航守卫的队列怎么跑。

40.1 createRouter：一个 reactive + 一次 install

export function createRouter(options) {
  const currentRoute = shallowRef(START_LOCATION);   // ⭐ 当前路径（浅响应）
  const matcher = createRouterMatcher(options.routes); // 路径 → 组件 的匹配器

  function push(to) {
    return pushWithRedirect(to);   // 内部：跑守卫队列 → 改 history → 更新 currentRoute
  }

  const router = {
    push, replace, back,
    install(app) {                 // ⭐ app.use(router) 时执行（第 18.5 节的套路）
      app.component("RouterView", RouterView);
      app.component("RouterLink", RouterLink);
      app.provide(routerKey, router);            // provide 三件套（第 24.1 节原型链顶端）
      app.provide(routeLocationKey, reactive(currentRoute));
      app.provide(routerViewLocationKey, currentRoute);

40.2 history 层：把浏览器 API 包成统一接口

export function createWebHistory(base) {
  function changeLocation(to, state, replace) {
    const url = base + to;
    history[replace ? "replaceState" : "pushState"](state, "", url);  // 不触发 popstate！
    // ⭐ 所以 push 后要手动同步：listeners.forEach(fn => fn({ location: currentLocation }))
  }
  window.addEventListener("popstate", () => {
    listeners.forEach(fn => fn({ location: currentLocation }));      // 前进后退走这里
  });
  return { location, listen(cb) {...}, push: to => changeLocation(to, null, false), ... };
}

40.3 matcher 深讲：路径怎么变成「能拿组件的记录」

// ① 注册：每条 route 编译成「正则 + 参数名清单 + 记分卡」
function addRoute(record, parent) {
  const normalized = { path: normalizePath(record.path), components: record.components, ... };
  const matcher = createRouteRecordMatcher(normalized, parent);
  // path-to-regexp：/user/:id → /^\/user\/([^/]+)?$/i + 参数名 ["id"]
  insertMatcher(matcher);        // ⭐ 按「特异性」排序插入
}
// ② 排序：/user/new 必须排在 /user/:id 前面
//    记分规则：静态段 > 动态段 > 可选段 > 重复参数 —— 分高者先匹配
// ③ 匹配：resolve(location) 从头找第一个 test(path) 通过的 matcher
//    → 返回 { matched: [record 链] }（嵌套路由的父子链按深度排好）
🧠 matched 数组是 RouterView 的燃料
/user/1/posts/2 命中两层嵌套路由时，matched = [User 记录, Posts 记录]。 RouterView 渲染时看「自己在 matched 里的深度」：第一层 View 取 matched[0]， 里面的 View 取 matched[1] —— 嵌套渲染就是同一组件查表取不同深度。

40.4 导航守卫队列：一次 push 的完整流水线

beforeRouteLeave（当前组件） → beforeEach（全局） → beforeEnter（目标路由） → beforeRouteEnter（目标组件）
全部放行 → 更新 history + currentRoute → afterEach / beforeResolve
任何一环 return false / next(false) → 队列中断、URL 回滚 —— 队列的本质是「可中断的 Promise 链」
自测一下：Vue Router

1. RouterView 重渲染的响应式链路是什么？
2. 为什么 /user/new 要写在 /user/:id 前面，官方才能保证正确？

答案：
1. currentRoute 是 reactive（40.1）→ RouterView 的 render 读它（同时读 matched 深度） → 路径变化触发组件重渲染 → 查 matched[深度] 换组件 → 走 18 章 patch。
2. matcher 按特异性排序注册，静态段分数高于动态段 —— 即使写错顺序，官方也会按分数 插到正确位置；「写在前面的优先」是给人的直觉，机器真正依赖的是 rank。

Pinia 源码导览

第 24.8 节剧透过它的本质。本章展开：install 流程、store 的惰性创建、 $patch / $subscribe 的实现，以及「为什么 pinia 没有 mutation」。

41.1 createPinia：install 做的四件事

export function createPinia() {
  const scope = effectScope(true);        // ⭐ 独立的根作用域（第 10 章）
  const state = {};                       // 所有 store 的 state 都存这里：id → state
  const pinia = {
    install(app) {
      setActivePinia(pinia);
      scope.run(() => {                   // 后续所有 store 都建在这个 scope 下
        app.provide(piniaKey, pinia);     // 全树可 inject（第 24.1 节）
      });
      app.config.globalProperties.$pinia = pinia;
    },
    _s: new Map(),                        // id → store 实例（useStore 的注册表）
    _e: scope, _p: plugins, state,
  };
  return pinia;
}

41.2 defineStore：返回的是一个「惰性 useStore」

export function defineStore(id, setup) {
  function useStore(pinia = activePinia) {
    pinia = pinia || getCurrentInstance()?.appContext.config.globalProperties.$pinia;
    if (!pinia._s.has(id)) {              // ⭐ 首次调用才创建 —— 惰性单例
      createSetupStore(id, setup, options, pinia);
    }
    return pinia._s.get(id);
  }
  useStore.$id = id;
  return useStore;
}

function createSetupStore(id, setup, pinia) {
  let store;                              // 循环引用的解法：先声明，setup 里可用
  const partialStore = { $id, _p: pinia, $patch, $reset, $subscribe, $onAction, ... };
  store = reactive(Object.assign(partialStore, setup()));  // ⭐ 状态+actions+getters 一锅 reactive
  pinia._s.set(id, store);
  return store;
}
🧠 为什么没有 mutation？
setup store 里 state 就是普通 ref、修改就是普通赋值 —— 响应式系统（第 3 章）天然支持细粒度追踪， Vuex 时代的 mutation 是为了给 devtools 一个「统一钩子」记录每次变更； pinia 改用 $subscribe 直接订阅 store 的变化（底层是 watch），不需要中间层。 架构演进的方向：当底层能力足够强，中间的仪式层就该消失。

VueUse 精选实现

VueUse 的两百个函数没有一个用到你没学过的机制 —— 它们全是第 2~29 章组合式函数范式（10.7）的复写。 本章亲手实现五个最高频的，写完你就有了「任何 VueUse 函数都能读」的信心。

42.1 useEventListener：清理的标准姿势

export function useEventListener(...args) {
  let cleanup = () => {};
  const register = (el, event, listener) => {
    el.addEventListener(event, listener);
    return () => el.removeEventListener(event, listener);
  };
  const stopWatch = watch(
    () => unrefEl(args),               // 目标元素可以是 ref/getter —— 10.7 的输入兼容
    (el) => {
      cleanup();                       // 元素变了 → 先拆旧的
      if (el) cleanup = register(el, event, listener);
    },
    { immediate: true, flush: "post" } // post：DOM 就位后再挂（第 23 章的时序）
  );
  const stop = () => { stopWatch(); cleanup(); };
  onScopeDispose(stop);                // ⭐ 随作用域自动清理（10.6）
  return stop;
}
💡 这个函数教会你的三件事
watch 负责响应式（目标可变）、cleanup 负责幂等（重复注册先拆旧）、onScopeDispose 负责生命周期 —— 三件套几乎构成所有 DOM 类组合式函数的模板。

42.2 useDebounceFn / useThrottleFn：纯函数包装

export function useDebounceFn(fn, ms = 200) {
  let timer = null;
  const debounced = (...args) => {
    if (timer) clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
  tryOnScopeDispose(() => timer && clearTimeout(timer));   // 作用域销毁 → 取消尾巴
  return debounced;
}
// 全程没有任何响应式 —— useXxx 不一定要碰 ref；「管理资源生命周期」本身就是价值

42.3 useLocalStorage：ref + 序列化 + 跨标签页

export function useLocalStorage(key, initial) {
  const data = ref(read());                        // ① 初始值从 localStorage 读
  function read() {
    try { const raw = window.localStorage.getItem(key);
          return raw ? JSON.parse(raw) : initial; } catch { return initial; }
  }
  watch(data, (v) => window.localStorage.setItem(key, JSON.stringify(v)),
        { deep: true });                           // ② 变了就写回
  window.addEventListener("storage", (e) => {      // ③ 其他标签页改了 → 同步（42.1 思想）
    if (e.key === key) data.value = read();
  });
  return data;
}

42.4 useIntersectionObserver / useMediaQuery：原生 API 的响应式马甲

export function useMediaQuery(query) {
  const matches = ref(false);
  const update = () => { matches.value = window.matchMedia(query).matches; };
  useEventListener(window, "resize", update, { passive: true });   // 复用 42.1
  update();                                                        // 立即初始化
  return computed(() => matches.value);
}
// 把「命令式 API」翻译成「响应式状态」—— 这是 VueUse 一半函数的套路
自测一下：VueUse 实现

1. 为什么 useEventListener 要 watch 元素而不是只 addEventListener 一次？
2. useDebounceFn 里没有任何 ref，为什么也要 tryOnScopeDispose？

答案：
1. 目标元素可能随 v-if / 动态 ref 变化 —— watch 元素变化时先拆旧监听再挂新监听，保证永不泄漏、永不双挂。
2. 组件销毁后 pending 的 setTimeout 仍会执行回调，访问已卸载组件的闭包轻则警告重则报错 —— 生命周期清理与「是否响应式」无关。

    let dummy, runs = 0;
    const spy = vi.fn(() => { runs++; dummy = state.flag ? state.name : state.age; });
    effect(spy);
    state.flag = false;                     // 分支切换
    const runsAfterSwitch = runs;
    state.name = "b";                       // 改已无人的 name
    expect(runs).toBe(runsAfterSwitch);     // ⭐ 不应再触发 —— 清理生效
  });

  it("ref setter 应保持对象的响应式（第 7 章找茬）", () => {
    const r = ref({ name: "a" });
    r.value = { name: "b" };
    expect(isReactive(r.value)).toBe(true); // ⭐ 你给官方提 PR 时就是这条
  });
});

43.3 @vue/runtime-test：官方自己的「假 DOM」

官方测渲染器时不操作真 DOM，而是用 @vue/runtime-test —— 一个输出「可断言轻量树」的自定义渲染器（第 37 章的活教材）。 断言形如 expect(root.innerHTML).toBe(...) 或直接检查节点树结构。 给渲染器写测试 = 给渲染器换一个可检查的宿主，这与你已经掌握的 nodeOps 注入完全一致。

💡 实战节奏建议
第 44~48 章每章末尾都给了验收测试 —— 正确姿势是先写测试、看它红、再抄实现、看它绿。 红绿循环把「抄代码」变成「验证理解」。
自测一下：用测试读源码

1. 为什么官方换掉整个依赖系统的内部结构，测试一行不用改？
2. 用 runtime-test 测渲染器和 37 章的 canvas 渲染器，本质相同吗？

答案：
1. 测试只断言公开行为（effect 触发次数、computed 缓存语义）—— 内部从 Map 换链表属于纯重构， 行为不变则测试不变。
2. 相同。都是「nodeOps 换宿主」：一个换到可断言的内存树，一个换到 canvas —— 测试友好性和显示能力，都是注入协议的产物。
