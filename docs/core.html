启动全流程：从 createApp 到第一个像素

前面 16 章，你把所有零件都拆开看过了：effect、Proxy、track/trigger、diff、组件实例…… 但零件不等于整车。本章回答一个终极问题：当你写下 createApp(App).mount('#app')， 到页面上出现第一个像素，中间到底发生了什么？一条调用链，串起全书所有章节 —— 官方源码入口在 runtime-core/src/apiCreateApp.ts。

21.1 createApp：工厂里的工厂

createApp 不是普通函数，它是「工厂里的工厂」： 外层 createAppAPI(render) 接收渲染器，内层才创建 app 对象。 官方源码里这个结构一眼可见： 

export function createAppAPI(render, hydrate) {
  return function createApp(rootComponent, rootProps = null) {
    const app = {
      _component: rootComponent,      // 根组件
      _props: rootProps,
      _container: null,
      _context: {                     // ⭐ 全局配置包
        components: {}, directives: {},
        provides: Object.create(null),  // 第 24 章 provide 的全局兜底
        config: { ... },
      },
      use(plugin, ...options) { ...; return app; },        // ⭐ 返回 app = 链式调用
      component(name, comp) { ...; return app; },
      directive(name, dir) { ...; return app; },
      provide(key, value) { this._context.provides[key] = value; return app; },

      mount(rootContainer) {          // ⭐⭐ 真正的启动入口
        const vnode = createVNode(rootComponent, rootProps);
        vnode.appContext = this._context;
        render(vnode, rootContainer); // ← 一切从这里开始
        this._container = rootContainer;
        return vnode.component.proxy; // 根组件实例的代理（第 22 章）
      },
    };
    return app;
  };
}
💡 两个「为什么不」
为什么不直接 render(App, '#app')？ 因为 app 对象是「全局配置的容器」： app.use / app.component / app.provide 都要在渲染之前收进 _context， 根组件和所有子孙（inject、全局组件注册）都要靠它。
为什么 createAppAPI 要接收 render？ 渲染器是注入的（第 15 章）—— 同一套 createAppAPI，web 上配 DOM nodeOps，自定义渲染器（比如本仓库嵌套 iframe 的玩法）配自己的 nodeOps。 一个入口，N 个平台。

本项目里对应的就是 packages/runtime-dom/src/index.ts 的那三行： 把 nodeOps + patchProp 打包成 renderOptions 交给 createRenderer， 再把 createRenderer(...).render 传给 createAppAPI —— 分层闭环。

21.2 app.mount('#app')：入口的三次「翻译」

你以为 mount 只是「渲染」？官方的 mount 在真正 render 之前做了三次翻译 （源码在 runtime-dom/src/index.ts 的 normalizedCreateApp 内）：

'#app'
字符串选择器 → querySelector 拿到容器
若是 <script> 模板标签则取 innerHTML 当根模板 → App 组件
翻译成根 vnode → render(vnode, container)
翻译①：容器规范化 normalizeContainer；翻译②：组件 → vnode；翻译③：进入渲染器世界

为什么组件必须先「翻译」成 vnode？因为 render 的世界只认 vnode（第 16 章）。 根组件、子组件、元素、文本 —— 在 patch 眼里一视同仁，全是节点。统一数据结构， 才有统一的 patch / diff / 组件复用逻辑。

发射倒计时：createApp 备货 → mount 点火 → patch 上屏

21.5 app 对象的其余 API：use / component / directive / provide

mount 之外，app 对象还有五个注册方法 —— 它们全都是「往 _context 里塞东西」，各有一个值得注意的细节：

// createAppAPI 的闭包里：
const installedPlugins: Plugin[] = [];          // ⭐ 记录本 app 装过哪些插件（防重复）

use(plugin, ...options) {
  if (installedPlugins.includes(plugin)) {      // 重复安装 → dev 警告
    warn(...);
  } else if (plugin && isFunction(plugin.install)) {
    installedPlugins.push(plugin);              // ① 对象插件：调它的 install 方法
    plugin.install(app, ...options);
  } else if (isFunction(plugin)) {              // ② 函数插件：直接调用
    installedPlugins.push(plugin);
    plugin(app, ...options);
  } else {
    warn(`Invalid plugin...`);
  }
  return app;
},
component(name, component) {
  this._context.components[name] = component;   // 注册进全局表
  return this;
},
directive(name, directive) { this._context.directives[name] = directive; return this; },
provide(key, value) { (this._context.provides)[key] = value; return this; },  // 第 24 章的原型链顶端
🧠 mixin：最后一个老 API 的处境
app.mixin 仍然存在（合并进组件 options，data 用深合并、钩子合并成数组依次执行）， 但官方文档已把它标为「不推荐」—— 逻辑来源分散、命名冲突隐晦。 组合式函数（composable）是官方给出的替代：显式 import、显式调用、类型可推导。 读老项目时你会遇到 mixin，理解它的合并策略即可，新代码请用组合式。

22.2 initProps：props 与 attrs 的「分家」

父组件传来的 vnode.props 是一锅生的：声明过的是 props，没声明的是 attrs（透传属性）。 initProps 就是分家现场： 

function initProps(instance, rawProps, isStateful) {
  const props = {};      // 将变成 shallowReactive
  const attrs = {};      // 将变成 shallowReactive
  setFullProps(instance, rawProps, props, attrs);   // 按 propsOptions 分拣

  if (isStateful) {
    // ⭐ 注意是「浅」响应式：只有第一层是响应的
    instance.props = shallowReactive(props);
  } else {
    instance.props = props;   // 函数式组件不包代理（性能）
  }
  instance.attrs = shallowReactive(attrs);
}

function setFullProps(instance, rawProps, props, attrs) {
  const options = instance.propsOptions;   // 组件声明的 props 规范
  for (const key in rawProps) {
    const value = rawProps[key];
    if (options && hasOwn(options, key)) {
      props[key] = value;                  // 声明过 → props
    } else {
      attrs[key] = value;                  // 没声明 → attrs（透传）
    }
  }
}
🧠 为什么是 shallowReactive 而不是 reactive？
props 通常是父传子的一次性快照，深层对象基本不会再被组件内部改写。 深度代理一个大对象要为每层嵌套建 Proxy + 收集依赖，开销巨大却几乎没收益 —— 所以 Vue 只代理第一层。这也是官方文档「不要在子组件里改 props」的性能注脚。
⚠️ attrs 的默认归宿：透传到根元素
子组件没声明 inheritAttrs: false 时，attrs（class、style、id...） 会在 patch 时自动合并到根元素上。声明 false 后，透传权交给你 —— 用 v-bind="$attrs" 手动指定去处。 本质都是同一份 attrs 数据，只是流向不同。

22.3 emit：一个事件名的两次变换

子组件里 emit('my-change', 1)，父组件里写的却是 @my-change。 两者怎么对上？答案是：emit 到 props 里找以事件名变换来的函数： 

function createEmit(instance) {
  function emit(event, ...args) {
    // 事件名两次变换：my-change → onMy-change（原样）→ onMyChange（驼峰）
    let handlerName;
    let handler =
      instance.props[(handlerName = toHandlerKey(event))] ||          // 原样
      instance.props[(handlerName = toHandlerKey(camelize(event)))];  // 驼峰
    // v-model 的 update:xxx 事件还有一次连字符兜底（仅 model 监听器会走这）
    if (!handler && isModelListener) {
      handlerName = toHandlerKey(hyphenate(event));
      handler = instance.props[handlerName];
    }
    if (handler) {
      callWithAsyncErrorHandling(handler, instance, args);  // 实际就是调用父组件传的 onXxx 回调
    } else {
      // ...未监听时的 dev 警告（v-model 以外的自定义事件不警告）
    }
  }
  return emit;
}
// toHandlerKey('my-change') = 'onMy-change'；camelize('my-change') = 'myChange'
💡 原来如此
emit 不是什么「事件总线」，它就是调 props 里的函数。 @my-change="fn" 编译后就是 onMyChange: fn —— 和 props 传函数是同一条路，只是命名有约定。理解了这一层， 「emit 和 prop 传函数有什么区别」这种面试题就有了降维打击的答案。

22.4 initSlots：编译好的「函数袋」

关键认知：插槽在编译期就已经变成了函数。模板里的子内容会被编译成 { default: () => [...] } 这样的槽对象， initSlots 只需要把它挂上实例（需要懒代理/兜底时再包一层 Proxy）： 

// 你写的模板（子组件）：
//   <div><slot :item="item"></slot></div>

// 父组件模板编译产物（静态内容的槽）：
h(Child, null, {
  default: () => [h('span', null, '固定文案')],   // 函数！
  _: 1 /* STABLE 标记 */
})

// initSlots（教学版）：
function initSlots(instance, children) {
  if (typeof children === 'object' && !Array.isArray(children)) {
    instance.slots = children;      // 编译器产出的槽对象，直接挂
  } else {
    instance.slots = { default: () => normalizeChildren(children) };
  }
}
🧠 普通插槽 vs 作用域插槽：函数调用的时机不同
编译后它们都是函数，但普通插槽的函数体在父组件渲染时执行（生成静态内容）， 作用域插槽的函数在子组件渲染时带着 slotProps 调用 —— 所以子组件数据一变， 槽内容能跟着变。slot 对象里的 _: 1（STABLE 标记，官方 SlotFlags： STABLE=1 / DYNAMIC=2 / FORWARDED=3）告诉 patch：槽内容不依赖子组件的状态，子组件更新时 可以跳过槽的重新收集；一旦槽里用到了 slotProps（作用域插槽），编译器就会打 _: 2（DYNAMIC）强制每次更新 —— 又是一个编译期反哺运行时的例子（第 30 章）。

22.6 defineExpose：把组件的「内部」关进抽屉

script setup 的组件默认是封闭的：父组件拿 ref 拿到的实例代理， 什么都看不到（这是有意的封装）。想主动暴露，必须用 defineExpose： 

// setupContext.expose 的真身：
expose(exposed) { instance.exposed = exposed || {}; }

// 父组件 ref 拿到的其实是：
const publicThis = exposed
  ? new Proxy(exposed, PublicInstanceProxyHandlers)   // ⭐ 只包 exposed
  : instance.proxy;                                    // options API：整实例可见

// 子组件：
const count = ref(0);
defineExpose({ reset: () => (count.value = 0) });
// 父组件：childRef.value.reset() ✅；childRef.value.count ✗（被关在抽屉外）
🧠 为什么默认封闭是正确的设计
组件间的合法通道只有三条：props（下行）、emit（上行）、插槽（内容注入）。 ref 直捅内部是「后门」—— 默认关上，逼你先想想这条通信是否真的该存在。 后门打开时也只开一条缝（exposed 白名单），而不是整扇门。 对比 React 的 useImperativeHandle —— 同一个设计决定，同一个理由。

22.6 mergeProps 的合并细则：同名 prop 冲突怎么办

16.6 的表格里埋了合并策略，这里给全量规则（源码 vnode.ts → mergeProps， createVNode / cloneVNode / v-bind 合并都走它）： 

for (const key in props) {
  if (key === 'class') {
    ret.class = normalizeClass([ret.class, toMerge.class]);   // 数组归一化拼接
  } else if (key === 'style') {
    ret.style = normalizeStyle([ret.style, toMerge.style]);   // 对象合并，后者优先
  } else if (isOn(key)) {                                     // on 开头 → 事件
    const existing = ret[key], incoming = toMerge[key];
    if (incoming && existing !== incoming) {
      ret[key] = existing
        ? [].concat(existing, incoming)                        // ⭐ 两个都调
        : incoming;
    }
  } else {
    ret[key] = toMerge[key];                                   // 其余：后者覆盖
  }
}
🧠 事件为什么合数组而不是覆盖？
高频场景：组件内部自己绑了 onClick（比如关闭弹窗）， 同时父组件又透传了 v-bind="$attrs" 里的 onClick（埋点）。 覆盖会让其中一方静默失效 —— 排查极难。合并数组让两者都跑，这是「透传不丢行为」的保证。 代价：invoker 里要处理数组（第 15 章的 invoker.value 调用前判断 Array.isArray 依次调用）。

ref 形态赋什么注意
ref 对象DOM 元素 / 组件公开代理卸载时自动赋 null
函数每次都调用：挂载传 el、更新传新 el、卸载传 null是「双态钩子」，不只是第一次拿 DOM
字符串（Options API）this.$refs[name]本质同样走 setRef，只是终点不同
v-for 中的 ref数组（按渲染顺序）不是响应式数组 —— 不要依赖它做模板渲染
🧠 三个「原来如此」
① 为什么 onMounted 里才拿得到？—— 赋值在 post 队列（23 章），和 mounted 同一工序，DOM 已就位；
② defineExpose 的消费点就在这：组件 ref 拿到的是 instance.exposed 的代理， 没暴露的内部一概不可见 —— 封装边界由「setRef 赋什么」物理决定；
③ 函数式 ref 在每次更新都会执行 —— 想做「元素进出视口埋点」这类逻辑，它比 onMounted 更准。
自测一下：组件三大件

1. 子组件没有声明 id 这个 prop，模板根元素上却出现了 id —— 是谁干的？怎么阻止？
2. 为什么在模板里 emit('my-change') 能触发 @myChange？中间发生了什么变换？

答案：
1. attrs 透传（fallthrough）：initProps 分家时没进 props 的属性进入 instance.attrs， patch 时默认合并到根元素。组件声明 inheritAttrs: false 即可阻止，改用 v-bind="$attrs" 手动指定。
2. emit 内部把 'my-change' 依次尝试 camelize（→ myChange）和 capitalize（→ MyChange）， 拼上 on 前缀后去 props 里找 onMyChange 调用 —— 本质就是调 props 里的函数。

第 23 章 · 组件与调度篇

调度器全貌：queueJob 与 nextTick

你在事件函数里连改三次数据，页面只重渲染一次；你在 updated 里读 DOM， 读到的一定是新值；你听说 nextTick 是微任务，但它凭什么排在 DOM 更新之后？ 这一章是全书调度知识的总装车间 —— 官方源码只有一个文件： runtime-core/src/scheduler.ts，不到 300 行，却支撑起整个框架的更新时序。

23.1 问题引入：同步更新的灾难

假设更新是同步的 —— 每次 trigger 立刻重渲染。看一个日常操作的下场：

handleClick() { a=1; b=2; c=3; } → trigger ×3 → render + diff ×3 → DOM 动了 3 次，前 2 次全是中间态
换成异步批处理： → trigger ×3 → job 只入队 1 次 → 微任务里 render + diff ×1 → DOM 只动最后那一次 ✅
批处理省掉的不仅是 render 次数，还有两次完整的 diff 和 DOM 操作 —— 用户更是一帧都看不到中间态

第 19 章你已经见过骨架版：Set 去重 + Promise.resolve().then(flushJobs)。 生产版要解决三个它没解决的问题：①父组件必须先于子组件更新（子组件可能依赖父组件更新后的状态）； ②有些事必须赶在渲染前 / 渲染后做（beforeUpdate / updated / watch 的 pre/post）； ③用户要能「在更新完成后插一脚」（nextTick）。

取号大厅：同帧任务合并成一趟 flush，nextTick 坐散场班车

23.2 queueJob：旗标去重 + 有序插入

const queue = [];              // ⭐ 主队列（数组，因为要保持有序）
let flushIndex = -1;           // 本轮已 flush 到哪（flush 期间也能入队）
const pendingPostFlushCbs = [];// post 队列：updated / mounted / flush:'post' watcher...

export function queueJob(job) {
  // ① 去重靠 QUEUED 旗标（O(1) 位判断，不扫描队列）
  if (!(job.flags & SchedulerJobFlags.QUEUED)) {
    const jobId = getId(job);
    const lastJob = queue[queue.length - 1];
    if (
      !lastJob ||
      // ② 快车道：id ≥ 队尾 → 直接 push（天然有序，绝大多数走这条）
      (!(job.flags & SchedulerJobFlags.PRE) && jobId >= getId(lastJob))
    ) {
      queue.push(job);
    } else {
      // ③ 慢车道：二分查找插入位（findInsertionIndex），保证队列始终按 id 升序
      //    pre watcher 与所属组件 update 同 id，会被插到 update 前面 —— 卸载时能被跳过
      queue.splice(findInsertionIndex(jobId), 0, job);
    }
    job.flags |= SchedulerJobFlags.QUEUED;
    queueFlush();              // ⭐ 入队成功就预约 flush（微任务）
  }
}
🧠 排序的意义：父先子后
每个组件的 update job 都带着 instance.uid（组件创建顺序编号，父 < 子）。 队列始终按 id 升序维护，父组件必然先重渲染：父给子传的新 props 已就位，子组件再更新时 shouldUpdateComponent（第 19 章）判断的才是「最终态」—— 避免子组件基于过期 props 白跑一趟。 这就是为什么队列不用 Set 而用数组：排序是硬需求。

23.3 flushJobs：一趟洗牌的完整流程

const resolvedPromise = Promise.resolve();
let currentFlushPromise = null;

export function flushJobs(seen) {
  isFlushing = true;
  currentFlushPromise = null;
  isFlushPending = false;

  try {
    // ① 先整体排序一次：uid 小的先跑 —— 父组件先更新
    queue.sort((a, b) => getId(a) - getId(b));

    // ② 下标遍历而不是 shift：flush 中新入队的 job 已被 findInsertionIndex
    //    插到正确位置，天然被本轮消化（while + sort 的老写法已废弃）
    for (flushIndex = 0; flushIndex < queue.length; flushIndex++) {
      const job = queue[flushIndex];
      if (job && !(job.flags & SchedulerJobFlags.DISPOSED)) {
        if (__DEV__ && check(job)) continue;   // dev：100 层递归上限保护
        callWithErrorHandling(job, job.i,
          job.i ? ErrorCodes.COMPONENT_UPDATE : ErrorCodes.SCHEDULER);
        job.flags &= ~SchedulerJobFlags.QUEUED;   // 跑完摘掉去重旗标
      }
    }
  } finally {
    flushIndex = -1;
    queue.length = 0;

    // ③ 主队列清空后，才 flush post 队列：updated、mounted、watch flush:'post'、模板 ref 赋值
    flushPostFlushCbs(seen);

    currentFlushPromise = null;
    // ④ post 队列里可能又改了数据 → 队列非空就再来一轮
    if (queue.length || pendingPostFlushCbs.length) {
      flushJobs(seen);          // 官方还带 100 层递归上限保护（检查死循环更新）
    }
  }
}

// 触发点：queueJob / queuePostFlushCb 的首次入队
function queueFlush() {
  if (!currentFlushPromise) {
    currentFlushPromise = resolvedPromise.then(flushJobs);  // ⭐ 微任务
  }
}
💡 生命周期钩子的真相：调度器的「工序位」
现在可以把生命周期连起来了：pre watcher（flush:'pre'，默认值）是一个带 PRE 旗标的 job， 与所属组件的 update 同 id 入队、排在其前 —— 组件被父级卸载时能被顺手跳过； onBeforeUpdate 在组件更新前同步调用（updateComponentPreRender 里）； onMounted / onUpdated / flush:'post' watcher 进 post 队列，由 queuePostRenderEffect 入队、主队列清空后统一执行。 所谓「生命周期时机」，本质是调度器队列的工序位置。第 19 章的「注册即挂榜」+ 本章的「flush 时工序」，拼图完成。

23.4 nextTick：排在 flush 之后的「顺路车」

nextTick 的真身只有一行核心逻辑 —— 它搭的是同一条微任务链的顺风车：

const p = Promise.resolve();

export function nextTick(fn) {
  // 有 flush 在排队/进行中 → 挂在 currentFlushPromise 后面（更新完了才轮到我）
  // 没有 → 挂在普通 resolved promise 后面（下个微任务直接跑）
  return (currentFlushPromise || p).then(fn);
}
同步代码 → count = 1（trigger，job 入队） → nextTick(fn) 挂上 flush 链 → setTimeout(fn2) 进宏任务队列
微任务 1：flushJobs → render + diff → DOM 更新 → 微任务 2：nextTick 的 fn → ……全部微任务跑完…… → 宏任务：setTimeout 的 fn2
nextTick 回调永远看到「最新 DOM」，setTimeout 则不一定 —— 它们隔着整个微任务队列
⚠️ 高频误区
nextTick 不是 setTimeout 的封装（宏任务）。它是微任务链的一环， 这意味着：① 它比 setTimeout 快得多（不用等整轮事件循环）；② 顺序有保证 —— 在 nextTick 里再 nextTick，后者一定在后者的 DOM 状态之后。 Vue2 的 nextTick 曾按 microtask 降级到 setImmediate/setTimeout，Vue3 直接锁定 Promise。

23.5 nextTick 的五个高频追问

追问①：nextTick 能 await 吗？

能 —— 它返回的就是 Promise，这是「真身是一行 then」决定的，没有任何黑魔法：

async function handleClick() {
  count.value++;
  await nextTick();              // 走到这里时，DOM 已经按 count 新值更新完
  console.log(el.textContent);   // 安全读取新 DOM
}

// 等价的老写法：nextTick(() => { console.log(el.textContent); })
// 两者都是「挂到 flush 链之后」，await 只是 p.then 的语法糖

追问②：nextTick 里再改数据、再调 nextTick，顺序会乱吗？

count++;                            // 触发第 1 轮 flush 排队
nextTick(() => {                    // A：挂第 1 轮 flush 链尾
  count++;                          // A 里又改数据 → 触发第 2 轮 flush 排队
  nextTick(() => console.log("C")); // C：挂第 2 轮 flush 链尾
});
nextTick(() => console.log("B"));   // B：也挂第 1 轮链尾

// 微任务队列严格保序，实际执行顺序：
// flush① → A（改数据，注册 flush②）→ B → flush② → C
// ⭐ 注意 B：执行时 count 已被 A 改成新值，但 DOM 还是第 1 轮的旧值！
🧠 B 为什么「半新半旧」？
B 排队时挂的是第 1 轮 flush 的链；A 中途新开一轮 flush，B 不会跟着「跳车」到第 2 轮。 所以在 nextTick 回调里再改数据时，同链后继读到的是「count 新、DOM 旧」的中间世界。 实践守则：nextTick 回调里尽量只读 DOM；要改数据，就把「读新 DOM」的动作挂到新一轮 nextTick 上（上面例子的 C）。下面的实验室场景④可以亲手看到 B 的「错位瞬间」。

追问③：updated 钩子和 nextTick，用哪个？

nextTickonUpdated
注册位置任何地方（事件回调、async 函数、组合式函数）只能 setup 同步阶段（currentInstance 指针在家的窗口期，第 19 章）
触发范围只等「这次触发」的那一轮 flush本组件任何一次更新完成都触发
适合一次性动作：「这次改完数据我要读一次 DOM」常驻逻辑：「每次更新后都要做」

追问④：为什么不用 setTimeout？—— 一张图看懂「渲染时机」

调用栈清空 → ① 清空整个微任务队列 → ② 浏览器渲染（rAF → style → layout → paint） → ③ 取一个宏任务（setTimeout）
事件循环的一轮。微任务在「渲染之前」清空，宏任务在「渲染之后」才轮到 —— 这是 nextTick 又快又稳的根本原因

三个推论：① nextTick 回调在本轮渲染前跑完，用户永远看不到中间态；② setTimeout 至少下一帧才执行，还要和其他宏任务排队；③ 假如用 setTimeout 做更新调度，一帧内多次改数据会画出多次中间态 —— 帧率直接崩。

追问⑤：nextTick 实现史：一条「降级链」的故事

Vue2 的 nextTick 是一段著名的降级链，原因只有一个：nextTick 必须是微任务（否则渲染时机不成立）， 但老浏览器 / 老 WebView 的 Promise 支持参差不齐。于是从高到低逐级探测：

23.7 递归更新保护：「Maximum recursive updates」从哪来

第 23.3 节的 flushJobs 里藏着一行防御代码，它就是那个著名报错的出处：

// checkRecursiveUpdates：seen 是本轮 flush 携带的 Map
const count = seen.get(job) || 0;
if (count > RECURSION_LIMIT /* 100 */) {
  throw new Error(
    'Maximum recursive updates exceeded in component. ' +
    'This means you have a reactive effect that is mutating its own dependencies...'
  );
}
seen.set(job, count + 1);
job();

什么代码会触发它？effect 更新了自己依赖的数据，且不是有意的：

// ① render 里改自己读的数据
{{ list.sort() }}                        // sort 原地改数组 → 读 list 又写 list → 循环

// ② watch 的回调里改自己 watch 的数据（无守卫）
watch(() => form.value, v => { form.value = normalize(v) })  // 每次都写 → 又触发

// ③ updated 钩子里改数据且每次都改
onUpdated(() => { counter.value++ })     // 每次渲染后都改 → 永远渲染不完
⚠️ 生产环境没有这个警告怎么办
递归检查主要在开发模式生效（生产构建会剥离部分检查）。上线后的表现是「页面卡死 / 更新风暴」。 排查口诀：找一个「渲染函数或其钩子里写了渲染函数读过的数据」的赋值语句； 修复姿势三选一：改成计算属性、给赋值加 if (!isEqual(next, prev)) 守卫、 或挪进事件回调。本质都是打破「读 → 写 → 触发读」的闭环。

23.7 插队与撤单：invalidateJob 与 flush:'sync'

生产级调度器还有两个边缘但必会的机制：

// 场景：flush 进行中，父组件 job 先跑 → 给子组件传了新 props → 子组件 job 已在队尾
// 若等子 job 照常执行，它读到的 next/props 又要再来一轮 patch —— 浪费一整次

export function invalidateJob(job) {
  const i = queue.indexOf(job);
  if (i > flushIndex) {          // 还没轮到它
    queue.splice(i, 1);          // ① 从队列移除
  }
}
// 调用点：updateComponentPreRender（beforeUpdate 工序）里发现 next 变化时
// ⭐ 效果：子组件的更新并入「父组件正在进行的这一轮」，子组件看到的 props 就是最终态
flush 模式注册 API执行时机典型场景
pre（默认）watch(source, cb)组件更新前（23.3 的 pre 队列）读写状态、联动校验
postwatch(source, cb, { flush: 'post' }) / watchPostEffectDOM 更新后（post 队列）测量 DOM、初始化图表
sync{ flush: 'sync' } / watchSyncEffect数据一变立即执行，不排队极少数需要即时联动（慎用：失去批处理）
⚠️ sync 的代价
flush:'sync' 意味着放弃 23.1 讲的一切批处理红利： 一个函数里改三次数据，回调跑三次。它的合法用途极窄（比如拖拽时同步计算位置）， 面试能说清「sync 放弃了什么」比「sync 是什么」值钱。
自测一下：调度器

1. 为什么队列用数组不用 Set？
2. 父组件更新导致子组件 props 变化，父和子的 update job 谁先执行？靠什么保证？
3. nextTick 里读 DOM 为什么一定是新值？在 setTimeout 里读呢？

答案：
1. 因为 flush 前要按 job.id 排序（父先子后），Set 无序；数组 + includes 去重即可。
2. 父先。每个 job.id = instance.uid，创建顺序父 < 子，flushJobs 开头 sort 保证。
3. nextTick 的回调挂在 currentFlushPromise 之后，DOM 更新的微任务先执行完； setTimeout 是宏任务，要等所有微任务（包括 flush 和 nextTick）跑完才轮到 —— 读到什么取决于之前是否触发过更新。

provide/inject 与内置组件走读

收官前的最后一站：四个「官方标准件」。它们的实现思想各不相同 —— 原型链、状态机、 DOM 挪移、patch 分流 —— 但用的全是你已经学过的机制。本章对照官方源码走读， 帮你把 vuejs/core 里最后一批「常用而未读」的文件划掉。

24.1 provide/inject：原型链的一次妙用

// 每个组件初始化时：
instance.provides = parent
  ? parent.provides                       // ⭐ 原型继承父的 provides
  : Object.create(appContext.provides);   // 根组件：以全局 provides 为原型

export function provide(key, value) {
  const currentInstance = getCurrentInstance();
  if (currentInstance) {
    currentInstance.provides[key] = value;   // 只是普通赋值！
  }
}

export function inject(key, defaultValue) {
  const instance = getCurrentInstance();
  const provides = instance.parent?.provides;
  if (key in provides) {
    return provides[key];                    // 原型链自动向上找 → 「就近原则」白送
  }
  return defaultValue;
}
🧠 一行原型链 = 沿父链循环查找
「子组件找注入值，先找最近的祖先」听起来要写「沿 parent 链一层层向上循环」—— 但 Object.create(parent.provides) 把这层循环交给了 JS 引擎： 属性查不到就自动沿原型链上溯。就近原则是原型链的天然属性，不是写的逻辑。 官方仓库的 apiInject.ts 一共不到 60 行，是 runtime-core 里性价比最高的阅读材料。
💡 provide 的响应式语义
provide 的 value 如果是 ref / reactive，注入侧拿到的是同一个引用（不脱壳、不拷贝）—— 上游改值下游自动更新；官方建议「提供只读视图时配 readonly(ref)」：依赖可下传，写入权留在源头。 注入原始值则完全静态 —— 后续互不相干。所以约定俗成：provide 的 key 用大写常量、value 尽量给 ref。
⚠️ 两处工程细节
① appContext.provides 用 Object.create(null) 创建 —— 不带 Object 原型，防止 'constructor' 这类 key 污染注入表； ② inject 的 key in provides 判断（而非 provides[key] 取值判断）—— 这样注入值为 undefined 和「未注入」才得以区分。
provide/inject = 原型链找爷爷：自己没有，就一路问上去

24.2 defineAsyncComponent：一个状态机包装器

export function defineAsyncComponent(source) {
  // 真身是 defineComponent 包出来的包装组件；__asyncLoader 字段存的是「加载函数」本身
  return defineComponent({
    name: 'AsyncComponentWrapper',
    __asyncLoader: load,
    setup() {
      // 官方用一组独立的 ref 表达状态（教学版收拢成 reactive 对象更好读）：
      //   loaded ref —— 组件加载好了吗     error ref —— 失败信息
      //   delay ref —— loading 延迟（默认 200ms）  timeout ref —— 超时打 errorComponent
      const refs = reactive({
        status: 'pending',           // pending → resolved / failed
        error: null, loaded: 0,
        delay: source.delay || 200, timeout: source.timeout,
      });
      // loader() 返回 Promise → then 记录组件、resolve；catch 进 failed
      // setTimeout(delay)：显示 loadingComponent
      // setTimeout(timeout)：超时打 errorComponent
      // 失败还能 retry(() => loader())，配 onError 钩子
      return () => {
        if (refs.status === 'resolved') return h(resolvedComp, ...);
        if (refs.status === 'failed' && errorComp) return h(errorComp);
        if (refs.status === 'pending' && loadingComp && refs.delayElapsed) return h(loadingComp);
        return null;
      };
    },
  });
}

本质：一个包装组件，render 函数根据状态机的当前状态返回不同 vnode。 它和 Suspense 的分工：defineAsyncComponent 管「单个组件」的加载态， Suspense 管「整棵依赖树」的等待态（含嵌套异步 setup）。

24.3 KeepAlive：缓存 vnode 的「第三个容器」

KeepAlive 是内置组件里最有意思的一个：它不渲染任何东西，只做「搬运工」。 三个核心机关（官方源码 components/KeepAlive.ts）：

机关做法为什么
① 缓存表cache: Map<key, vnode> + keys: Set 维护使用顺序，超 max 时驱逐最久未用切回来不用重建，状态全在
② DOM 挪移失活时把真实 DOM 从页面移进一个隐藏容器；激活时再移回来DOM 不销毁 → 状态、滚动位置、播放进度全部保留
③ patch 分流processComponent 前先问 KeepAlive：缓存里有吗？有 → 激活旧 vnode，无 → 挂新的配合 shouldUpdateComponent 决定走哪条路
切换 away → deactivated（不是 unmounted！） → DOM 移入隐藏容器 + vnode 入缓存
切回来 → activated（不是 mounted！） → 缓存命中 → DOM 移回页面（LRU 顺手修剪）
所以被 KeepAlive 的组件生命周期是 activated/deactivated —— 因为 DOM 从未销毁，mounted 只会来一次

24.4 Teleport：patch 的第二入口

// vnode.type === Teleport 时，patch 走的不是 processElement/Component：
function processTeleport(n1, n2, container, anchor) {
  if (n1 == null) {
    // 挂载：target = document.querySelector(to)
    const target = (n2.target = querySelector(n2.props.to));
    mountChildren(n2.children, target);        // ⭐ 直接把子元素挂到 target
  } else {
    // 更新：
    n2.el = n1.el;
    const target = (n2.target = querySelector(n2.props.to));
    if (target !== n1.target) {                // ⭐ to 动态变了 → 整体搬走
      moveTeleport(n2, target);
    }
    patchChildren(n1, n2, target);             // 正常 diff
    if (n2.props.disabled !== n1.props.disabled) {  // ⭐ disabled 切换 → 搬回原位
      toggleTeleportDisabled(n2);
    }
  }
}

Teleport 破坏了一个假设：「子元素都渲染在父容器里」。为此官方把 patch 拆出了第二入口 —— vnode 上带 shapeFlag.TELEPORT，进入 patch 时优先分流。 注意 mounted 的语义：Teleport 的 children 挂在 target 上，但组件实例树不变 —— 逻辑树和 DOM 树在这里正式分家（第 16 章「VNode 树 ≠ 组件树」的进阶版）。

24.5 Suspense：异步等待的「计数器 + 状态机」

// ① 约定：async setup() 返回的 Promise 存进 vnode 的 asyncDep
//    （同步组件没有 asyncDep → Suspense 直接跳过它）
// ② 挂载：初始化 suspense 实例：
suspense = {
  vnode,
  deps: 0,                 // ⭐ 「未完成异步任务」计数器
  pendingId: 0,            // 区分新旧内容的切换批次
  isInFallback: false, ... // 当前显示的是不是 fallback 分支
}
// ③ 收集：渲染子树遇到 asyncDep → deps++，
//    同时把「Promise 完成 → deps-- → 尝试 resolve」挂进 post 队列
// ④ deps === 0 → resolve：切回默认插槽内容
queuePostRenderEffect(() => { suspense.isInFallback = false; /* 切换显示 */ }, ...)
// ⑤ 期间显示 fallback 插槽；resolved 后切默认插槽内容（24.4 的 enter 过渡可用）
成员作用
deps 计数器每个 async setup +1，resolve 后 -1；归零即「整棵子树就绪」
pendingId区分旧内容卸载与新内容显示，防切换竞态
fallback / content 分支就是两个普通插槽 vnode，走同一套 patch（18 章）
onResolve / onFallbackResolve对外事件钩子，全部走 post 队列（第 23 章）
🧠 一句话本质
Suspense 把「异步」从组件内部抽到组件树外：子组件只管返回 Promise，等待与展示的编排交给 父级 Suspense 的计数器。它和 defineAsyncComponent（24.2 单组件状态机）是同一问题的两个粒度 —— 一个管一棵树，一个管一个点。SSR 流式渲染（36.4）的占位机制，底层正是这个 pending 计数。

24.7 KeepAlive 的三个工程细节

细节规则源码位置
缓存 key 怎么定vnode.key == null ? comp : vnode.key —— 同一组件的多个实例要靠 key 区分（否则互相串缓存）KeepAlive.ts 的 cacheSubgraph / cache 建键
include/exclude 何时匹配在 processComponent 入口就检查组件 name：不匹配 → 直接走普通挂载/卸载，根本不进缓存体系name 匹配函数（支持字符串/正则/数组）
LRU 驱逐时发生什么超 max 时淘汰最久未用的：如果它当前还挂在页面上 → 先搬运进隐藏容器再触发 deactivated；已经不在页面 → 直接走完整 unmountpruneCacheEntry
🧠 同组件多实例的缓存串台
路由里用 <KeepAlive><router-view /></KeepAlive> 缓存「同组件不同参数」的页面 （如 /user/1 和 /user/2 渲染同一个 User.vue）时，若不给 router-view 设置按路由分化的 key， 两页会共用一条缓存 —— 数据串台。原因就是上面的建键规则：key 缺省时以组件对象为准， 同一个组件对象自然只有一条缓存。解法：给 key 绑路由参数，让「身份」真的不同。

24.7 实战组合：KeepAlive + 路由缓存的标准姿势

<RouterView v-slot="{ Component }">
  <KeepAlive :include="['Home', 'Detail']" :max="10">
    <component :is="Component" :key="$route.fullPath" />
  </KeepAlive>
</RouterView>
配置作用不写的后果
include白名单：只有列名的组件进缓存（匹配组件 name）所有页面缓存 → 表单页旧数据残留、逻辑错乱
maxLRU 上限，超出淘汰最久未访问（24.3 的机关①）长会话内存持续增长
:key="$route.fullPath"同组件不同参数（/detail/1 → /detail/2）视为不同实例参数变了页面不刷新（组件复用但状态没重置）
💡 onActivated 是缓存页的「每次都跑」钩子
缓存页的 mounted 只来一次，数据刷新要写在 onActivated 里（每次切回都执行）。 常见模式：mounted 拉一次全量，onActivated 里只做轻量校验/滚动位置恢复 —— 这是「缓存 + 新鲜度」的平衡术。

24.8 组件通信七种武器：一张表选型

武器方向适用反模式
props父 → 子一切数据下行深层逐级转传（props 钻井）→ 换 provide
emit / v-model子 → 父事件上报 + 双向绑定（22.3 / 34.2）emit 传对象让父改子内态 → 边界混乱
defineExpose + 模板 ref父 → 子（命令式）focus、滚动画布等「方法调用」（22.7）拿 exposed 改子组件状态 → 应该用 props
provide / inject祖先 → 子孙（跨层）主题 / 用户 / 请求实例等「环境依赖」拿它传业务数据 → 数据流不可追
slots（含作用域）父渲染进子内容定制（22.4）用 slot 传数据 → 应该用 props
attrs 透传父 → 子根元素class / 事件的包装组件（22.2 / 22.6）依赖它传业务 props
全局状态（pinia）任意跨页面共享状态组件私有状态塞全局 → 内存与耦合双输
🧠 pinia 的底层你早就懂了
全局状态库的本质 = app.provide(storeKey, store) + reactive(store) + devtools 钩子： store 用 reactive（第 3 章）保响应，provide 保证全树可注入（24.1），effectScope 管订阅清理（第 10 章）。 学到这里，pinia 对你已是「透明盒子」—— 这就是读源码最大的回报。
自测一下：内置组件

1. 为什么 KeepAlive 包裹的组件用 activated 而不是 mounted 判断「被切回来了」？
2. provide/inject 的「就近原则」为什么不需要写循环？
3. Teleport 后子组件的父实例还成立吗？（比如 inject 还能用吗）

答案：
1. DOM 从未销毁 —— 组件实例一直活着，mounted 只在真正首次创建时触发一次； 切换只是 DOM 挪进/挪出隐藏容器，所以对应钩子是 deactivated/activated。
2. instance.provides 的原型是 parent.provides，属性查找由 JS 引擎沿原型链自动上溯， 最近祖先的 provide 天然先被找到。
3. 成立。Teleport 只搬 DOM，组件树（vnode 树 / 实例父子关系）完全不变，inject/provide 照常工作 —— 「逻辑树 ≠ DOM 树」。
