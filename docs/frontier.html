错误处理：捕获与传播

渲染函数抛错、watch 回调抛错、生命周期钩子抛错 —— 如果没有一套体系， 任何一处用户代码的异常都会炸掉整个组件树更新。Vue 的答案是两层结构： 调用时包装（接住错误）+ 实例链上溯（处理错误）。 官方源码：runtime-core/src/errorHandling.ts。

35.1 第一层：callWithErrorHandling 包装一切

export function callWithErrorHandling(fn, instance, type, args) {
  let res;
  try {
    res = args ? fn(...args) : fn();     // 用户代码（render / 钩子 / 回调）
  } catch (err) {
    handleError(err, instance, type);    // ⭐ 统一入口
  }
  return res;
}

// 异步版本：返回 promise 上挂 catch
export function callWithAsyncErrorHandling(fn, instance, type, args) {
  const res = callWithErrorHandling(fn, instance, type, args);
  if (res && isPromise(res)) {
    res.catch((err) => handleError(err, instance, type));
  }
  return res;
}

// 框架内所有「调用户代码」的地方都走这两个包装：
// render()、setup()、生命周期钩子、watch 回调、指令钩子、事件监听器……
💡 设计思想：接错点在调用处
Vue 不去碰你的 try/catch，也不做全局 unhandledrejection 依赖 —— 而是框架调用用户代码的每一个地方都包一层。这依赖一个纪律： 所有用户代码必须经由框架调用（这正是响应式 + 虚拟 DOM 的副产品：渲染和回调的入口高度收敛）。

35.2 第二层：handleError 沿父链上溯

function handleError(err, instance, type, throwInDev = true) {
  const contextVNode = instance ? instance.vnode : null;
  if (instance) {
    let cur = instance.parent;                       // ⭐ 从父组件开始沿链上溯
    while (cur) {
      const errorCapturedHooks = cur.ec;             // onErrorCaptured 注册的钩子
      if (errorCapturedHooks) {
        for (let i = 0; i < errorCapturedHooks.length; i++) {
          if (errorCapturedHooks[i](err, instance, type) === false) return;  // ⭐ 返回 false = 终止传播
        }
      }
      cur = cur.parent;
    }
    // 组件自己的 app.config.errorHandler（全局兜底）
    const appErrorHandler = instance.appContext.config.errorHandler;
    if (appErrorHandler) {
      callWithErrorHandling(appErrorHandler, null, ErrorCodes.APP_ERROR_HANDLER,
        [err, instance, type]);
      return;
    }
  }
  logError(err, type, contextVNode, throwInDev);     // 没人接 → 控制台警告
}
子组件 render 抛错 → 父 onErrorCaptured → 祖父 onErrorCaptured → app.config.errorHandler → 控制台警告（兜底）
任何一层钩子返回 false → 传播立刻终止（适合错误上报后吞掉）

35.4 生产分工：errorHandler 接全局，异步错误要另请高明

两件实战里最常被问到的边界事：

① errorHandler 与 onErrorCaptured 的分工：

角色管什么典型代码
app.config.errorHandler全局兜底：统一上报（Sentry / 自建埋点）、屏蔽白屏应用入口配置一次
onErrorCaptured局部降级：某棵子树出错时显示占位 UI、阻止错误惊动全局布局组件 / 边界组件里

② 框架接不住的错误：第 35.1 节说过「框架只包它自己发起的调用」。这三类错误框架看不见：

setTimeout(() => { throw new Error('x') }, 0);   // 宏任务回调 → 框架不在调用链上
fetch(...).then(() => { throw ... });             // 未接住 rejection → unhandledrejection
new Promise(() => { throw ... });                 // 同上

// 通用兜底（不属于 Vue，属于浏览器）：
window.addEventListener('error', e => report(e));
window.addEventListener('unhandledrejection', e => report(e.reason));
// ⭐ 完整的前端监控 = Vue errorHandler + 浏览器兜底，缺一不可
🧠 记住这条边界
判断一个错误「Vue 能不能接住」只需问一句：这次调用是不是 Vue 发起的？ render、生命周期、watch 回调、事件 invoker（第 35.1 节）—— 是，接得住； setTimeout、原生事件、自己 new 的 Promise 链 —— 不是，接不住。 这条边界同样是第 26 章指令钩子、第 23 章调度器 shared 的心智模型：框架的世界止于它发起的调用。

35.4 生产环境的错误上报体系

app.config.errorHandler = (err, instance, info) => {
  // ① 错误指纹去重：同一错误刷屏会淹死日志系统
  const fingerprint = `${err.message}::${instance?.uid ?? 'root'}::${info}`;
  if (reported.has(fingerprint)) return;
  reported.add(fingerprint);

  // ② 按来源分级（info 就是 35.1 的 ErrorCodes）
  const level = info.includes('render') ? 'fatal'     // 渲染炸 = 页面白屏级
              : info.includes('watch') ? 'warn'        // watch 炸 = 功能局部受损
              : 'info';
  report({ level, fingerprint, stack: err.stack, info });

  // ③ 上报本身绝不能再抛错 —— 包一层 try/catch
  // ④ 开发期保留 console 打印，方便本地复现
};
框架管不到的漏网之鱼兜底方案
裸 Promise 的 reject（没走 callWithAsyncErrorHandling 的）window.addEventListener('unhandledrejection', ...)
setTimeout / 原生事件监听器里的错误window.addEventListener('error', ...)
资源加载失败error 事件 + capture: true
💡 双保险架构
框架的 errorHandler 管「经过 Vue 的调用」（信息最全：有 instance、info）， window 级监听管「框架外的世界」（信息少但无死角）。 两路都接到同一个上报管道，指纹去重避免重复 —— 生产监控的标准三层。

自测一下：错误处理

1. 为什么事件监听器里的错误也能被捕获？监听器是浏览器调用的啊。
2. onErrorCaptured 返回 false 的语义是什么？

答案：
1. 因为你模板里的 @click 编译后不是裸函数 —— 它被 patchEvent 包进 invoker（第 15 章）， invoker 调用真实回调时走了 callWithAsyncErrorHandling。框架从不过问「谁调用的」， 它保证「经过框架的调用」都被包装。
2. 「我已处理，停止向上传播」。适合埋点上报后吞掉错误，防止干扰上层逻辑； 不返回 false 则继续上溯，直到全局 errorHandler 或控制台兜底。

第 36 章 · 边界与生态

SSR 与 hydration：一棵 vnode 树，两台发动机

第 21 章埋了一个伏笔：为什么 createApp 要懒创建渲染器？本章揭晓 —— 同一套 runtime-core，配 DOM nodeOps 就能操作浏览器，配「字符串拼接 nodeOps」就能在服务器直出 HTML。 而客户端接手的过程叫 hydration（水合）。官方源码： runtime-core/src/hydration.ts + server-renderer 包。

36.1 服务器端：renderToString 换一台发动机

// server-renderer 包的核心思路：
// 把「操作真实 DOM」的 nodeOps 换成「操作字符串」的产物
renderToString(app, (ctx) => {
  // 遍历组件树 → 跑 render → 生成 vnode
  // 元素：_push(`<div class="box">`)   ← 不是 createElement！
  // 文本：_push(escapeHtml(toDisplayString(text)))
  // 组件：递归 renderToString 子组件
  // 结束：_push(`</div>`)
});

// ⭐ 对比第 15 章 createRenderer(renderOptions)：
//    web:     nodeOps = { createElement: document.createElement, insert: parent.insertBefore, ... }
//    server:  「nodeOps」= push('<div>') / push('</div>') —— 纯字符串工艺
// runtime-core 的渲染逻辑一行不改，只是「如何落盘」由注入方决定 —— 分层的胜利
🧠 为什么 SSR 版渲染叫「不挂牌」
服务器跑的 render 函数和浏览器是同一个（编译产物通用），只是输出端不同。 SSR 组件还会走 ssrRender 快速通道（第 33 章的另一台打印机）， 跳过 vnode 创建直接拼字符串 —— 所以服务端开销远低于客户端渲染。
hydration = 只接电线不重建：房子是服务器盖的，家电客户端来装

原因例子修法

36.4 renderToString 的另一件产物：payload 与状态传送

renderToString 返回 HTML 字符串之外，还会往传入的 context 对象里写「行李」：

const ctx = {};
const html = await renderToString(app, ctx);
// ctx.teleports   → Teleport 内容的 HTML（弹窗等挂到 body 的内容要单独搬运）
// ctx.modules     → CSS 模块等资源的记录（SSR 样式注入用）
// ctx.__asyncComponents / suspense 状态等

// 组装完整响应：
res.send(`
  <div id="app">${html}</div>                    // ① 主体
  <div>${ctx.teleports?.body ?? ''}</div>        // ② 传送门内容
  <script>window.__INITIAL_STATE__ = ${serialize(storeState)}</script>  // ③ 状态传送
`);

第 ③ 项是实战最容易漏的：服务端预取的数据（比如首屏列表）如果不随 HTML 传给客户端， 客户端复水后第一件事就是重新请求一遍 —— 首屏白快了，数据还是等。标准做法是把服务端 已有的 store 状态序列化进一个全局变量，客户端初始化 store 时直接注入（Pinia 官方文档的 SSR 章节就是这套流程的工程化封装）。

⚠️ 状态传送的安全细节
状态要序列化进 HTML，就逃不开 XSS 风险：</script> 注入、 % 编码歧义都是经典洞。务必用框架推荐的序列化器（如 devalue / @nuxt/devalue）， 不要手写 JSON.stringify 直接拼 —— 它对 </script> 不设防。

36.4 流式渲染：从一次性水合到按需水合

同步 renderToString 有个先天缺陷：最慢的组件拖住整个页面。 Vue 3.3+ 的流式 API 把 HTML 分块发送： 

import { renderToPipeableStream } from 'vue/server-renderer';

renderToPipeableStream(app).pipe(res);
// 产出顺序：
// <div id="app"><main>…静态与已就绪内容…</main>
// <!--[-->                                        ← 异步组件占位注释
// </div>                                         ← 骨架先到，用户立刻看到内容
// （异步组件就绪后，分块补发占位处的 HTML 片段）
演进阶段机制体验
同步 SSR整棵树渲染完再返回首字节被最慢组件拖住
流式 SSR骨架先发 + 占位注释，就绪后补发首屏极快，异步块逐步浮现
懒水合（3.5+）组件级策略：可视 / 空闲 / 首次交互时才水合首屏 JS 开销大幅降低，可交互时间提前
选择性水合客户端只 hydrate 已就绪/可视的部分可交互时间进一步提前（Nuxt 等元框架在推进的方向）
💡 <ClientOnly> 是最小号的「选择性」
纯浏览器组件（window 依赖、编辑器、图表）在 SSR 里跳过渲染、客户端挂载后再上 —— 流式水合是它的规模化版本。「整个页面一次水合」正在被「哪里需要水哪里」逐步取代， 这条线在 React（RSC）、Vue（3.5 懒水合 → 3.6 Vapor 无 VDOM 渲染）上完全同步。
自测一下：SSR 与 hydration

1. createSSRApp 和 createApp 的产物差异在哪一步发生？
2. hydration 只绑事件不建 DOM，那响应式数据呢？

答案：
1. 在 mount 时分岔：SSR app 的 mount 走 hydrate（认领现有 DOM）， 普通 app 走 createVNode + render 全新挂载。app 对象、编译产物、组件定义完全一致。

自定义渲染器实战：给 mini-vue3 换个画布

全书第 15 章留下的悬念终于引爆：createRenderer(nodeOps) 的注入点， 意味着 Vue 的渲染目标根本不必是 DOM。本章亲手写一个 60 行的「画布渲染器」， 让同一套组件语法跑在 canvas 上 —— 这也是小程序框架（uni-app / Taro）的全部底层原理。 本仓库的 packages/runtime-dom 就是你的参考答案。

37.1 注入点的完整清单

37.2 画布渲染器：一次「全量重绘」策略

// 组件代码不用改！仍然 h('rect', { x: 10, y: 10, w: 80, h: 30, fill: 'green' })
const canvasNodeOps = {
  createElement(type) {
    return { type, props: {}, children: [], text: '' };   // 描述对象，不碰 DOM
  },
  insert(el, parent, anchor) {
    const idx = anchor ? parent.children.indexOf(anchor) : -1;
    idx === -1 ? parent.children.push(el) : parent.children.splice(idx, 0, el);
    draw(parent);                          // ⭐ 每次结构变化 → 全量重绘
  },
  remove(el) {
    const parent = el.parent;
    parent.children.splice(parent.children.indexOf(el), 1);
    draw(parent);
  },
  setElementText(el, text) { el.text = text; draw(el); },
  parentNode: (node) => node.parent,
  nextSibling: (node) => {
    const p = node.parent, i = p.children.indexOf(node);
    return p.children[i + 1];
  },
  patchProp(el, key, prev, next) { el.props[key] = next; },
};

function draw(root) {
  const ctx = canvas.getContext('2d');
  ctx.clearRect(0, 0, canvas.width, canvas.height);
  (function walk(nodes) {
    for (const n of nodes) {
      if (n.type === 'rect') {
        ctx.fillStyle = n.props.fill;
        ctx.fillRect(n.props.x, n.props.y, n.props.w, n.props.h);
      } else if (n.type === 'circle') {
        ctx.beginPath();
        ctx.arc(n.props.x, n.props.y, n.props.r, 0, Math.PI * 2);
        ctx.fillStyle = n.props.fill;
        ctx.fill();
      }
      walk(n.children);
    }
  })(root.children);
}

// 用法 —— 与 web 端一字不差：
createRenderer(canvasNodeOps).render(h(App), { children: [] });

uni-app / Taro 的原理 = 把这张表的右列换成「调小程序 setData / native 组件」。 Vue 团队自己的 @vue/runtime-test（单元测试用渲染器）也是同一思路： 输出一棵可断言的轻量树，而不是真 DOM。 「框架核心不关心渲染目标」不是口号，是 nodeOps 这张接口表的物理现实。
⚠️ 两个工程细节
① 全量重绘在真实画布场景要用脏矩形 / requestAnimationFrame 合帧（本质又是第 23 章的批处理思想）； ② 事件：canvas 上要自己做命中检测（hit test）转发给对应节点 —— patchEvent 里挂的 invoker 需要一个坐标 → 节点的反查表。这两点都是开源 canvas 渲染器（如 vue-canvas-effect 类项目）的核心工作量。

37.4 进阶作业：给画布渲染器补上事件系统

第 37.2 节的 nodeOps 能画不能点。事件缺失的根源：canvas 只有一个真实 DOM， 事件都落在它身上，「点中了哪个节点」要自己算：

// patchProp 的 onXxx 分支：只存引用，不 addEventListener（没有真实元素可挂）
patchProp: (el, key, prev, next) => {
  if (/^on/.test(key)) { el.props[key] = next; return; }   // onClick 等
  el.props[key] = next;
}

canvas.addEventListener('pointerdown', (e) => {
  const rect = canvas.getBoundingClientRect();
  const x = e.clientX - rect.left, y = e.clientY - rect.top;
  // ⭐ 倒序遍历（最后画的在最上层）→ 深度优先命中检测
  const hit = (nodes) => {
    for (let i = nodes.length - 1; i >= 0; i--) {
      const n = nodes[i];
      const child = hit(n.children) || (inRect(x, y, n.props) ? n : null);
      if (child) return child;
    }
  };
  const target = hit(root.children);
  if (target?.props.onPointerDown) target.props.onPointerDown(e);  // 转发给节点
});
// 作业目标：pointermove / pointerleave / 拖拽选中 —— 全部基于这套 hit test
// 进阶：把 handler 存引用 + 合帧派发（回忆第 15 章 invoker 与第 23 章批处理）
🧠 做完这个作业你会真正理解什么
浏览器替 DOM 渲染器干了三件隐形的事：命中检测（事件路由）、层叠顺序（z-index）、 焦点管理。自己实现 canvas 渲染器时这三件全部现出原形 —— 这也是所有 canvas 应用框架（Fabric.js、Konva、飞书白板）的核心工程量所在。 做完它，你对「渲染器分层」的理解就从「接口表」升级到「浏览器到底替我们做了什么」。

37.4 命中检测：canvas 上的「事件冒泡」是自己写的

DOM 里浏览器替你做了 hit test（点谁高亮谁），canvas 渲染器必须自己实现 —— 这是 nodeOps 协议之外、每个自定义渲染器都逃不掉的一课： 

canvas.addEventListener('click', (e) => {
  const { x, y } = getCanvasPos(e);          // 屏幕坐标 → canvas 内坐标
  const target = hitTest(rootNode, x, y);    // 从「最上层」往下找
  if (target) bubble(target, 'click', e);    // 找到 → 模拟冒泡
});

function hitTest(node, x, y) {
  // 逆序遍历：后画的上层优先命中（画家算法）
  for (let i = node.children.length - 1; i >= 0; i--) {
    const hit = hitTest(node.children[i], x, y);
    if (hit) return hit;
  }
  return contains(node, x, y) ? node : null; // 矩形：范围判断；圆：(x-cx)²+(y-cy)² ≤ r²
}

function bubble(node, event, e) {
  let cur = node;
  while (cur) {
    const fn = cur.props['on' + event];
    if (fn && fn(e) === false) break;        // 返回 false = 模拟 stopPropagation
    cur = cur.parent;                        // 沿 parent 链上溯 = 冒泡
  }
}
🧠 这段代码解释了一个架构事实
patchEvent（第 15 章）只负责「把回调挂到节点的 props 上」，事件的触发链是宿主环境的事： DOM 有浏览器冒泡，canvas 要手写逆序命中 + 链上溯，终端渲染器可能根本没有「点击」概念。 所以官方 createRenderer 的注入点里没有事件 —— 事件天生属于平台层。 这正是 37.3 提到的「逻辑树 ≠ 平台」的又一处体现。
自测一下：自定义渲染器

1. 画布渲染器为什么可以不做属性 diff（patchProp 直接覆盖）？
2. Teleport 在画布渲染器里还能用吗？

答案：
1. 因为每次变更都是全量重绘：props 覆盖后重画的成本 ≈ diff 后最小更新的成本。 「要不要 diff」永远取决于宿主环境的写操作成本 —— DOM 写贵所以 diff，画布画便宜所以直画。
2. 能。Teleport 只是「挂载到另一个目标」，画布渲染器里 target 可以是另一个画布/图层 —— 内置组件依赖的只是 vnode 层协议，不依赖 DOM。这正是分层的威力。
