编译器：模板到 render 函数

你写的 <template> 不是浏览器能懂的东西 —— 它在构建阶段被编译成 h() 调用。本章不实现编译器（那是一座独立的山）， 但要看懂它的产物和三大优化 —— 这决定了你写模板时的性能直觉。

30.1 三段流水线：parse → transform → generate

template 字符串 → parse
→ AST 语法树 → transform
→ 优化 + 打标 → generate
→ render 函数代码
和任何编译器（Babel、TypeScript、GCC）同构：词法/语法分析 → 转换 → 代码生成
翻译流水线：模板进门，render 函数出门，三大优化是附赠的加速包

30.2 一段模板的「前后对照」

<template>
  <div class="box">
    <h1>标题不变</h1>
    <p>{{ count }}</p>
  </div>
</template>
// ① 静态节点被「提升」到函数外 —— 只创建一次，每次渲染直接复用（hoistStatic）
const _hoisted_1 = h("h1", null, "标题不变");

function render(_ctx) {
  return h("div", { class: "box" }, [
    _hoisted_1,                              // 直接引用，不重新创建 vnode
    h("p", null, _ctx.count, -1 /* PROPS 无, TEXT 有 */),
    //                                    ↑ patchFlag：告诉 patch「这个节点只有文本会变」
  ]);
}

30.3 优化一：静态提升（hoistStatic）

模板里大量内容是静态的（标题、图标、装饰节点）。不提升的话，每次渲染都为它们重建 vnode —— 纯浪费。 提升到 render 函数外后：创建一次，终身复用。配合第 17 章 patch 里 oldVNode === vnode 的短路判断 —— 连 diff 都不用做，同一引用直接跳过。

💡 写模板的黄金直觉
模板里「写死的内容」几乎零成本（提升 + 短路）。真正的开销在动态绑定的数量 —— 一个 {{ }} 就是一个动态点。把静态内容从 v-for 里挪出来，比任何手动优化都实在。

30.4 优化二：patchFlag —— 靶向更新

第 18 章的 patchElement 要 diff 完整的 props 对象。但编译器在编译期就知道哪些属性是动态的： 

// 模板：<div :class="cls" :id="id">文本不变</div>
// 编译产物（示意）：
h("div", { class: _ctx.cls, id: _ctx.id }, "文本不变",
  3 /* CLASS | ID */);      // ← 只有 class 和 id 是动态的！

// patch 时：
if (patchFlag & PatchFlags.CLASS)  只更新 class
if (patchFlag & PatchFlags.ID)    只更新 id
// 其余属性：看都不看 —— diff 一个对象的成本变成了 diff 两个布尔位

这就是 Vue3 官方 benchmark 比 Vue2 快的原因之一：运行时把编译期攒的情报花掉。 React 没有编译层（JSX 太自由），只能全量 diff —— 这是两种框架哲学的分水岭。

30.5 优化三：Block Tree / dynamicChildren

有了 patchFlag 再往前一步：patch 为什么还要递归整棵树？ 编译期把所有「动态节点」收集到一个扁平数组（dynamicChildren）里， 更新时只遍历这个数组 —— 静态的整棵子树被完全绕过：

div（静态） ├─ ul（静态） │  └─ li {{item}} ⭐
传统 patch：递归访问每个节点（含静态）
Block: [li⭐] → Block 模式：只有 1 个动态节点，只 patch 它

为什么叫 Block？模板里出现结构性指令（v-if/v-for）时会「开新块」，块的边界处理结构变化 —— 细节较多，记住结论即可：

编译器把「哪里会变」提前告诉了运行时，运行时因此能跳过一切不会变的地方。Vue3 性能的三大支柱：静态提升、patchFlag、Block Tree。

30.6 cacheHandlers：事件也提升

// 模板：<button @click="count++">
// 编译产物（开启 cacheHandlers 后）：
const _cache = [];
function render(_ctx) {
  return h("button", {
    onClick: _cache[0] || (_cache[0] = ($event) => (_ctx.count++)),
  }, "点我");
}
// 没缓存：每次渲染生成新函数 → props diff 认为变了 → 触发 patchProp
// 有缓存：同一函数引用 → diff 短路 → 配合第 15 章 invoker，事件彻底零开销

看到没 —— 第 15 章的 invoker + 第 18 章的 props diff + 编译器的 cacheHandlers，三章的知识在这里拧成了一股绳。

30.7 模板表达式的沙箱：为什么模板里写不了 window

你在模板里写 {{ Math.max(1, 2) }} 可以，写 {{ window.alert(1) }} 不行 —— 这不是浏览器限制，是编译器+运行时共同修的围栏：

// 编译期：prefixIdentifiers 处理模板里的每个标识符
const GLOBALS_ALLOWED = 'Infinity,undefined,NaN,isFinite,isNaN,parseFloat,parseInt,' +
  'decodeURI,decodeURIComponent,encodeURI,encodeURIComponent,' +
  'Math,Number,Date,Array,Object,Boolean,String,RegExp,Map,Set,JSON,Intl,BigInt,' +
  'console,Error,Symbol';

// 不在白名单、也不是 _ctx 上有的标识符 → 统一加前缀 _ctx.xxx
// 模板里写 window.alert → 编译成 _ctx.window.alert
// → 渲染时 warn: Property "window" was accessed during render but is not defined on instance.
你在模板里写实际编译成结果
{{ count }}_ctx.count从实例口袋找（第 19.6 节顺序）
{{ Math.abs(x) }}Math.abs(_ctx.x)白名单放行，用真全局
{{ window.alert(x) }}_ctx.window.alert(...)警告 + undefined 报错
{{ setTimeout(fn) }}_ctx.setTimeout(fn)警告（setTimeout 不在白名单）
🧠 为什么建围栏
① 安全：模板是「半信任输入」（组件库文档、低代码平台都允许用户写模板）， 能摸到 window 就能摸到 fetch/location —— 攻击面不可控； ② 可静态分析：标识符来源被限定后，编译器才知道哪些是「数据」哪些是「常量」， 静态提升、patchFlag 才有依据；③ 可移植：不依赖浏览器全局，SSR / 小程序渲染器（第 37 章） 才能跑同一份模板。想用 setTimeout？放进 setup 里导出 —— 需求成立时它就该是组件状态的一部分。

30.7 SFC 编译：一个 .vue 文件产出三份代码

前面六章讲的都是 <template> 的编译。完整的单文件组件由 @vue/compiler-sfc 统一处理，产出三份互相咬合的代码：

源码块编译产物关键点
<script setup>普通 setup() 函数顶层变量自动 return（编译期收集，不用手写）；编译宏被原地拆掉（见 34.4）
<template>render 函数第 30 章三段流水线；顶层变量通过 $setup 前缀访问（31.5）
<style scoped>带 [data-v-xxx] 属性选择器的 CSS同时给模板里每个元素插桩 data-v-xxx attr —— 样式隔离的原理
/* 你写的 */
p { color: red; }

/* 编译产物 */
p[data-v-7ba5bd90] { color: red; }
/* 模板同时被插桩： _createVNode("p", { "data-v-7ba5bd90": "" }, ...) */
🧠 为什么 scoped 隔离靠属性选择器而不是 Shadow DOM？
Shadow DOM 隔离太彻底（全局样式、字体、弹窗挂载都会被切断），生态工具链难适配； 属性选择器是「够用的隔离」—— 同一文档内，cost 为零。框架选型里的反复权衡， 比技术本身更值得学。

自测一下：编译优化

1. 为什么 v-if 会导致「开新 Block」，而 v-show 不会？
2. {{ Date.now() }} 每次渲染值都不同，但编译器认为它是静态文本（无依赖）——这有坑吗？

答案：
1. v-if 改变结构（节点存在与否），dynamicChildren 的扁平数组无法表达「这块结构可能整个消失」，必须在分支处切块、走传统递归 patch；v-show 只改 style.display，结构恒定，仍可走 Block 快路径。

AST 与 tokenizer：模板变成树

第 30 章讲了编译器的三段流水线，从本章开始逐段下钻。parse 是起点： 把一串字符变成一棵抽象语法树（AST）。官方实现是一台 500+ 行的 tokenizer 状态机（compiler-core/src/parser.ts）—— 本章解释它为什么值这个价钱。

31.1 AST 长什么样

先看产物。左边是模板，右边是 parse 出的 AST（去掉 loc 位置信息的精简版）：

<div id="app"> ┃ RootNode
<span>hello {{ name }}</span> ┃ └ ElementNode(div, props: [id])
<p v-if="ok">hi</p> ┃    ├ ElementNode(span)
</div> ┃    │  └ TextNode("hello ") + InterpolationNode(name)
┃    └ ElementNode(p, directives: [vIf(ok)])
每个节点都带 type + children + loc（源码位置）—— loc 是开发时「模板第几列报错」的底气
节点类型来自将来变成
ElementNode真实标签h() 调用（createElementVNode）
TextNode纯文本字符串参数或 createTextVNode
InterpolationNode{{ name }}toDisplayString(name)
CompoundExpressionNode文本 + 插值混排"hello " + toDisplayString(name)（拼接表达式）
DirectiveNodev-if / v-on 等指令transform 阶段消化掉（第 32 章）
状态机流水线：逐字符吞模板，边解析边纠错边埋线

31.2 为什么是状态机，而不是正则一把梭

官方 parser 的核心是一张 25 个状态的状态机（DATA、TagOpen、TagName、BeforeAttrName……）。 每读一个字符，按当前状态决定转移：

DATA 遇到 < TagOpen 遇到字母 TagName 遇空格 / > AttrName / Value 遇到 > 回到 DATA（递归读 children）
文本、插值 {{ }}、标签、属性……每种语法都是一次状态转移
🧠 状态机的两个「不可替代」
① 性能：一遍扫描 O(n)，每个字符只处理一次；正则回溯在超大模板上是灾难。 ② 错误恢复：状态机在任意位置都知道「合法的下一个符号是什么」—— 所以能报出「v-else/v-else-if has no adjacent v-if」 这类精确错误，甚至容错修复继续解析。Vue 3.4 重写 parser 后， 性能提升约一倍、体积减半，就是靠把正则组合换成了纯状态机。

31.5 报错之后继续编译：parser 的错误恢复

解析到一半发现语法错误，直接 throw 是最容易的实现，但体验最差 —— 用户每次只能看到一个错。 官方 parser 的选择是收集着继续跑：

// ① 错误不抛出，统一上报
function onError(code, loc, msg) {
  options.onError(createCompilerError(code, loc, messages, msg));
}
// 每个 ErrorCodes 都带精确的 loc：{ start: { line, column, offset } }

// ② 分支跳过：闭合标签对不上时，跳到下一个合法边界继续扫
function parseChildren(...) {
  while (!isEnd(context)) { ... }        // isEnd 检查：父级闭合标签？EOF？
  // 遇到无法识别的标签 → 当作纯文本降级处理，解析不中断
}

// ③ 最后统一报告：所有错误一起呈现
// <div><span></div></span>
//        ↑ 1 个错误：<span> 闭合缺失，且指出它"期望"在哪里闭合
🧠 容错的价值链
状态机（31.2 节）+ 错误码 + loc 三件套是配套的：状态机知道「此刻合法的符号集」， 所以能给出「期望是什么」级别的提示；loc 让编辑器能画波浪线； 容错继续跑让 IDE 能一次给出全部诊断 —— Volar 插件的模板红色波浪线，源头就是这套编译器错误恢复。 这也解释了为什么选状态机而不选正则：正则整体失败，拿不到「继续扫」的断点。

模板里的 count、user.name， 最终要变成「运行时能找到的变量」。它们从哪来？前缀化（prefixIdentifiers）负责定位：

{{ items.filter(f) }}_ctx.items...，方法走 _ctx.f闭包直取，方法调用零查找
// createExp 处理插值/指令值时，同时分析其中的标识符：
//   count     → { content: 'count', isStatic: false, identifiers: ['count'] }
// 前缀化遍历 identifiers，按来源打前缀：
//   在 setup 绑定表里 → $setup.count  （script setup 进一步：直接闭包引用）

🧠 这就是 <script setup> 更快的根源

1. {{ name }} 在 AST 里是什么节点？它和纯文本混排后呢？
2. 为什么说状态机的错误报告能力是正则比不了的？

答案：

第 32 章 · 编译器篇

transform 流水线：指令的变身术

parse 出的 AST 还「太老实」—— v-if 就是挂在元素上的指令记录，codegen 没法直接打印。 transform 负责把「指令描述」改写成「可执行的结构」，顺带完成静态提升、patchFlag 打标。 官方源码：compiler-core/src/transform.ts + transforms/ 目录。

32.1 洋葱模型：enter 与 exit

transform 对 AST 做一次深度优先遍历，每个节点依次穿过一组 nodeTransforms。 关键在双阶段设计： 

function traverseNode(node, context) {
  context.currentNode = node;
  const { nodeTransforms } = context;
  const exitFns = [];
  for (let i = 0; i < nodeTransforms.length; i++) {
    const onExit = nodeTransforms[i](node, context);   // ⭐ enter 阶段
    if (onExit) exitFns.push(onExit);                  // 收集 exit 回调
  }
  switch (node.type) {
    case NodeTypes.COMMENT: ... break;
    case NodeTypes.INTERPOLATION: break;               // 插值无子节点
    case NodeTypes.IF:
    case NodeTypes.FOR:
    case NodeTypes.ELEMENT:
    case NodeTypes.ROOT:
      traverseChildren(node, context);                 // 先递归子节点
      break;
  }
  // ⭐ 子节点全部处理完才执行 exit —— 后进先出 = 洋葱模型
  context.currentNode = node;
  let i = exitFns.length;
  while (i--) exitFns[i]();
}
🧠 为什么必须有 exit 阶段？
v-if 的 transform（enter）先于子节点的 transform 跑，但它的「变身」必须等 子树处理完（children 的 patchFlag、静态提升都定了）才能包装 —— exit 就是干这个的。 同时 transform 顺序有讲究：vFor 必须在 vIf 之前（同一元素上 v-for 先于 v-if 语义）， 编译器靠数组顺序硬约束这一点。
洋葱模型：enter 进去、exit 出来 —— v-if 在出口完成变身

32.2 一场 v-if 的完整变身

// enter（transformIf.ts）：只是登记结构指令，先不动手
function createStructuralDirectiveTransform(name, fn) {
  return (node, context) => {
    if (node.type !== NodeTypes.ELEMENT) return;
    const { directives } = node;              // DirectiveNode 数组
    for (const dir of directives) {
      if (dir.name === 'if' || dir.name === 'else-if' ...) {
        fn(node, dir, context);               // ⭐ 记录到 node 的 vIf 属性
      }
    }
    return () => { /* exit 时才真正处理 */ };
  };
}

// <p v-if="ok">hi</p>  →  codegenNode = { type: IF, branches: [...], consistent: true }
// codegen 时打印成：ok ? (createVNode("p", null, "hi")) : createCommentVNode("v-if", true)
// ⭐ 没有 else 分支时补一个注释 vnode 占位 —— 这就是为什么 v-if=false 会留下 <!---->

32.5 亲手写一个 transform：编译期给静态 class 加前缀

transform 不是黑盒 —— compiler 的选项直接暴露 nodeTransforms 数组， 你的函数可以和官方 transform 并排坐：

import { baseParse } from '@vue/compiler-core';

// 需求：所有静态 class 值加命名空间前缀（微前端样式隔离的编译期方案）
const nsTransform = (node, context) => {
  if (node.type !== 1 /* NODE_TYPES.ELEMENT */) return;   // enter：只关心元素

  return () => {                                            // exit：等子树处理完
    const prop = node.props.find(
      (p) => p.type === 6 /* ATTRIBUTE */ && p.name === 'class'
    );
    if (prop?.value) {
      prop.value.content = 'myapp-' + prop.value.content;   // 直接改 AST！
    }
  };
};

const { code } = baseCompile('<button class="btn">OK</button>', {
  nodeTransforms: [nsTransform],   // ⭐ 和官方 transform 并排执行
});
// 产物：_createVNode("button", { class: "myapp-btn" }, "OK")
🧠 这扇门后面是什么
官方全家桶（transformIf / hoistStatic / transformElement…）和你的自定义 transform 走同一个入口、同一套洋葱模型（32.1 节）—— 没有「内部特权」。 这扇门是整个 Vue 生态魔改力的来源：uni-app 把节点编译成小程序标签、 Vue Macros 把宏编译成普通代码、低代码平台把设计稿编译成组件， 全都是往这个数组里塞自己的 transform。记住 enter 改结构、exit 改产物的分寸， 你就有了「改写 Vue 语言本身」的能力。

32.4 动手写一个编译期 transform：构建时替你写代码

nodeTransforms / directiveTransforms 不只是官方内部清单 —— 它们是通过 compilerOptions 公开的插件 API（vite 的 vue() 插件可透传）。 来写一个把 v-theme="'dark'" 在编译期转成 style 的 transform： 

const themeThemes = { dark: 'color:#eee;background:#222', light: 'color:#222;background:#fff' };

const themeTransform = (node, context) => {
  if (node.type !== NodeTypes.ELEMENT) return;
  return () => {                                   // ⭐ exit 阶段（32.1 洋葱模型）
    const dir = node.props.find(p => p.name === 'theme');   // DirectiveNode
    if (!dir) return;
    const themeName = dir.exp?.content;            // 'dark'
    // 编译期查表 → 直接改 AST：合并进 staticProps
    context.helper(MERGE_PROPS);                   // 需要的 helper 自己登记（32.3）
    node.props = node.props.filter(p => p !== dir);
    node.props.push({
      type: NodeTypes.ATTRIBUTE,
      name: 'style', value: { content: themeThemes[themeName] },
    });
  };
};

// vite.config.ts 里接入：
// vue({ template: { compilerOptions: { nodeTransforms: [themeTransform] } } })
🧠 编译期 transform vs 运行时指令：一倍差距
同样一个「主题」需求：运行时指令每个实例挂钩子、每次更新跑判断； 编译期 transform 在构建时就把代码写死 —— 运行时零成本。 unplugin-vue-macros、官方 v-model 的修饰符展开，全是这条路线。 「能用编译期解决的不留给运行时」—— Vue3 的 compiler-centric 哲学。

32.5 v-for 的 transform 走查（和 v-if 的相遇规则）

// exit 阶段把 DirectiveNode 消化成 FOR 结构：
codegenNode = {
  type: NodeTypes.FOR,
  source: "list",             // v-for="item in list" 的源
  valueAlias: "item",         // 别名
  keyAlias: undefined,        // v-for="(v, k) in obj" 时的 key 别名
  children: [ ...循环体... ],
}
// codegen 打印成：
_createBlock(_Fragment, { key: item.id },
  (_openBlock(true), _createBlock(_Fragment, { key: 0 },
    _renderList(list, (item) => [...循环体...]), 128 /* KEYED_FRAGMENT */)))
// ⭐ v-for 天然是 Block 边界：循环体每次渲染开新 Block（30 章 dynamicChildren 以它为界）
规则说明
v-for 比 v-if 先变身transformFor 排在 transformIf 之前（数组顺序硬编码）—— 同元素时 v-if 作用在「每轮循环体」上
同元素 v-if 拿不到 itemv-if 条件在「外层作用域」求值，访问不到 v-for 变量 —— 官方明令禁止；正确姿势是包一层 <template v-for>
key 写在真实元素上写在 template v-for 标签上会被警告 —— key 属于循环体的 vnode（25.5）
解构语法直接支持v-for="{ id, name } in list" —— parse 阶段把解构模式当普通表达式收集（31.5）
🧠 为什么 v-for 一定开新 Block
列表长度可变 → 子树结构不稳定 → 静态收集（30 章 Block Tree）必须在这里「重新开始」。 这也是「大列表天然比静态页面慢」的算法根源：v-for 区域永远享受不到 Block 级跳过， 优化只剩三件武器：正确的 key（18 章）、就地复用（diff）、以及工程手段虚拟滚动。
自测一下：transform

1. v-if 的 transform 为什么必须在 exit 阶段做「真正变身」？
2. 一个组件模板里一个 helper 都没用（纯静态），import 会是什么样？

答案：
1. 因为分支的判定代码要引用子树的处理结果（分支内容的 codegenNode、是否含组件、 patchFlag 等）。enter 时子树还没处理完，只有 exit（子树齐备后）才能安全地包装成 ConditionalExpression。
2. import 列表为空（或只剩最小集）—— helpers 按需登记的机制保证零冗余； 这类纯静态组件的 render 几乎是空函数 + 一堆提升常量。

第 33 章 · 编译器篇

codegen：render 函数的印刷厂

走完 parse 和 transform，AST 已经是「打印就绪」的状态。codegen 做的事朴素到让人意外： 深度优先遍历 AST，按节点类型拼字符串。它就是一台函数式印刷厂 —— 官方源码 compiler-core/src/codegen.ts。

33.1 CodegenContext：一个小字符串拼接器

function createCodegenContext(ast, options) {
  const context = {
    code: '',                    // 最终产物（或 push 进数组最后 join）
    level: 0,                    // 缩进层级
    helper(key) {
      context.helpers.add(key);  // 与 transform 阶段登记对齐（第 32 章）
      return `_${helperNameMap[key]}`;
    },
    push(code, node) { context.code += code; },
    indent() { context.level++; newline(); },   // 新 level：缩进 +1 并换行
    deindent() { context.level--; newline(); },
    newline() { push('\\n' + '  '.repeat(level)); },
  };
  return context;
}

33.2 genNode：一张分发表

打印的核心是一个 switch 分发表 —— 每种 AST 节点对应一个 gen 函数：

33.3 同一棵 AST 的两种产物

同一个模板，编译目标不同，产物不同 —— 差异全在「变量从哪来」： 

// ① 运行时编译（vue.global.js 的 compiler 在浏览器里跑，包大但即开即用）
const render = new Function('with (this) { return _createVNode("div", null, name) }');
//                       ⭐ with 前缀：name 直接走作用域链找到实例数据（非严格模式）

// ② 预编译（SFC 构建时产出，prefixIdentifiers 已把变量前缀化）
import { createVNode as _createVNode } from "vue";
function render(_ctx, _cache) {
  return _createVNode("div", null, _ctx.name);   // ⭐ 显式 _ctx 前缀
}
// 预编译产物可以走严格模式 + 完整 tree-shaking + 更小的运行时（不需要 compiler）
// 这就是「runtime-only 构建」比「完整版」小 40% 的原因

33.4 SSR 通道：同一棵树的另一台打印机

codegen 还有个平行产物：ssrRender 函数 —— 不生成 vnode 调用， 而是生成 字符串拼接代码（_push('<div>') ...）， 供服务端直出 HTML。同一个 AST、两台打印机、两个产物 —— 第 36 章讲消费端。

🧠 为什么 codegen 值得一读
它是「理解编译产物」的最短路径：面试官让你手写「模板编译成 render 函数」， 本质就是 parse + 一把 switch 的 codegen（第 51 章的作业③）。 读完这章你会发现 Vue 编译器没有一处神秘 —— 全是字符串工艺。

33.5 同一棵树的第二台打印机：ssrRender 产物对照

33.4 说 SSR 有平行产物，展开看具体形态 —— 同一个模板 <p>{{ n }}</p>：

// ① 客户端 render（你熟悉的）：
function render(_ctx) {
  return _createVNode("p", null, _toDisplayString(_ctx.n));
}

// ② 服务端 ssrRender（ssr: true 的编译目标）：
function ssrRender(_ctx, _push, _parent, _attrs) {
  _push(`<p${_ssrRenderAttrs(_attrs)}>${_ssrInterpolate(_ctx.n)}</p>`);
}
// ⭐ 没有 vnode、没有 patchFlag、没有 children 数组 —— 纯字符串拼接
差异点clientssr
事件（onClick）生成 onXxx prop整体跳过 —— 服务端没有交互，压根不生成
动态更新（patchFlag）精确标记供 patch 用无意义，全部省略
ref / 指令 mounted运行时执行跳过，只在 hydration 补挂（36 章）
产物体积大小且执行快（无对象分配）
💡 「一台 AST 两台打印机」的架构意义
transform 产出的 codegenNode 是「中立的中间表示」—— 打印成 vnode 调用还是字符串拼接， 只是两个不同的 genNode 分发表。这和现代编译器的多后端设计（一份 IR，多个目标平台）完全同构。
自测一下：codegen

1. with(this) 版和 _ctx 前缀版最大的工程差异是什么？
2. patchFlag 这个数字是在哪一步被打印进参数的？

答案：
1. with 版依赖非严格模式的作用域链查找，无法 tree-shaking、无法静态分析； _ctx 版显式声明依赖来源，可做 tree-shaking、TS 类型推导和更小的运行时。
2. transform 阶段（transformElement）就已经把 patchFlag 计算好存进 codegenNode， codegen 的 genElement 只是原样打印 —— 「计算」与「打印」分离，是三段流水线的分工原则。

v-model 与事件修饰符：语法糖的编译真相

你写得最顺手的几个语法 —— @click.stop、v-model、 @keyup.enter —— 全是编译期展开的语法糖。 本章对照产物逐个拆解，看完你会获得「模板里没有魔法」的终极平静。

34.1 事件修饰符：每个都是一小段内联代码

// 你写的：
<button @click.stop.prevent="onClick" @keyup.enter="onEnter"></button>

// 编译产物（transformOn + 修饰符处理，简化）：
_createVNode("button", {
  onClick: _withModifiers(_onClick, ["stop", "prevent"]),
  onKeyup: _withKeys(_onEnter, ["enter"])
})

// ⭐ 注意两层设计：
// - .stop/.prevent/.self/.capture 等是「通用」修饰符 → 一个通用 helper _withModifiers
//   （运行时按 flags 位运算判断，因为组合太多，内联太长）
// - .enter/.tab/.delete 等按键修饰符 → _withKeys（读 e.key 判断）
🧠 为什么不全内联？
Vue2 时代确实是纯内联（$event.stopPropagation() 直接写进产物）； Vue3 发现修饰符组合爆炸（2ⁿ 种），改用 运行时 helper + 位运算 flags： 编译期把修饰符压成数字，运行时一次判断。这是「内联 vs helper」的经典权衡 —— 简单修饰符（.once）内联，组合型修饰符走 helper。

34.2 v-model：三种目标，一种思想

用在编译产物同步事件
<input type="text">modelValue prop + onUpdate:modelValue + vModelText 指令input（.lazy 则 change）
<input type="checkbox">同上，但走 vModelCheckboxchange
<select> / <textarea>vModelSelect / vModelTextchange / input
组件上modelValue: x, 'onUpdate:modelValue': $event => x = $event子组件 emit('update:modelValue')
_createVNode(MyInput, {
  modelValue: text,
  "onUpdate:modelValue": $event => ((text) = $event)
})
// ⭐ 所谓「双向绑定」= 传一个 prop + 传一个改自己的回调。
// 和第 22 章 emit 的结论接上了：事件就是调 props 里的函数。
// v-model:foo 是同一个糖的带参数版本（prop: foo + onUpdate:foo）

34.3 .lazy / .trim / .number 落在哪里？

这三个不是编译期展开的 —— 它们作为 modifiers 对象传给第 26 章讲过的 vModelText 运行时指令，由它决定监听 input 还是 change、 回写前要不要 trim / 转数字。回忆一下那条 beforeUpdate 里 activeElement 检查 —— 「正在输入时不覆盖」就是 .trim/.number 不打断你打字的关键。

💡 模板里没有魔法，只有分工
编译期能确定的（事件名、prop 名、修饰符 flags）→ 编译期展开； 依赖运行时状态的（输入焦点、组合键）→ 运行时指令/helper。 Vue 团队对每个语法糖都做过这道选择题 —— 你现在有能力看懂他们的答案了。

34.5 语法糖速查总表：一张表查完所有糖

💡 用法
面试遇到「谈谈 XX 的实现」：先定位它在表里的行，再顺着「编译产物 → 运行时 helper/指令 → 对应章节」三步走。全部语法糖的归宿只有两种：编译期展开成确定性代码，或 携带 flags 交给运行时 helper —— 没有第三种（34.4 节的选择题）。

34.4 编译宏：不是函数的「函数」

<script setup> 里那些不需要 import 的 defineProps / defineEmits / defineExpose / defineOptions / defineModel， 叫编译宏（compiler macros） —— 它们长得像函数调用，但运行时不存在： 

// 你写的：
const props = defineProps({ msg: String });
const emit = defineEmits(['change']);
defineExpose({ reset });

// 编译产物（script setup → setup()）：
props: { msg: { type: String } },           // ⭐ defineProps 被「原地拆开」挂到组件选项
emits: ['change'],                          // defineEmits 同理
setup(__props, { expose }) {
  expose({ reset });                        // defineExpose 变成一次普通调用
  ...
}
// defineModel（3.4+）展开成：prop + emit('update:xxx') + 内部 ref 的三件套（34.2 的糖）
因此带来的约束原因
不用 import（import 了反而报错）它们是编译器关键字，运行时根本没有这个函数
参数不能写运行时逻辑（如三元、变量）宏在编译期求值，执行代码时它已经消失了
只能在 <script setup> 顶层调用编译器只在顶层扫描宏
🧠 宏与 31.5 的合谋
defineProps 把 props 声明编译期静态化，编译器由此拿到完整的绑定信息 （哪些来自 props、哪些来自 setup），31.5 的前缀化才能生成「闭包直取」代码。 宏不是语法糖，是编译器打开 <script setup> 优化的钥匙孔 —— 面试聊到「script setup 为什么快」，宏 + 前缀化两点缺一不可。
自测一下：语法糖

1. 组件上的 v-model 和 v-model:title 分别编译成什么？
2. @click.stop 为什么用 helper 而不是直接内联 $event.stopPropagation()？

答案：
1. 前者 = modelValue prop + onUpdate:modelValue 回调；后者 = title prop + onUpdate:title 回调 —— 同一套糖，只是参数化了名字。组件内部 defineEmits(['update:modelValue']) 配合使用。
2. 修饰符可组合（.stop.prevent.self.capture... 共 2ⁿ 组合），内联代码会爆炸； 编译期把组合压成位 flags + 一个 _withModifiers helper，运行时一次位运算判断 —— 产物体积和判断成本都恒定。
