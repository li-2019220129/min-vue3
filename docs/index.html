全景：先看懂整个项目

读源码最大的敌人不是代码难，而是「迷路」。所以在深入任何一行代码之前， 我们先站在山顶俯瞰一次：这个项目长什么样？每个目录是干嘛的？谁依赖谁？ 搞清楚地图，后面每一章你都知道自己走到了哪。

📌 版本基准
本站以官方最新稳定版源码为主线：响应式各章直接精读 vuejs/core v3.5.43（写作时最新，2026-09 发布）的 effect / dep / reactive / ref / computed / watch 真实实现。 仓库里的 mini-vue3 是配套的动手施工材料（教学简化版）， 用于实验室演示与「把 mini-vue3 写完」系列（第 44~48 章）；它与官方的差异，各章会明确标注。 下一代的 3.6（Vapor 模式 + alien-signals 重写）见第 51 章结业展望。

1.1 一个 monorepo 的自我修养

项目根目录下有一个 pnpm-workspace.yaml， 它宣告了这是一个 pnpm monorepo（单仓库多包）。 一个文件夹里塞着四个「小 npm 包」，各管一摊：

目录职责现状（学习进度）
packages/shared 最基础的工具函数：isObject、isFunction ✅ 完成（就这么俩函数，1 分钟学完）
packages/reactivity 整个响应式系统：effect / reactive / ref / computed / watch ✅ 完成 —— 本站 90% 的主角
packages/runtime-core 跨平台渲染器核心（不认识 DOM，只认识「节点操作接口」） 🚧 骨架（createRenderer 已就位，render 待实现）
packages/runtime-dom 浏览器专属：真正操作 DOM 的那层 🚧 nodeOps + patchProp 已完成
🧠 为什么要拆成四个包？
拆分不是为了炫技，是为了跨平台：runtime-core 只定义「渲染需要哪些操作」（插入节点、删节点、改属性……）， 具体怎么干交给下层。给浏览器就配 runtime-dom（真 DOM），给 canvas 可以配一个「画图版 runtime」， core 一行代码都不用改。这套「依赖倒置」的思想值得偷走。

1.2 shared：小而美的起点

整个 shared 包的源码，全部加起来只有这几行：

export function isObject(value) {
  return typeof value === "object" && value !== null;
}
export function isFunction(value) {
  return typeof value === "function";
}

注意 value !== null 这个细节：JavaScript 里 typeof null === "object" 是语言级的历史 bug， 所以判断对象必须把 null 单独踢出去。再大的框架，也是从一个严谨的 isObject 开始的。

1.4 怎么跑起来 & 怎么调试

1.6 读源码的三把钥匙

  1. 从测试用例读：每个包的 __tests__ 目录是「行为说明书」—— 先看测试断言什么，再回源码找实现，永远比硬啃实现快。
  2. 从类型定义读：官方源码 TS 密度很高，interface 先行。 读懂 ReactiveEffectRunner、RendererNode 这些类型， 实现只是「把类型跑起来」。
  3. 打断点跟一帧：用 vite 起一个最小 demo，在 track 里下断点， 看一次点击从事件回调一路走到 patch 的完整调用栈 —— 一帧胜读百行。
💡 阅读心法：主流程优先，细节殿后
第一遍只追「一次赋值怎么让页面更新」的主干（本书 2~6 章）， 错误处理、边界警告、兼容逻辑全部跳过 —— 它们不影响理解，只会拖慢你。 第二遍带着「哪里可能出错」的问题再读，那些被跳过的代码才显出意义。
自测一下：架构理解

1. 为什么 runtime-core 里找不到一行 document.xxx 的代码？
2. 我要给一个小游戏做 canvas 渲染，需要重写哪一层？

答案：
1. 因为 core 只定义接口（插入、删除、打补丁），具体操作由外部「注入」进来 —— 它根本不知道自己会被用在浏览器还是别的地方，这正是它能跨平台的原因。
2. 只需要写一个新的「runtime-canvas」，提供一套操作 canvas 节点的 nodeOps 和 patchProp，core 和 reactivity 原封不动照用。
