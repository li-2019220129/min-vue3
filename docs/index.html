全景：先看懂整个项目

读源码最大的敌人不是代码难，而是「迷路」。所以在深入任何一行代码之前， 我们先站在山顶俯瞰一次：这个项目长什么样？每个目录是干嘛的？谁依赖谁？ 搞清楚地图，后面每一章你都知道自己走到了哪。

1.1 一个 monorepo 的自我修养

项目根目录下有一个 pnpm-workspace.yaml， 它宣告了这是一个 pnpm monorepo（单仓库多包）。 一个文件夹里塞着四个「小 npm 包」，各管一摊：

目录职责现状（学习进度）
packages/shared 最基础的工具函数：isObject、isFunction ✅ 完成（就这么俩函数，1 分钟学完）
packages/reactivity 整个响应式系统：effect / reactive / ref / computed / watch ✅ 完成 —— 本站 90% 的主角
packages/runtime-core 跨平台渲染器核心（不认识 DOM，只认识「节点操作接口」） 🚧 骨架（createRenderer 已就位，render 待实现）
packages/runtime-dom 浏览器专属：真正操作 DOM 的那层 🚧 nodeOps + patchProp 已完成
🧠 为什么要拆成四个包？
拆分不是为了炫技，是为了跨平台：runtime-core 只定义「渲染需要哪些操作」（插入节点、删节点、改属性……）， 具体怎么干交给下层。给浏览器就配 runtime-dom（真 DOM），给 canvas 可以配一个「画图版 runtime」， core 一行代码都不用改。这套「依赖倒置」的思想值得偷走。

1.2 shared：小而美的起点

整个 shared 包的源码，全部加起来只有这几行：

export function isObject(value) {
  return typeof value === "object" && value !== null;
}
export function isFunction(value) {
  return typeof value === "function";
}

注意 value !== null 这个细节：JavaScript 里 typeof null === "object" 是语言级的历史 bug， 所以判断对象必须把 null 单独踢出去。再大的框架，也是从一个严谨的 isObject 开始的。

第 2 章 · 响应式篇

effect：万物的起点

在 Vue 里，你写的每一行模板、每一个 computed、每一个 watch，最后都会变成一个 effect（副作用）。它是整个响应式大厦的地基。这一章我们把地基砸开看看。

2.1 什么是「副作用」？

先别管 Vue，看一段最普通的代码：

const state = { name: "张三", age: 18 };

function renderTitle() {
  document.title = state.name;   // 读了 name，还顺手改了页面标题
}

renderTitle 除了返回值，还对外面的世界产生了影响（改了标题）—— 这种「影响」就叫副作用（side effect）。

现在问题来了：

如果有人改了 state.name，renderTitle 怎么才能自动重新执行？

Vue 要做的事情，本质上就一句话：在一个函数「读」数据时记住它，在数据「变」时重新喊它。 围绕这句话，产生了两个核心动作 —— 你将在这本书里反复遇到它们：

读取时登记
track（依赖收集） ＋ 修改时通知
trigger（派发更新） ＝ 响应式 ✨

2.2 ReactiveEffect：给函数发一张「身份证」

要「记住」一个函数，光有函数本身不够 —— 函数是匿名的，没法当 key 存进 Map。 所以源码包了一个类 ReactiveEffect，把函数变成对象， 对象就有身份、能被 Map 存了。来看源码（有删节，保留主干）： 

export let activeEffect;                 // ⭐ 全局指针：当前正在执行哪个 effect

export class ReactiveEffect {
  _trackId = 0;          // 执行了几轮（用来识别「本轮」新收集的依赖，第 6 章主角）
  deps = [];             // 双向记录：我读过哪些 dep（反向指针）
  _depsLength = 0;       // 本轮收集到第几个 dep 了（双指针清理，第 6 章主角）
  _running = 0;          // 防止自己触发自己 → 死循环
  public active = true;  // 停止开关

  constructor(public fn, public scheduler) {}   // fn=函数本体, scheduler=调度器(第5章讲)

  run() {
    if (!this.active) return this.fn();  // 已停止：普通调用，不收集依赖

    let lastEffect = activeEffect;       // ① 暂存上一个 effect（支持嵌套）
    try {
      activeEffect = this;               // ② 把全局指针指向自己 ⭐ 关键一步
      preCleanEffect(this);              // ③ 本轮收集开始：_trackId++, _depsLength=0
      this._running++;                   // ④ 标记「我在运行中」
      return this.fn();                  // ⑤ 真正执行函数 → 里面的读取会触发 track
    } finally {
      this._running--;                   // ⑥ 恢复
      postCleanEffect(this);             // ⑦ 收尾：清掉本轮不再需要的旧依赖
      activeEffect = lastEffect;         // ⑧ 还原全局指针
    }
  }
}

逐行解读最关键的 ②⑤ 两步

  • ② activeEffect = this：在函数执行前，把自己挂到全局变量上。这样函数体里每读一个属性，track 都能通过 activeEffect 知道「现在是谁在读」—— 没有这一步，依赖收集根本无从谈起。
  • ⑤ this.fn()：执行函数本体。函数里所有对响应式数据的读取，都会被 Proxy 拦截（下一章），进而查到 activeEffect，完成登记。这就是 Vue 的「读取即收集」。
💡 比喻时间：追踪器
把 activeEffect 想象成特工电影里的追踪器： 特工（effect）潜入目标家（执行 fn）之前，指挥部先给他别上追踪器（activeEffect = this）。 他在屋里碰过的每一样东西（读过的每个属性）都会被记录（track）。 任务结束后追踪器收回（activeEffect = lastEffect），下一批特工再来。

try/finally 的讲究（⑧ 为什么放 finally）

如果 this.fn() 中途抛异常，没有 finally 的话 activeEffect 会永远停留在「我」身上，后续无关代码的读取会被错误地收集到我名下。 finally 保证指针无论成功还是炸了都会还原 —— 响应式系统的健壮性就藏在这些细节里。

2.3 effect()：对外的大门

export function effect(fn, options?) {
  const _effect = new ReactiveEffect(fn, () => {
    _effect.run();                        // 默认调度器：直接重跑
  });
  _effect.run();                          // ⭐ 立即执行一次（首次收集依赖）

  if (options?.scheduler) {
    Object.assign(_effect, options);      // 允许用户自定义调度器
  }
  const runner = _effect.run.bind(_effect);
  runner.effect = _effect;                // 返回可调用函数，还携带 effect 本体
  return runner;
}

三件事：

  1. 立即执行一次 —— 依赖收集不是凭空来的，必须先跑一遍函数才知道它读了什么；
  2. 可注入 scheduler —— 数据变了不直接重跑，先调用 scheduler。computed 和 watch 全靠这个口子实现各自的脾气（第 8、9 章）；
  3. 返回 runner —— 拿到它就像拿到一个「手动挡」的 effect，可以随时自己再跑。
⚠️ 找个茬：源码里的可爱拼写
本项目源码里有个函数叫 tarckEffect —— 没错，是 track 拼成了 tarck 😄。 不影响运行（拼写一致就行），但你在源码里搜索时别困惑。本站为了阅读体验统一写作 trackEffect。 看源码时保持这种「怀疑精神」是好事：官方源码也是人写的，也有手滑的时候。
自测一下：effect 基础

1. 为什么 effect(fn) 必须立即执行一次 fn？
2. 如果在 effect 里写 state.count = state.count + 1 会发生什么？源码靠什么机制兜底？

答案：
1. 因为依赖收集是「运行时」行为 —— 不跑一遍函数，系统根本不知道它读了哪些属性。首次执行 = 首次登记。
2. 会触发「自己更新自己依赖的数据」：run() 里读取时 _running 已是 1，trigger 时检查 effect._running === 0 才触发 scheduler，运行中则跳过，避免无限递归死循环。

第 3 章 · 响应式篇

reactive：Proxy 的魔法

上一章我们知道了「谁在读」—— activeEffect。但数据是死的， 它怎么知道「自己被读了」？答案是把普通对象换成替身：Proxy 代理。 本章还埋着一个高频面试陷阱题：Reflect 和 receiver。

3.1 一句话理解 Proxy

Proxy 就是你给对象雇的一个万能管家：任何人想读属性、写属性，都必须先过管家这一关：

const raw = { name: "张三" };

const proxy = new Proxy(raw, {
  get(target, key) {
    console.log("有人读了", key);        // 拦截到了！
    return target[key];
  },
  set(target, key, value) {
    console.log("有人把", key, "改成了", value);
    target[key] = value;
    return true;
  },
});

proxy.name;        // 控制台：有人读了 name
proxy.name = "李四"; // 控制台：有人把 name 改成了 李四

「读/写都能被拦截」—— 这正是响应式的命门。 Vue2 用的 Object.defineProperty 只能在初始化时给已知属性装监控， 而 Proxy 是全对象、全时段的管家：

痛点Vue2 definePropertyVue3 Proxy
新增属性 obj.newKey = 1❌ 监控不到（要靠 $set）✅ set 拦截器直接捕获
数组下标 arr[0] = 9❌ 要劫持七个数组方法绕路✅ 一视同仁
删除属性 delete obj.key❌ 监控不到（要靠 $delete）✅ deleteProperty 拦截
惰性深层代理❌ 初始化时递归整个对象✅ 取到时才代理下一层

3.2 源码：createReactiveObject

let targetMap = new WeakMap();          // 原对象 → 它的代理（缓存，防止重复代理）

export function reactive(target) {
  return createReactiveObject(target);
}

function createReactiveObject(target) {
  if (!isObject(target)) {
    return target;                        // 原始值直接返回：数字/字符串没法被 Proxy
  }
  if (target[ReactiveFlags.IS_REACTIVE]) {
    return target;                        // 已经是代理了，别再包一层
  }
  const exitsProxy = targetMap.get(target);
  if (exitsProxy) {
    return exitsProxy;                    // 同一个对象第二次 reactive() → 返回缓存
  }
  let proxy = new Proxy(target, mutableHandlers);
  targetMap.set(target, proxy);           // 登记缓存
  return proxy;
}

三个防御性检查，各有深意

  • 非对象直接返回：reactive(18) 是无效操作（Proxy 只能代理对象）。 这正是 ref 存在的理由 —— 第 7 章。
  • target[IS_REACTIVE]：注意！读这个 key 会触发代理的 get 拦截器， 拦截器里看到这个特殊 key 就直接返回 true（见下节源码第 8 行）。 一个属性同时实现了「识别身份」和「防重复包装」两个功能，很巧。
  • WeakMap 缓存：保证 reactive(obj) === reactive(obj)， 否则两个代理互不相认，数据会「精神分裂」。

3.3 baseHandler：管家的工作手册

export const mutableHandlers: ProxyHandler<any> = {
  get(target, key, receiver) {
    if (key === ReactiveFlags.IS_REACTIVE) {
      return true;                        // 身份暗号：问我这个就说明我是代理
    }
    track(target, key);                   // ⭐ 读取登记（第 4 章）
    let res = Reflect.get(target, key, receiver);
    if (isObject(res)) {
      return reactive(res);               // ⭐ 惰性深层代理：取到对象才继续包
    }
    return res;
  },
  set(target, key, value, receiver) {
    let oldValue = target[key];
    let result = Reflect.set(target, key, value, receiver);
    if (oldValue !== value) {
      trigger(target, key, value, oldValue);  // ⭐ 值变了才通知（第 5 章）
    }
    return result;
  },
};
🧠 惰性代理：性能的小心思
注意 get 里的 return reactive(res)：嵌套对象不是在 reactive(obj) 时一次性递归代理的，而是被访问到的那一刻才转成代理。 一个巨大的对象只用一个字段时，其他 99 层结构根本不会被代理 —— 按需付费。

3.4 ⚠️ 高频陷阱：为什么必须用 Reflect.get + receiver？

这是本章压轴题，也是源码注释里作者特意强调的点。看这个对象：

const obj = {
  name: "张三",
  get aliasName() {          // aliasName 是个 getter
    return this.name + "（别名）";   // ⚠️ 注意 this 指向谁？
  },
};

当我们用代理去读 proxy.aliasName 时：

  1. 代理的 get 拦截器被触发，track(obj, 'aliasName') ✅（aliasName 被登记）
  2. 拦截器内部去执行真正的 getter，getter 里写了 this.name —— this 指向谁，name 就在谁身上被读；
  3. 如果用 target[key] 取值：this = 原始对象 obj → 读 name 不经过代理 → track(obj, 'name') 永远不会发生 ❌
  4. 如果用 Reflect.get(target, key, receiver)：this = 代理 proxy → 读 name 经过代理 → name 正常登记 ✅

一句话总结：

Reflect.get 的第三个参数 receiver，作用是把 getter 里的 this 矫正成代理， 保证 getter 内部的属性读取也能被拦截、被收集。少了它，依赖会静默丢失，页面莫名不更新。
🧪 实验：有 receiver vs 没 receiver亲手制造一次「依赖丢失」

下面运行两套代理（同一份数据）：左边用 Reflect.get(target, key, receiver)， 右边用 target[key]。两个 effect 都只读 aliasName。 然后我们改 name —— 看看谁丢失了更新。

自测一下：reactive 原理

track：画好「关注名单」

前两章集齐了所有演员：activeEffect 知道「谁在读」，Proxy 拦截器知道「读了谁」。 这一章把两者登记到一本花名册上 —— 著名的 WeakMap 套 Map 套 Map。 登记完，我们去实验室现场看这本名册怎么长出来的。

4.1 需要一本什么样的名册？

先自己推演一下需求。要支持「改 name 时只通知关注 name 的 effect」，名册必须能回答：

哪个对象？ → 哪个属性？ → 哪些 effect 在等它？
三层问题，三层 Map。答案就是著名的三层嵌套结构

4.2 源码：三层结构的诞生地

let targetMap = new WeakMap();          // 第①层：target(原对象) → depsMap

export const createDep = (cleanup, key) => {
  const dep = new Map() as any;          // 第③层：effect → trackId
  dep.cleanup = cleanup;                 // dep 清空时，顺手把自己从 Map 里删掉
  dep.name = key;
  return dep;
};

export function track(target, key) {
  if (!activeEffect) return;             // 没人在读（不在 effect 里）→ 不登记

  let depsMap = targetMap.get(target);   // 第①层：找对象的登记表
  if (!depsMap) {
    depsMap = new Map();                 // 第②层：key → dep
    targetMap.set(target, depsMap);
  }
  let dep = depsMap.get(key);
  if (!dep) {
    dep = createDep(() => depsMap.delete(key), key);
    depsMap.set(key, dep);
  }
  trackEffect(activeEffect, dep);        // 登记 effect（见下）
}

给每个 dep 起个户号 —— createDep 的巧思

dep 本体就是个普通 Map（key 是 effect 对象，value 是 trackId）， 但源码往上面挂了两个属性：cleanup 和 name。 cleanup 的作用：当 dep 里最后一个 effect 也被清掉时，dep 自动把自己从第②层 Map 里删掉， 名册保持干净、不积垃圾。JS 里 Map 也是对象，可以挂自定义属性 —— 一个不太优雅但非常好用的黑科技。

4.3 trackEffect：双向奔赴的登记

export function trackEffect(effect, dep) {
  // 同一个 effect 读同一属性多次 → 只登记一次
  if (dep.get(effect) !== effect._trackId) {
    dep.set(effect, effect._trackId);        // dep 记住 effect（正向）

    const oldDep = effect.deps[effect._depsLength];
    if (oldDep && oldDep !== dep) {
      cleanDepEffect(oldDep, effect);        // 这个位置上坐着别的 dep → 它过期了
    }
    effect.deps[effect._depsLength++] = dep; // effect 记住 dep（反向）
  }
}

注意「双向记录」：dep 收录 effect 的同时，effect 的 deps 数组也收录 dep。 为什么要反向记？—— 为了第 6 章的依赖清理：effect 要能找到「我名下登记过哪些 dep」才能逐一注销。 这对正反指针就是 Vue 3.4 高性能清理的地基。

💡 比喻时间：小区门禁
targetMap = 整个小区的花名册；depsMap = 某栋楼的住户表； dep = 某个门牌号里的「关注这个门的人」名单（住户 + 进门编号 trackId）。 track 就是门卫登记：「effect-1（本轮编号 1）关注了 3 号门的 name」。
🧠 为什么最外层是 WeakMap？
WeakMap 的 key 是弱引用：当原对象在别处被销毁（比如组件卸载），它和整个名册的登记会被垃圾回收器自动带走， 不需要手动清理、也不会内存泄漏。如果换成 Map，key 永远被强引用着，对象就永远「阴魂不散」。

trigger：一呼百应

登记完成，就等数据变化的那一刻。set 拦截器发现值变了，trigger 就拿着名册挨家挨户敲门。 这一章很短，但有两个值钱的细节：值的比较，和「调度」的萌芽。

5.1 源码：从 set 到 effect 重跑的完整链路

// baseHandler.ts 的 set 拦截器里：
set(target, key, value, receiver) {
  let oldValue = target[key];
  let result = Reflect.set(target, key, value, receiver);
  if (oldValue !== value) {                 // ⭐ 值没变就不折腾
    trigger(target, key, value, oldValue);
  }
  return result;
}

// reactiveEffect.ts：
export function trigger(target, key, newValue, oldValue) {
  const depsMap = targetMap.get(target);    // 顺着名册找：对象 →
  if (!depsMap) return;                     //   （没人登记过，直接回家）
  const dep = depsMap.get(key);             //   → 属性 →
  if (!dep) return;
  triggerEffects(dep);                      //   → effect 们
}

// effect.ts：
export function triggerEffects(dep) {
  for (const effect of dep.keys()) {
    if (effect._dirtyLevel < DirtyLevels.Dirty) {
      effect._dirtyLevel = DirtyLevels.Dirty;   // 给 computed 用的脏标记（第 8 章）
    }
    if (effect._running === 0) {                // ⭐ 正在运行的自己不触发（防死循环）
      if (effect.scheduler) {
        effect.scheduler();                     // 有调度器走调度器
      }
    }
  }
}

5.2 细节一：oldValue !== value 的坑

项目源码用的是 !==。思考题：给 name 赋值 NaN 两次会怎样？ 

NaN === NaN      // false ！（NaN 不等于任何值，包括自己）
NaN !== NaN      // true

state.name = NaN;   // oldValue="张三" !== NaN → 触发 ✓
state.name = NaN;   // NaN !== NaN 恒为 true → 又触发了！✗（其实值没变）

官方 Vue 源码用的是 !Object.is(oldValue, newValue)， 因为 Object.is(NaN, NaN) === true，能正确识别「NaN 没变化」。 差一个字符的严谨性，就是「能跑」和「正确」的距离。

5.3 细节二：_running 防自杀循环

effect(() => {
  state.count = state.count + 1;   // 读了 count，又写了 count
});
// 若无保护：跑 effect → 读 count（登记）→ 写 count（trigger 自己）→
//          重跑 effect → 写 count → 重跑 effect → …… 栈溢出 💥

run() 执行 fn 前会 _running++，triggerEffects 里检查 effect._running === 0 才允许触发 —— 自己触发自己的那一下会被吞掉，死循环斩断。

5.4 细节三：scheduler —— 一颗埋好的种子

注意 triggerEffects 并不直接 effect.run()，而是调 effect.scheduler()。默认 scheduler 等价于直接重跑（见第 2 章 effect 函数）， 但 computed 和 watch 会传入自己的版本：

API自己的 scheduler效果
effect（默认）_effect.run()数据一变立刻重跑
computed只把自己标脏 + 通知下游不着急算，等下次有人读
watch调用用户的回调 cb执行的是「你的代码」而不是 getter

同一个引擎，靠注入不同的 scheduler 长出三种性格 —— 这就是第 2 章说的「可注入调度器」的价值。

state.name = "李四" → set 拦截 → 值变了吗？ → trigger → 查名册 → scheduler() → 重跑 / 标脏 / 回调
一次赋值背后的九连环。实验室里每点一次按钮，走的就是这条链

2. 为什么 triggerEffects 先标 dirtyLevel 再判断 _running？

答案：
1. trigger 里 depsMap.get(key) 找不到 dep（或 dep 空）直接 return —— 开销止于两次 Map 查找，非常便宜。这也是响应式「按需通知」的效率来源。
2. 两个动作服务两类需求：标脏是给 computed 的「记账」（哪怕这次不执行，账也要记下）；_running 拦的是「执行」这个动作。记账不花钱，执行才花钱。

依赖清理：分支切换之谜

这是整个 reactivity 里最烧脑、也最有含金量的一章 —— Vue 3.4 用「版本号 + 双指针」 替换了沿用多年的「全删重建」方案。看懂它，你就超过了 90% 的「Vue 使用者」。 别怕，我们有一整个动画实验室帮你。

6.1 问题：分支切换会让依赖「过期」

effect(() => {
  app.textContent = state.flag
    ? state.name      // flag=true：本轮只登记 flag、name
    : state.age;      // flag=false：本轮只登记 flag、age
});

推演一遍：

  1. flag 为 true，effect 跑完，名册里：flag → [effect]、name → [effect]
  2. 有人把 flag 改成 false → effect 重跑 → 这次只读 flag 和 age
  3. 问题来了：名册里 name → [effect] 这条记录过期了！ 现在页面显示的是 age，name 已经和我无关
  4. 如果不清理：以后每次改 name（哪怕一万次），effect 都会白白重跑 → 性能浪费 + 逻辑错误

6.2 老方案（Vue 3.0~3.3）：全删重建

老版本的思路很朴素：每次 effect 重跑之前，把它 deps 里登记的所有 dep 全部清空，跑完重新收集。 正确性没问题，但代价是：哪怕依赖一点没变（绝大多数情况），也要做一轮「全部删除 + 全部登记」的无用功。

6.3 新方案（Vue 3.4 / 本项目）：版本号 + 双指针 diff

核心思想一句话：「本轮收集完，和上一轮比一比，只删多出来的」 —— 像极了虚拟 DOM 的 diff。三个角色：

角色作用
_trackId（版本号）每 run 一次就 +1。dep 里记录的「上次登记时的版本号」不等于当前版本 → 说明这条登记不是本轮写的
_depsLength（写指针）本轮新登记写到了 effect.deps 的第几个位置
effect.deps（登记簿）effect 反向记录自己登记过的所有 dep（第 4 章埋的伏笔）

三步走源码

// ① run() 开头：本轮收集开始
function preCleanEffect(effect) {
  effect._depsLength = 0;   // 写指针归零：本轮从头登记
  effect._trackId++;        // 版本号 +1：旧记录全部「作废」
}

// ② trackEffect 里：登记即 diff
function trackEffect(effect, dep) {
  if (dep.get(effect) !== effect._trackId) {     // 不是本轮登记的？
    dep.set(effect, effect._trackId);            //   → 写入本轮版本号
    const oldDep = effect.deps[effect._depsLength];
    if (oldDep && oldDep !== dep) {
      cleanDepEffect(oldDep, effect);            //   → 写指针位置上还坐着旧 dep？它过期了，删！
    }
    effect.deps[effect._depsLength++] = dep;     // 写入新 dep，指针 +1
  }
}

// ③ run() 结尾：清尾巴
function postCleanEffect(effect) {
  if (effect.deps.length > effect._depsLength) { // 登记簿比本轮写到的位置长？
    for (let i = effect._depsLength; i < effect.deps.length; i++) {
      cleanDepEffect(effect.deps[i], effect);    //   → 多出来的全是过期依赖，逐一注销
    }
    effect.deps.length = effect._depsLength;     //   → 登记簿截断
  }
}

function cleanDepEffect(dep, effect) {
  dep.delete(effect);          // 从 dep 里删除登记
  if (dep.size === 0) {
    dep.cleanup();             // dep 空了 → 把自己从 depsMap 里也删掉（第 4 章的 cleanup 闭包）
  }
}

走一遍完整流程（flag: true → false）

第 1 轮（flag=true）：depsLength=2
deps: [dep·flag, dep·name] ✓ 本轮读了 flag、name
第 2 轮（flag=false）：depsLength=2，但内容变了！
deps: [dep·flag, dep·age] → 本轮只读了 flag、age
写指针走到 index=1 时 发现 oldDep = dep·name ≠ dep·age → 注销 dep·name 💥
登记簿像一个正在原地翻新的书架：新书从左往右放，放的时候发现架上有旧书挡道就扔掉；最后把书架右边多余的旧书全部清空
🧠 为什么说这是「diff」？
源码注释里作者自己写道："这块做个类似 diff 的比较"。 老方案是「销毁重建」，新方案是「原地复用 + 增量更新」—— 和虚拟 DOM diff 的哲学完全一致。 好框架的品味是相通的：能不动的，绝不动。

第 7 章 · 进阶篇

ref：给原始值一个家

「为什么要写 .value？」大概是 Vue3 被抱怨最多的问题。 读完本章你会发现：.value 不是麻烦，它是响应式系统能覆盖「数字、字符串」的唯一门票。

7.1 Proxy 的盲区

let num = 18;
const proxyNum = new Proxy(num, {});   // 💥 TypeError: 不能代理原始值

// Proxy 的本质是「拦截对对象的属性访问」
// 数字/字符串/布尔值没有属性访问这个动作 → 无从拦截 → 无法追踪

reactive 只能守护对象。可是 count++ 这种场景天天有，怎么办？ Vue 的答案：既然原始值装不上「门禁」，那就给它盖一座房子（对象），把值锁进 .value 这个房间里 —— 房子是对象，能装门禁了： 

class RefImpl {
  __v_isRef = true;                 // 身份标识（和 IS_REACTIVE 暗号异曲同工）
  private _value;
  public dep = createDep(() => (this.dep = undefined), "ref");
                                    // ref 自带一个专属 dep（不用三层名册了！）
  constructor(public rawValue) {
    this._value = toReactive(rawValue);   // 对象值 → 转成 reactive（ref 也能套娃！）
  }
  get value() {
    trackRefValue(this);            // 读 .value → 登记（比 track 三层查找还快）
    return this._value;
  }
  set value(newValue) {
    if (newValue !== this.rawValue) {    // 值没变不折腾（和 set 拦截器同理）
      this.rawValue = newValue;
      this._value = newValue;            // ⚠️ 注意这里（见本章彩蛋找茬）
      triggerRefValue(this);             // → 通知所有登记的 effect
    }
  }
}

为什么 ref 的 dep 更简单？

reactive 需要三层名册，是因为「一个对象有 N 个属性，每个属性各自有粉丝」。 而 ref 只有一个属性（.value），一个 ref 配一个 dep 就够了， 直接挂在实例上（this.dep），读写都少走两层 Map，性能更好。

💡 比喻时间：储物柜
reactive 对象是一整面储物墙（每个格子 = 一个属性，各有各的登记表，所以要三层索引）； ref 是单个带锁储物柜（就一个格子 .value，登记表直接贴柜门上）。

7.2 toRef / toRefs：解构救星

用 reactive 时有个大坑：解构会丢失响应式 —— 解构相当于把值「抄」出来一份普通变量，和原对象断联。 toRefs 的解法是不抄值，改发「引用卡片」： 

class ObjectRefImpl {
  __v_isRef = true;
  constructor(public _object, public _key) {}   // 只记住：哪个对象 + 哪个 key

  get value()    { return this._object[this._key]; }  // 读：实时去原对象拿
  set value(v)   { this._object[this._key] = v; }     // 写：实时写回原对象
}

export function toRef(object, key) {
  return new ObjectRefImpl(object, key);        // 一张「引用卡片」
}

export function toRefs(object) {
  const res = {};
  for (let key in object) {
    res[key] = toRef(object, key);              // 整包对象 → 一沓卡片
  }
  return res;
}

注意 ObjectRefImpl 的 get/set 里没有任何 track/trigger —— 它只是个转发器， 真正的登记发生在 this._object[this._key] 这次「读取原响应式对象」的时候。 代理的代理，轻装上阵。

7.3 proxyRefs：模板里为什么不用写 .value

setup 返回的对象会被 proxyRefs 包一层：

export function proxyRefs(object) {
  return new Proxy(object, {
    get(target, key, receiver) {
      const res = Reflect.get(target, key, receiver);
      return res.__v_isRef ? res.value : res;   // 读到 ref？自动帮你拆箱！
    },
    set(target, key, value, receiver) {
      const oldValue = target[key];
      if (oldValue.__v_isRef) {
        oldValue.value = value;                 // 写到 ref 身上？自动装箱！
        return true;
      } else {
        return Reflect.set(target, key, value, receiver);
      }
    },
  });
}

所以 count 在模板里直接用，count = 5 直接赋值 —— 不是魔法，是 proxyRefs 在 get/set 里默默帮你 .value 了。 这也是为什么 script 里必须写 .value 而模板里不用：两套访问通道而已。

🔍 彩蛋找茬：源码里的一个小瑕疵
看回 RefImpl 的 set：this._value = newValue 直接赋值， 没有再过一次 toReactive。假如你 ref({a:1}) 后又 myRef.value = {b:2}，新对象会以裸对象身份存进 _value， 它的属性读写将失去响应！官方源码里这行是 this._value = toReactive(newValue)。 修掉它，就当是本项目留给你的第一道实战题 😏

computed：聪明的偷懒

computed 的全部哲学浓缩成四个字：能不算就不算。 它靠一个布尔值（dirty 脏标记）统治了整个缓存王国，而且 —— 你已经认识它的全部零件了。

8.1 比喻先行：冰箱里的牛奶

你想喝牛奶（读取 computed），有两种策略：每喝一次就去超市买一次（每次重新计算），或者看一眼冰箱 —— 牛奶还在保质期（不脏）就直接喝，过期了（脏）才去买新的。 「保质期状态」就是 dirty 标记；「牛奶过期」= 依赖变了。

8.2 源码：ComputedRefImpl

class ComputedRefImpl {
  public _value;        // 缓存的结果（牛奶）
  public effect;        // 内部藏着一个 ReactiveEffect（去超市的腿）
  public dep;           // 自己也发卡片：别人可以依赖我这个 computed！

  constructor(public getter, public setter) {
    this.effect = new ReactiveEffect(
      () => getter(this._value),          // 真正干活的：执行你的 getter
      () => { triggerRefValue(this); }    // ⭐ 自定义 scheduler：依赖变了只「通知下游」
    );                                    //    而不是立刻重算！
  }

  get value() {
    if (this.effect.dirty) {              // 牛奶过期了吗？
      this._value = this.effect.run();    //   过期 → 重新计算 & 存冰箱
      trackRefValue(this);                //   同时让「读我的人」也能登记依赖我
    }
    return this._value;                   // 没过期 → 直接喝（零计算）
  }

  set value(newValue) {
    this.setter(newValue);                // 可写 computed（{get,set} 传参那个）
  }
}

export function computed(getterOptions) {
  let onlyGetter = isFunction(getterOptions);
  return new ComputedRefImpl(
    onlyGetter ? getterOptions : getterOptions.get,   // 支持两种传参
    onlyGetter ? () => {}    : getterOptions.set || (() => {})
  );
}

  2. 下游 effect 重跑 → 执行渲染 → 过程中读到 double.value

🧠 精妙之处：懒计算的传播链
脏标记像多米诺骨牌一样传播：count 变 → double 标脏 → 下游 effect 重跑 → 读 double → 才触发计算。 如果下游永远不来读，getter 永远不执行。一个 computed 依赖另一个 computed 时同理 —— 骨牌可以无限接力，计算永远推迟到「真正需要」的那一刻。这就是脏标记算法的威力。

watch：优雅的观察者

学到这里的你，看 watch 源码会是一种享受：没有新概念，全是老朋友 —— ReactiveEffect、scheduler、getter 归一化。这一章更像一次「综合复习」。

9.1 三种形态，归一为 getter

watch 的 source 可以是响应式对象、ref、函数。doWatch 第一步就是把它们统一成 getter：

function doWatch(source, cb, { deep, immediate } = { deep: false, immediate: false }) {
  const reactiveGetter = (source) =>
    traverse(source, deep === false ? 1 : undefined);  // 见 9.2

  let getter;
  if (isReactive(source)) {
    getter = () => reactiveGetter(source);   // 形态① 响应式对象 → 遍历它
  } else if (isRef(source)) {
    getter = () => source.value;              // 形态② ref → 直接读 .value
  } else if (isFunction(source)) {
    getter = source;                          // 形态③ 函数 → 原样使用
  }
  // 不管什么形态，最后都变成「一个函数」，跑在 ReactiveEffect 里
  ...
}

9.2 traverse：为什么要「摸一遍」对象？

watch(obj, cb) 时，如果 getter 只返回 obj 本身，effect 里根本没有发生任何属性读取 —— 不读属性就没有 track，那改任何属性都不会触发回调！traverse 的作用就是把对象每个属性都读一遍， 人为制造 track： 

function traverse(source, depth, currentDepth = 0, seen = new Set()) {
  if (!isObject(source)) return source;
  if (seen.has(source)) return source;      // 防循环引用：摸过的不再摸
  seen.add(source);
  if (depth && currentDepth >= depth) return source;
  for (let key in source) {
    traverse(source[key], depth, currentDepth + 1, seen);  // 递归读取 = 递归登记
  }
  return source;
}
💡 一句话记住
watch 响应式对象 = 「先把全家福每个人都点一遍名，以后谁动了都通知我」。 traverse 就是点名册。seen 集合防止 obj.self = obj 这种环把点名变成死循环。

9.3 job：回调的三个入场券

let oldValue;
let clean;
const onCleanup = (fn) => {                  // 用户注册的「清理上一轮」钩子
  clean = () => { fn(); clean = undefined; };
};

let job = () => {
  if (cb) {
    let newValue = effect.run();             // 重新执行 getter 拿新值
    if (clean) clean();                      // 先清理上一轮的过期任务
    cb(newValue, oldValue, onCleanup);       // 再把新旧值交给用户
    oldValue = newValue;
  } else {
    effect.run();                            // watchEffect：没有回调，直接跑
  }
};

let effect = new ReactiveEffect(getter, job);   // ⭐ 老配方：scheduler = job
if (cb) {
  if (immediate) job();                        // immediate：先斩后奏，立刻执行一次
  else oldValue = effect.run();                // 否则：先跑一遍记录初始值
} else {
  effect.run();
}

注意 watch 的 scheduler 是 job —— 数据变了不重跑 getter 就完了， 而是执行你的回调。这就是第 5 章那张 scheduler 表格里 watch 那一行的落地。

9.4 onCleanup：解决「过时响应」竞态

经典场景：搜索框输入 "ab"，请求 A 发出；马上又输入 "abc"， 请求 B 发出。如果 A 比 B 后返回，页面就会显示旧结果 —— 竞态 bug。onCleanup 的解法：

watch(keyword, async (newVal, oldVal, onCleanup) => {
  let expired = false;
  onCleanup(() => { expired = true; });     // 下一轮触发前，上一轮的 expired 会被置 true
  const result = await api.search(newVal);
  if (!expired) renderList(result);         // 过期了就丢弃，只有最新一轮能上屏
});

effect 嵌套与 effectScope

组件里面还有组件，effect 里面还有 effect。当它们层层嵌套时， 全局唯一的 activeEffect 指针会不会乱套？ 本章回答这个问题，并顺手学会 Vue 生态里批量清理的神器 effectScope。

10.1 问题：嵌套 effect 的「身份错乱」

想象组件树：父组件渲染时跑 outer effect，渲染到子组件时又要跑 inner effect：

effect(() => {            // outer：父组件渲染
  renderParent();
  effect(() => {          // inner：子组件渲染（在 outer 执行期间创建）
    renderChild();
  });                     // ⚠️ inner 结束后，outer 还没跑完！
  renderParentRest();     // 这些读取应该算在 outer 头上
});

如果 activeEffect 是「设置后不管」的普通全局变量，inner 跑完把它设成了自己， 之后 outer 剩余代码的依赖就会全部错误地登记到 inner 名下 —— 数据一变，错的 effect 重跑。

10.2 解法：暂存-还原（隐式借用了函数调用栈）

回看第 2 章 run() 的代码，答案早已埋下：

run() {
  let lastEffect = activeEffect;   // ① 暂存「上一层」是谁（压栈）
  try {
    activeEffect = this;           // ② 指针换成自己
    ...
    return this.fn();              // ③ 执行（里面可能再嵌套下一层）
  } finally {
    ...
    activeEffect = lastEffect;     // ④ 还原（弹栈）
  }
}

①④ 配合就是一次手动压栈/弹栈 —— 只是借用了 JS 函数调用栈本身的递归结构来保存 lastEffect， 不需要真的维护一个数组。嵌套多深都没关系：每层 run 都会保存/恢复自己的「上一层」。

🧠 源码演进八卦
Vue 3.0 ~ 3.3 时代，源码里真的有一个 effectStack 数组（push/pop）； 到 3.4 重构时发现「暂存局部变量 + finally 还原」完全等价且更少一次数组操作，就换成了现在这种写法 —— 本项目采用的正是 3.4 版。读源码时见到两种写法不要慌，它们是同一思想的不同年代版本。

10.4 effectScope：给 effect 们发一个「团长」

一个组件会创建大量 effect：渲染 effect、N 个 watch、M 个 computed。 组件卸载时要一个个 stop 吗？太蠢了。Vue 3.2 引入 effectScope： 「作用域内的 effect 我统一记账，一声令下集体退休」。 

let activeScope = null;                 // 又见「全局指针 + 暂存还原」！

export class EffectScope {
  effects = [];                         // 记账本：本作用域内创建的所有 effect
  cleanups = [];                        // onCleanup 钩子们
  active = true;

  run(fn) {
    const lastScope = activeScope;      // 和 effect.run 一模一样的套路！
    activeScope = this;
    try {
      return fn();                     // 期间创建的 effect 会自动来找团长登记
    } finally {
      activeScope = lastScope;
    }
  }

  on(fn) { this.cleanups.push(fn); }

  stop() {
    this.active = false;
    this.effects.forEach(e => e.stop());   // 集体退休
    this.cleanups.forEach(fn => fn());
    this.effects.length = 0;
  }
}

// ReactiveEffect 构造时（源码真实逻辑）：
//   if (activeScope && activeScope.active) activeScope.effects.push(this)
//   ↑ 这就是「自动记账」：effect 出生时看一眼当前团长是谁

使用方式（也是 Composition API 中 stop 的底层原理）：

const scope = effectScope();

scope.run(() => {
  const state = reactive({ count: 0 });
  watch(() => state.count, cb);         // 被记账
  computed(() => state.count * 2);      // 被记账
  effect(() => state.count);            // 被记账
});

scope.stop();                           // 💥 上面三个全部停止，一行搞定
💡 在哪见过它？
Vue 组件的 setup 就运行在一个 effectScope 里 —— 组件卸载时调 scope.stop()， 该组件所有的 watch/computed/渲染 effect 一次性停干净。VueUse 的 createEventHook、 tryOnScopeDispose 也基于它。你写的每个组合式函数，都活在一个 scope 里。
自测一下：嵌套与作用域

1. 如果去掉 finally 里的 activeEffect = lastEffect，嵌套场景会发生什么？

答案：
1. 内层 effect 跑完后 activeEffect 永远指向内层，外层剩余代码的依赖全登记到内层名下：改外层数据 → 内层重跑（错），改内层数据 → 也内层重跑，外层从此失去响应。
2. 能读（run() 里 if (!this.active) return this.fn()，非激活态照常执行），但不再收集依赖、不再缓存 —— computed 退化成普通函数调用。

11.2 官方是怎么用一个函数工厂生产四兄弟的

本项目的 reactive 写死了 mutableHandlers。官方源码用「处理器组合 + 工厂」批量生产 —— 这是值得学习的代码组织方式： 

// 四种 baseHandler 的差异只体现在两个维度：是否递归（get），是否可写（set）
function createGetter(isReadonly = false, shallow = false) {
  return function get(target, key, receiver) {
    if (key === ReactiveFlags.IS_REACTIVE) return !isReadonly;
    const res = Reflect.get(target, key, receiver);
    if (!isReadonly) track(target, key);          // 只读也 track！（只读也能驱动 watch）
    if (shallow) return res;                       // shallow：到此为止，不递归
    if (isObject(res)) return isReadonly ? readonly(res) : reactive(res);
    return res;
  };
}

function createSetter(shallow = false) {
  return function set(target, key, value, receiver) {
    const oldValue = target[key];
    const result = Reflect.set(target, key, value, receiver);
    if (!shallow && oldValue !== value) trigger(target, key);
    return result;
  };
}

// 四兄弟 = 四种组合
const mutableHandlers    = { get: createGetter(), set: createSetter() };
const shallowHandlers    = { get: createGetter(false, true), set: createSetter() };
const readonlyHandlers   = { get: createGetter(true) };   // 没有 set！改就报错
const shallowReadonlyHandlers = { get: createGetter(true, true) };

// 一个工厂生产所有 reactive 家族
function createActiveObject(target, baseHandlers) {
  return new Proxy(target, baseHandlers);
}
🧠 为什么 props 是 shallowReadonly？
props 由父组件下发，子组件不该改它（只读），且深层转响应式是父组件的事 （避免重复代理、保证同一份数据只有一个代理源）—— 所以 Vue 给 props 的默认包装是 shallowReadonly。 你在子组件里改 props.obj.inner.x 能成功（第一层之外没锁）但会被警告， 这正是 shallow 的边界。现在你不仅知道「不能改」，还知道「为什么锁在这一层」。

11.4 customRef：手动挡的 ref

ref 的 track（读时登记）和 trigger（写时通知）都是自动的。 customRef 把这两个时机的控制权交给你 —— 经典应用：防抖。 

import { customRef } from "vue";

function debouncedRef(value, delay = 200) {
  let timer;
  return customRef((track, trigger) => ({
    get() {
      track();                        // 读：登记（自动挡改手动挡，但一般照常登记）
      return value;
    },
    set(newValue) {
      clearTimeout(timer);
      timer = setTimeout(() => {      // 写：先攒着，攒够 200ms 才通知
        value = newValue;
        trigger();                    // 通知时才触发界面更新
      }, delay);
    },
  }));
}

12.2 Bug 案例一：「数据改了页面不动」——解构惹的祸

const state = reactive({ count: 0, list: [] });

12.3 Bug 案例二：「解构 props 之后父组件更新失效」

12.4 Bug 案例三：「放进 Set/Map 之后响应式消失了」

const state = reactive({ id: 1 });

渲染器：分层的艺术

响应式系统已经毕业，现在换个口味：看 Vue 怎么把「数据」变成「页面上的像素」。 本章有两个宝藏：跨平台的 nodeOps 适配器，和一个被无数框架抄袭的事件缓存技巧 —— invoker。

13.1 nodeOps：把 DOM 装进「接口盒子」

第 1 章说过：runtime-core 不认识 DOM。但它渲染时确实需要「插入节点、删除节点、改文本」这些动作。 怎么办？我不亲自干，我定义标准，谁来谁干。runtime-dom 交上了自己的答卷： 

// 主要是对节点元素的增删改查
export const nodeOps = {
  insert(el, parent, anchor) {
    parent.insertBefore(el, anchor || null);   // 插入（anchor 指定插到谁前面）
  },
  remove(el) {
    const parent = el.parentNode;
    parent && parent.removeChild(el);          // 删除
  },
  createElement: (type) => document.createElement(type),  // 创建元素
  createText: (text) => document.createTextNode(text),    // 创建文本节点
  setText: (node, text) => (node.nodeValue = text),       // 改文本节点的字
  setElementText: (el, text) => (el.textContent = text),  // 改元素的内容
  parentNode: (node) => node.parentNode,
  nextSibling: (node) => node.nextSibling,
};

九个纯函数，全是 DOM API 的薄封装。然后 runtime-dom 把它们和 patchProp 打包，注入给 core：

// runtime-dom：组装渲染选项（接口实现）
export const renderOptions = Object.assign(nodeOps, { patchProp });

export const render = (vnode, container) => {
  createRenderer(renderOptions).render(vnode, container);  // 依赖注入！
};

// runtime-core：拿到一整套「操作能力」，但不知道背后是浏览器
export function createRenderer(renderOptions) {
  const {
    insert: hostInsert,
    remove: hostRemove,
    createElement: hostCreateElement,
    setElementText: hostSetElementText,
    setText: hostSetText,
    parentNode: hostParentNode,
    nextSibling: hostNextSibling,
    patchProp: hostPatchProp,
  } = renderOptions;

  // core 不关心如何渲染
  const render = (vnode, container) => {
    console.log(vnode, container);   // 🚧 项目进度：render 骨架已立，等你来写
  };
  return { render };
}
🧠 这就是「依赖倒置」
高层模块（core）定义抽象接口，低层模块（dom）提供具体实现，通过参数注入。 换一个 runtime-xxx 就能渲染到 canvas、WebGL、原生 App —— 响应式系统一行动不用改。 框架的跨平台能力，从来不是靠兼容，而是靠分层。

13.2 patchProp：属性的分流处理

vnode 的 props 千奇百怪，patchProp 按类型分流到四个处理模块：

function patchProp(el, key, prevValue, nextValue) {
  if (key === "class") {
    return patchClass(el, nextValue);          // class 走 className（比 setAttribute 快）
  } else if (key === "style") {
    return patchStyle(el, prevValue, nextValue);  // style 要做新旧 diff
  } else if (/^on[^a-z]/.test(key)) {          // onClick、oninput → 事件
    return patchEvent(el, key, nextValue);
  } else {
    return patchAttr(el, key, nextValue);      // 其他 → setAttribute
  }
}

四个小模块中最普通的是 attr：

// patchAttr：有值设值，没值删掉
export default function patchAttr(el, key, nextValue) {
  if (nextValue) el.setAttribute(key, nextValue);
  else el.removeAttribute(key);
}

// patchClass：清空用 removeAttribute（注意不是设空字符串）
export default function patchClass(el, value) {
  if (!value) el.removeAttribute("class");
  else el.className = value;
}

// patchStyle：新样式逐条应用；旧样式里新值没有的 → 清空
export default function patchStyle(el, prevValue, nextValue) {
  let style = el.style;
  for (let key in nextValue) style[key] = nextValue[key];
  if (prevValue) {
    for (let key in prevValue) {
      if (nextValue[key] == null) style[key] = null;   // 清掉被删掉的样式
    }
  }
}

13.3 ⭐ patchEvent：invoker，事件缓存的绝招

思考题：每次渲染都会给元素挂新的 onClick 函数。最笨的写法：

el.removeEventListener("click", oldFn);   // 摘掉旧的
el.addEventListener("click", newFn);       // 挂上新的
// ⚠️ 每次渲染都来这么一下，两个昂贵的 DOM 调用

源码的解法妙到毫巅：真正挂到元素上的永远是一个不变的 invoker 壳子， 用户的回调藏在 invoker.value 里随时替换：

function createInvoker(value) {
  const invoker = (e) => invoker.value(e);   // 壳子：点击时才去找此刻的 value
  invoker.value = value;                     // 回调挂在壳子的 value 属性上
  return invoker;
}

export default function patchEvent(el, name, nextValue) {
  const invokers = el._vei || (el._vei = {});     // 元素级缓存表：_vei = {onClick: invoker}
  const eventName = name.slice(2).toLowerCase();
  const existingInvoker = invokers[name];

  if (nextValue && existingInvoker) {
    return (existingInvoker.value = nextValue);   // 情况A：已挂过 → 只换 value！0 次 DOM 调用
  }
  if (nextValue) {
    const invoker = (invokers[name] = createInvoker(nextValue));
    return el.addEventListener(eventName, invoker);  // 情况B：首次 → 挂壳子
  } else if (existingInvoker) {
    el.removeEventListener(eventName, existingInvoker); // 情况C：新值为空 → 摘除
    invokers[name] = undefined;
  }
}
💡 比喻时间：公司前台
addEventListener 像雇一位前台：真正的前台（invoker）永远不换人； 客户来了（点击发生）前台才喊当前负责的同事（invoker.value 回调）。 换负责同事（更新回调）只需换工牌，不用解雇再招聘前台 —— 频繁变化的回调，包一层不变的外壳。React 合成事件、小程序框架里都有同款思想。

h 与 VNode：虚拟的代价与回报

从本章起，我们亲手把 runtime-core 的骨架写满。第一块砖：虚拟节点（VNode）—— 用 JS 对象描述界面，而不是直接操作界面。为什么多此一举？答案藏在一个字里：diff。

14.1 为什么需要 VNode

直接操作 DOM 有什么问题？三个：

  1. DOM 操作昂贵：一次 appendChild 可能触发重排/重绘，代价是 JS 对象操作的百倍量级；
  2. 无法比较：两个真实 DOM 之间没有「新旧可比性」——改了就是改了，覆水难收；
  3. 强绑浏览器：document 只存在于浏览器（还记得第 13 章的跨平台野心吗？）。

JS 对象便宜、可保存、可比较、可跨平台 —— VNode = 界面某一刻的快照。渲染器的工作就是：拍快照 → 新旧快照 diff → 把差异最小化地应用到真实 DOM。

旧 VNode 树 + 新 VNode 树 → diff（纯 JS，超快） → 最小 DOM 更新
昂贵操作（DOM）被「批量 + 最小化」了，便宜操作（比较对象）随便造 —— 这就是虚拟 DOM 的全部经济学

14.2 VNode 结构解剖

{
  __v_isVNode: true,      // 身份暗号（IS_REACTIVE 的老朋友了）
  type: "div",            // 标签名 / 组件对象 / Text / Fragment…
  key: null,              // diff 复用的身份证（第 16 章主角）
  props: { class: "card", onClick: fn },
  children: "文本" 或 [vnode, vnode, ...],
  el: null,               // ⭐ 挂载后指向真实 DOM（VNode 与真实世界的桥）
  shapeFlag: ShapeFlags.ELEMENT,   // 类型位标记（下节）
}

三个字段值得划重点：

  • el：挂载时渲染器把真实 DOM 写回 vnode.el —— diff 阶段顺着 el 就能找到真实节点，新旧 vnode 通过它「共用」一个 DOM；
  • key：用户不传就用 null。为什么列表必须传 key？第 16 章你会看到没有 key 时算法直接退化；
  • children 的两种形态：字符串（文本子节点）或数组（子节点列表）—— mount 时分两条路径处理。

14.3 shapeFlag：一个数字背着 32 个布尔值

VNode 可能是元素/文本/组件/Fragment，children 可能是文本/数组/插槽……如果每个可能性都存一个布尔字段，对象会又胖又慢。官方用位运算把所有类型压进一个数字：

const ShapeFlags = {
  ELEMENT: 1,          // 0001  是元素
  FUNCTIONAL: 1 << 1,  // 0010  是函数组件
  STATEFUL: 1 << 2,    // 0100  是有状态组件
  TEXT_CHILDREN: 1 << 3,       // 1000  children 是文本
  ARRAY_CHILDREN: 1 << 4,     // 10000 children 是数组
};

// 标记：一个数字同时记住多个事实
let flag = ShapeFlags.ELEMENT | ShapeFlags.TEXT_CHILDREN;   // 1001 = 9

// 判断：一次 & 运算，比读属性还快
if (flag & ShapeFlags.ELEMENT) { /* 是元素 */ }
if (flag & ShapeFlags.ARRAY_CHILDREN) { /* children 是数组 */ }
💡 位运算为什么快
flag & 8 是一次 CPU 位与指令；而 obj.isElement 是一次属性查找（可能走原型链）。 VNode 创建频率极高（每帧每节点），这种微观优化累积起来就是宏观性能。 Linux 的文件权限（755）、React 的 fiber flags、Vue 的 patchFlags —— 全是同一招。

14.4 h()：创建 VNode 的工厂

直接写对象字面量太啰嗦，Vue 提供 h()（hyperscript，源自 HTML 的发明者超文本思路）：

export function h(type, props, children) {
  // 参数归一化：h("div") / h("div", props) / h("div", [], ...) 都合法
  if (!props) props = {};

  let shapeFlag = typeof type === "string"
    ? ShapeFlags.ELEMENT          // 字符串 → 元素
    : ShapeFlags.STATEFUL;        // 对象 → 组件（第 17 章）

  if (typeof children === "string") {
    shapeFlag |= ShapeFlags.TEXT_CHILDREN;
  } else if (Array.isArray(children)) {
    shapeFlag |= ShapeFlags.ARRAY_CHILDREN;
  }

  return {
    __v_isVNode: true,
    type, props,
    key: props && props.key != null ? props.key : null,
    children,
    el: null,
    shapeFlag,
  };
}

// 使用对照：
// 模板 <div class="card" @click="fn">hi</div> 等价于：
h("div", { class: "card", onClick: fn }, "hi");
// children 是数组的版本：
h("ul", null, [ h("li", { key: "a" }, "苹果"), h("li", { key: "b" }, "香蕉") ]);

一个容易混淆的点，先种个种子（第 17 章展开）：

VNode 树是「界面结构」的快照，其中某些节点的 type 是组件对象； 组件树是「逻辑单元」的嵌套。一个组件 VNode 展开后是一整棵元素 VNode 子树。
🧠 为什么叫 h？
h = hyperscript，"HyperText Markup Language" 里的 HTML 拆开就是 Hyperscript。 这个命名来自虚拟 DOM 的鼻祖 hyperscript 生态（React.createElement 的思想同源）。 知道来历，你就再也不会把 h 和 hash、height 之类搞混了。

mountElement：首挂载实战

本章我们把 render 函数从 console.log 写成真正的渲染器： 递归地把 VNode 树翻译成真实 DOM。写完后你会突然明白 —— 原来第 2 章的 effect 和第 15 章的 render，只差一层窗户纸。

15.1 总路线图

render(vnode, container) → patch(null, vnode) → mountElement(vnode, container)
patch 是统一的入口：oldVNode 为 null 就是「挂载」，否则是「更新」（下一章）

15.2 完整实现（可直接抄进 runtime-core/src/index.ts）

export function createRenderer(renderOptions) {
  const {
    insert: hostInsert, remove: hostRemove,
    createElement: hostCreateElement,
    setElementText: hostSetElementText,
    setText: hostSetText,
    parentNode: hostParentNode, nextSibling: hostNextSibling,
    patchProp: hostPatchProp,
  } = renderOptions;

  /* ---------- 挂载一个元素 vnode ---------- */
  function mountElement(vnode, container, anchor) {
    // ① 把 el 回写进 vnode（第 14 章说的那座桥）
    const el = (vnode.el = hostCreateElement(vnode.type));

    // ② 上属性：遍历 props，分流给 patchProp（第 13 章的四分流）
    for (const key in vnode.props) {
      hostPatchProp(el, key, null, vnode.props[key]);
    }

    // ③ 挂 children：文本 / 数组 两条路（shapeFlag 决定）
    if (typeof vnode.children === "string") {
      hostSetElementText(el, vnode.children);
    } else if (Array.isArray(vnode.children)) {
      for (const child of vnode.children) {
        // 数组 children：每个子节点递归 patch(null, child) 挂进来
        patch(null, child, el, null);
      }
    }

    // ④ 最后一步才把 el 插入文档（先在「内存里」组装好，一次进场）
    hostInsert(el, container, anchor);
  }

  /* ---------- 卸载 ---------- */
  function unmount(vnode) {
    hostRemove(vnode.el);
  }

  /* ---------- 统一入口 ---------- */
  function patch(oldVNode, vnode, container, anchor) {
    if (oldVNode === vnode) return;          // 同一个对象引用，啥也不用干
    if (oldVNode && oldVNode.type !== vnode.type) {
      // 类型都变了：旧树整个卸掉，走全新挂载
      unmount(oldVNode);
      oldVNode = null;
    }
    // 统一交给 processElement（预留组件分支的位置，第 17 章）
    processElement(oldVNode, vnode, container, anchor);
  }

  function processElement(oldVNode, vnode, container, anchor) {
    if (oldVNode == null) {
      mountElement(vnode, container, anchor);   // 无旧 → 挂载
    } else {
      patchElement(oldVNode, vnode);            // 有旧 → 更新（下一章实现）
    }
  }

  function render(vnode, container) {
    if (vnode == null) {
      // 传 null → 卸载整棵树（Vue3 卸载组件的官方姿势）
      if (container._vnode) unmount(container._vnode);
    } else {
      patch(container._vnode || null, vnode, container, null);
    }
    container._vnode = vnode;   // container 记住当前树，下次更新 diff 用
  }

  return { render };
}

四个细节，四个心意

  • 「先组装后进场」（④ 在 ③ 后面）：子树全部在游离 DOM 上构建完才 insert，避免布局引擎看到中间状态，减少无谓重排 —— 和装修完再搬家一个道理；
  • container._vnode：渲染器把「上一次的树」记在容器身上。render 两次，自动获得 diff 能力 —— 状态就存在 DOM 节点上，很朴素；
  • anchor 参数一路透传：为 diff 阶段「往中间插节点」预留的位置参数（insert 的第三个参数）；
  • oldVNode === vnode 短路：同一个 vnode 对象直接跳过 —— 第 18 章编译优化的静态提升就靠它白嫖。

第 16 章 · 渲染器篇

patch 与 diff：最长递增子序列

渲染器的珠穆朗玛峰：当两组带 key 的子节点都变了， 如何用最少的 DOM 移动让旧列表变成新列表？Vue3 的答案是五步预处理 + 最长递增子序列（LIS）。 这是前端算法面试的天花板题，也是本章的全部内容。

16.1 patchElement：属性打补丁

先热身。新旧 vnode 同类型时，不走推倒重来，而是「就地打补丁」：

function patchElement(oldVNode, vnode) {
  const el = (vnode.el = oldVNode.el);   // ⭐ 复用旧 DOM！这一行就是「不推倒重来」

  // ① 属性 diff：新旧 props 的键取并集，逐键比较
  const oldProps = oldVNode.props || {};
  const newProps = vnode.props || {};
  for (const key in newProps) {
    if (newProps[key] !== oldProps[key]) {          // 变了的才动
      hostPatchProp(el, key, oldProps[key], newProps[key]);
    }
  }
  for (const key in oldProps) {
    if (!(key in newProps)) {                        // 新里没有 → 删属性
      hostPatchProp(el, key, oldProps[key], null);
    }
  }

  // ② children diff：本章主角
  patchChildren(oldVNode, vnode, el);
}

属性 diff 的哲学和第 6 章依赖清理、第 13 章 patchStyle 完全同构：新来的应用，过期的清除，没变的不碰。

16.2 patchChildren 的分诊台

function patchChildren(oldVNode, vnode, el) {
  const oldCh = oldVNode.children, newCh = vnode.children;

  if (typeof newCh === "string") {
    // 新是文本：旧的不管是啥，整体覆盖（数组的话先逐个卸载）
    if (Array.isArray(oldCh)) oldCh.forEach(c => unmount(c));
    if (oldCh !== newCh) hostSetElementText(el, newCh);
  } else if (Array.isArray(newCh)) {
    if (Array.isArray(oldCh)) {
      patchKeyedChildren(oldCh, newCh, el);   // ⭐ 双数组：进入主战场
    } else {
      hostSetElementText(el, "");             // 旧文本 → 清空再挂新数组
      newCh.forEach(c => patch(null, c, el, null));
    }
  } else {
    // 新 children 为空：旧的清光
    if (Array.isArray(oldCh)) oldCh.forEach(c => unmount(c));
    else hostSetElementText(el, "");
  }
}

16.3 主战场：五步预处理 + LIS

patchKeyedChildren 是 Vue3 渲染器最复杂的 100 行。它的智慧在于：先用便宜的预处理干掉大多数情况，实在乱序才请出 LIS。

第一步：从头同步（sync from start）

ab c← 停！ 前面 key 相同的逐个 patch（打补丁不移动），到 c 停下

第二步：从尾同步（sync from end）

尾部 key 相同的也逐个 patch → 停！→ def

头尾两次「白捡」之后，剩下中间一段真正乱序的。若一方已耗尽，直接批量挂载/卸载收工（第三步，略）。

第四步：乱序段 —— key 映射表

// 给新节点建索引表：key → 在新列表中的下标
const keyToNewIndex = new Map();
for (let j = s2; j <= e2; j++) keyToNewIndex.set(newCh[j].key, j);

// 遍历旧乱序段：在表里找得到 → 复用；找不到 → 卸载
const toBePatched = e2 - s2 + 1;
const newIndexToOldIndex = new Array(toBePatched).fill(-1);  // ⭐ 核心数组
let moved = false, maxNewIndexSoFar = 0;

for (let i = s1; i <= e1; i++) {
  const newIndex = keyToNewIndex.get(oldCh[i].key);
  if (newIndex === undefined) {
    unmount(oldCh[i]);                        // 新列表没有我 → 卸载
  } else {
    newIndexToOldIndex[newIndex - s2] = i;    // 记下「新位置的旧主人」
    if (newIndex < maxNewIndexSoFar) moved = true;  // 顺序倒退了 → 需要移动
    else maxNewIndexSoFar = newIndex;
  }
}

newIndexToOldIndex 是整个算法的枢纽：下标 = 新位置，值 = 这个位置的旧节点是谁。 -1 表示这个新位置没有旧主人（要新建）。

第五步：LIS —— 能不动就不动

如果 moved = true，问题变成：newIndexToOldIndex 里哪些节点保持相对顺序不变（不用动），剩下的才需要移动？ 这正是最长递增子序列（Longest Increasing Subsequence）的定义。LIS 里的节点原地不动，其余的用 insert 挪到位 —— 数学保证这就是最少移动方案。 

// 目标：返回最长递增子序列的「下标集合」（注意：是下标，不是值！）
function getSequence(arr) {
  const result = [0];            // result 存下标；对应值单调递增
  for (let i = 1; i < arr.length; i++) {
    if (arr[i] === -1) continue;              // -1 = 新挂载位置，跳过
    const last = arr[result[result.length - 1]];
    if (arr[i] > last) {
      result.push(i);                         // 比尾巴大 → 直接接上（LIS 变长）
    } else {
      // 二分找到 result 中第一个 ≥ arr[i] 的位置，替换之（给后面留「更低的台阶」）
      let lo = 0, hi = result.length - 1;
      while (lo < hi) {
        const mid = (lo + hi) >> 1;
        if (arr[result[mid]] < arr[i]) lo = mid + 1;
        else hi = mid;
      }
      result[lo] = i;
    }
  }
  return result;   // 这些下标对应的节点 → 原地不动
}

// 最后一步：从后往前遍历新列表（从后往前是为了算 insert 的 anchor）
let lisIndex = result.length - 1;
for (let j = toBePatched - 1; j >= 0; j--) {
  const oldIndex = newIndexToOldIndex[j];
  if (oldIndex === -1) {
    patch(null, newCh[s2 + j], el, anchor);    // 没有旧主人 → 新建
  } else {
    if (lisIndex < 0 || j !== result[lisIndex]) {
      hostInsert(newCh[s2 + j].el, el, anchor); // 不在 LIS 里 → 挪我
    } else {
      lisIndex--;                                // 在 LIS 里 → 纯 patch，不挪
    }
  }
  anchor = newCh[s2 + j].el;                    // 锚点随行
}
💡 LIS 为什么「从后往前」遍历？
insert(el, container, anchor) 的语义是「插到 anchor 前面」。从后往前处理时，anchor 永远指向「已经处理好的下一个位置」， 每个节点挪到 anchor 前就自动落位。从前往后的话 anchor 语义会打架。这个方向选择是理解 diff 实现的钥匙之一。

⚠️ 为什么不许用 index 当 key？
index 是「位置编号」而不是「身份」。头部插入一项后所有 index 平移 —— 旧节点 a（原 index 0）会被误认为新节点 a（现 index 1）的身份完全错位， diff 退化成大面积错误复用 + 移动；带输入框的列表还会出现「内容串行」的经典 bug。 key 的本质是「身份证号」，不是「座位号」。
自测一下：diff 算法

1. old [a,b,c] → new [a,b,c,d,e] 走到 LIS 吗？总共几次 DOM 操作？
2. LIS 保护「不动节点」时，patch（属性补丁）还执行吗？

答案：
1. 走不到。头同步吃掉 a,b,c，旧列表耗尽 → 第三步批量挂载 d,e。DOM 操作 = 2 次 mount + 2 次 insert，零移动 —— 预处理的省钱威力。
2. 执行。LIS 只免除「位置移动」，新旧节点仍要 patchElement diff 属性/子节点 —— 不动 ≠ 不更新。

第 17 章 · 渲染器篇

组件化：响应式 × 渲染器合流

全书高潮。当 vnode.type 从字符串变成「组件对象」，两大系统正式会师： 组件的渲染函数被包进 effect，从此数据变了，界面自动重渲染 —— 你日常写的每一个 .vue 文件，底层都是这一章的代码。

17.1 组件 vnode：type 是个对象

// 元素 vnode：type 是字符串
h("div", { class: "box" }, "hi");

// 组件 vnode：type 是对象（或 setup 函数）
const Counter = {
  props: ["count"],
  setup(props) { /* ... */ },
  render() { return h("div", null, `count is ${this.count}`); },
};
h(Counter, { count: 1 });   // ← type = 组件对象

所以 patch 只需在入口加一个分流：

function patch(oldVNode, vnode, container, anchor) {
  if (oldVNode === vnode) return;
  if (oldVNode && oldVNode.type !== vnode.type) { unmount(oldVNode); oldVNode = null; }

  if (typeof vnode.type === "string") {
    processElement(oldVNode, vnode, container, anchor);   // 元素线（第 15 章）
  } else {
    processComponent(oldVNode, vnode, container, anchor); // ⭐ 组件线（本章）
  }
}

17.2 mountComponent：三步走

function mountComponent(oldVNode, vnode, container, anchor) {
  // ① 创建组件实例：一个装所有运行时状态的「档案袋」
  const instance = (vnode.component = {
    vnode, props: {}, slots: null, subTree: null,   // subTree = 组件渲染出的元素树
    isMounted: false, next: null,                    // next = 待更新的新 vnode
  });

  // ② 初始化 props + 调用 setup（你写的组合式 API 在这里执行！）
  instance.props = vnode.props;
  const setupResult = vnode.type.setup?.(instance.props);
  if (typeof setupResult === "function") {
    instance.render = setupResult;      // setup 返回函数 → 就是 render
  } else {
    instance.setupState = proxyRefs(setupResult);  // 返回对象 → 第 7 章的自动脱 .value！
    instance.render = vnode.type.render;
  }

  // ③ 建立响应式渲染：⭐⭐ 全书最重要的一次 effect 包装 ⭐⭐
  setupRenderEffect(instance, container, anchor);
}

function setupRenderEffect(instance, container, anchor) {
  instance.update = effect(function componentUpdateFn() {
    if (!instance.isMounted) {
      // 首挂载：跑 render 拿到元素子树，递归挂载
      const subTree = instance.render();
      patch(null, subTree, container, anchor);
      instance.subTree = subTree;
      instance.isMounted = true;
    } else {
      // 更新：重跑 render 拿新子树，与旧 subTree 做 patch（第 16 章 diff 上场）
      const nextTree = instance.render();
      const prevTree = instance.subTree;
      patch(prevTree, nextTree, container, anchor);
      instance.subTree = nextTree;
    }
  });
}

请把 ③ 读三遍。所有魔法在这里闭环：

render() 读响应式数据 → track 收集依赖
数据变化 trigger → update（effect）重跑 → 新旧 subTree diff → 最小化更新 DOM
第 2 章的 effect + 第 16 章的 diff = 「数据驱动视图」的完整闭环

17.3 父组件更新，子组件怎么办？

父组件重渲染时，子组件 vnode 也会重建。但子组件不一定要重渲染 —— Vue 的组件更新是有「资格审查」的（shouldUpdateComponent）： 

function updateComponent(oldVNode, newVNode) {
  newVNode.component = oldVNode.component;   // ⭐ 复用整个实例（组件的「身份」不变）

  if (shouldUpdateComponent(oldVNode, newVNode)) {
    newVNode.component.next = newVNode;      // 待更新 vnode 挂到 next 上（异步排队）
    newVNode.component.update();             // 手动触发一次渲染 effect
  } else {
    // props 没变（浅比较 + hasChanged）：直接吃掉新 vnode，跳过重渲染
    newVNode.component.vnode = newVNode;
  }
}

// shouldUpdateComponent 的粗略逻辑：
//   - 新旧 props 里有任何一个键的值变了（Object.is 比较）→ true
//   - 子组件还有 slots/emits 依赖 → 保守起见 true
🧠 这就是「组件级缓存」的第一道防线
props 没变就跳过整棵子树的重渲染 —— 比 memo 手动优化更早、更自动。 配合第 18 章编译器的 patchFlag（精确知道哪些 props 可能变），这道闸门效率极高。 Vue 里 v-memo、React 里 memo + 浅比较，本质都在做同一件事：身份没变就别动。

17.4 生命周期：注册即挂榜

onMounted 等钩子的原理朴素得可爱：往当前组件实例的钩子数组里 push 回调，时机到了挨个调用。 关键又是那个熟悉的全局指针模式： 

let currentInstance = null;          // 第三次见到这个模式了！（activeEffect、activeScope）

function onMounted(fn) {
  if (currentInstance) {             // 必须在 setup 同步执行期间调用！
    currentInstance.mounted.push(fn);
  } else {
    warn("onMounted 只能在 setup 中调用");
  }
}

function setupComponent(instance) {
  const last = currentInstance;      // 暂存（第 10 章的老配方）
  currentInstance = instance;
  try {
    instance.render = instance.type.setup(instance.props) || ...;
  } finally {
    currentInstance = last;          // 还原 —— 所以异步回调里调 onMounted 会丢
  }
}

function mountComponent(instance) {
  /* ...挂载完成后... */
  instance.mounted.forEach(fn => fn());   // 挨个执行（源码里叫 invokeArrayFns）
}
⚠️ 为什么 async setup 里不能裸调 onMounted？
setup 一旦 await，执行权就交出去了 —— 后续代码运行时 currentInstance 早已还原成 null，钩子注册失败。 所以 Vue 提供 onActivated/onDeactivated 之外还有 Suspense 的特殊处理， 而普通项目里的忠告是：生命周期注册必须在 setup 的同步阶段完成。原理现在你懂了：不是规则霸道，是指针回家了。

17.5 更新调度：effect 的 scheduler 第二春

真实 Vue 里 instance.update 的 scheduler 不是立刻执行，而是 queueJob —— 推进一个去重队列，微任务里统一 flush。 为什么？一个事件里改 3 个数据，trigger 3 次 update，但 patch 只需要最后一次： 

const queue = new Set();          // Set 天然去重：同一组件的 update 只留一份
let isFlushing = false;

function queueJob(job) {
  queue.add(job);                 // 只排队，不执行
  if (!isFlushing) {
    isFlushing = true;
    Promise.resolve().then(flushJobs);   // 微任务：等本轮同步代码全跑完
  }
}

function flushJobs() {
  queue.forEach(job => job());    // 此刻数据已是最终态，每个组件只 patch 一次
  queue.clear(); isFlushing = false;
}

第 5 章 scheduler 的种子（「数据变了不直接跑，先问调度器」）至此完全开花结果。

2. 父组件重渲染、子组件 props 未变，子组件的 render 会执行吗？其模板里的 DOM 会被重建吗？

答案：
1. ① ref 的 set 拦截（第 7 章）→ ② triggerRefValue 找到组件 update effect（第 5 章）→ ③ queueJob 入队，微任务 flush（本章）→ ④ effect.run 重跑 render，读 count 被重新 track（第 2/4 章）→ ⑤ 新旧 subTree 走 patch/diff（第 15/16 章）→ ⑥ 最小化 DOM 更新上屏。
2. render 不执行（shouldUpdateComponent 拦截 + vnode 复用）；DOM 也不会重建 —— 子树 vnode 对象都没变，patch 直接短路。这就是 Vue 组件树的自动剪枝。

第 18 章 · 编译器篇

编译器：模板到 render 函数

你写的 <template> 不是浏览器能懂的东西 —— 它在构建阶段被编译成 h() 调用。本章不实现编译器（那是一座独立的山）， 但要看懂它的产物和三大优化 —— 这决定了你写模板时的性能直觉。

18.1 三段流水线：parse → transform → generate

template 字符串 → parse
→ AST 语法树 → transform
→ 优化 + 打标 → generate
→ render 函数代码
和任何编译器（Babel、TypeScript、GCC）同构：词法/语法分析 → 转换 → 代码生成

18.2 一段模板的「前后对照」

<template>
  <div class="box">
    <h1>标题不变</h1>
    <p>{{ count }}</p>
  </div>
</template>
// ① 静态节点被「提升」到函数外 —— 只创建一次，每次渲染直接复用（hoistStatic）
const _hoisted_1 = h("h1", null, "标题不变");

function render(_ctx) {
  return h("div", { class: "box" }, [
    _hoisted_1,                              // 直接引用，不重新创建 vnode
    h("p", null, _ctx.count, -1 /* PROPS 无, TEXT 有 */),
    //                                    ↑ patchFlag：告诉 patch「这个节点只有文本会变」
  ]);
}

18.3 优化一：静态提升（hoistStatic）

模板里大量内容是静态的（标题、图标、装饰节点）。不提升的话，每次渲染都为它们重建 vnode —— 纯浪费。 提升到 render 函数外后：创建一次，终身复用。配合第 15 章 patch 里 oldVNode === vnode 的短路判断 —— 连 diff 都不用做，同一引用直接跳过。

💡 写模板的黄金直觉
模板里「写死的内容」几乎零成本（提升 + 短路）。真正的开销在动态绑定的数量 —— 一个 {{ }} 就是一个动态点。把静态内容从 v-for 里挪出来，比任何手动优化都实在。

18.4 优化二：patchFlag —— 靶向更新

第 16 章的 patchElement 要 diff 完整的 props 对象。但编译器在编译期就知道哪些属性是动态的： 

// 模板：<div :class="cls" :id="id">文本不变</div>
// 编译产物（示意）：
h("div", { class: _ctx.cls, id: _ctx.id }, "文本不变",
  3 /* CLASS | ID */);      // ← 只有 class 和 id 是动态的！

// patch 时：
if (patchFlag & PatchFlags.CLASS)  只更新 class
if (patchFlag & PatchFlags.ID)    只更新 id
// 其余属性：看都不看 —— diff 一个对象的成本变成了 diff 两个布尔位

这就是 Vue3 官方 benchmark 比 Vue2 快的原因之一：运行时把编译期攒的情报花掉。 React 没有编译层（JSX 太自由），只能全量 diff —— 这是两种框架哲学的分水岭。

18.5 优化三：Block Tree / dynamicChildren

有了 patchFlag 再往前一步：patch 为什么还要递归整棵树？ 编译期把所有「动态节点」收集到一个扁平数组（dynamicChildren）里， 更新时只遍历这个数组 —— 静态的整棵子树被完全绕过：

div（静态） ├─ ul（静态） │  └─ li {{item}} ⭐
传统 patch：递归访问每个节点（含静态）
Block: [li⭐] → Block 模式：只有 1 个动态节点，只 patch 它

为什么叫 Block？模板里出现结构性指令（v-if/v-for）时会「开新块」，块的边界处理结构变化 —— 细节较多，记住结论即可：

编译器把「哪里会变」提前告诉了运行时，运行时因此能跳过一切不会变的地方。Vue3 性能的三大支柱：静态提升、patchFlag、Block Tree。

18.6 cacheHandlers：事件也提升

// 模板：<button @click="count++">
// 编译产物（开启 cacheHandlers 后）：
const _cache = [];
function render(_ctx) {
  return h("button", {
    onClick: _cache[0] || (_cache[0] = ($event) => (_ctx.count++)),
  }, "点我");
}
// 没缓存：每次渲染生成新函数 → props diff 认为变了 → 触发 patchProp
// 有缓存：同一函数引用 → diff 短路 → 配合第 13 章 invoker，事件彻底零开销

看到没 —— 第 13 章的 invoker + 第 16 章的 props diff + 编译器的 cacheHandlers，三章的知识在这里拧成了一股绳。

自测一下：编译优化

1. 为什么 v-if 会导致「开新 Block」，而 v-show 不会？

答案：
1. v-if 改变结构（节点存在与否），dynamicChildren 的扁平数组无法表达「这块结构可能整个消失」，必须在分支处切块、走传统递归 patch；v-show 只改 style.display，结构恒定，仍可走 Block 快路径。

性能优化：源码视角

学完源码，性能优化不再是背清单 —— 每一条优化你都能说出「为什么有效」。 本章把全书知识串成 8 个实战招式，每招标注原理出处。

19.1 八招速查表

招式适用场景为什么有效（原理）
① 大数据用 shallowRef 万行表格、图表数据 跳过深层代理（第 11 章）：10 万对象 × 每对象的 get 拦截全免
② 第三方实例 markRaw Three.js / Map / 类实例 深层代理对它们毫无意义还破坏 === 判等（第 11/12 章）
③ 昂贵计算用 computed 过滤/排序/聚合 dirty 标记缓存：依赖不变不重算（第 8 章），还能链式传播
④ 精确 watch source 监听深层对象里一个字段 () => obj.a 只 track 一个属性（第 9 章）；watch(obj) 的 traverse 全树点名
⑤ v-memo 缓存子树 昂贵的列表项 依赖数组不变 → 直接复用旧 vnode，diff 整段跳过（第 15 章 === 短路的放大版）
⑥ 稳定的 key 一切列表 LIS 命中率最大化 → DOM 移动最少（第 16 章）；index 当 key 是灾难
⑦ 静态内容外提 v-for 内的固定部分 静态提升只提升「模板级」静态节点（第 18 章）—— 手动外提才算数
⑧ v-show 替 v-if（高频切换） tab、弹层 v-if 动结构 → 开新 Block 走慢路径 + 组件重建（第 18 章）；v-show 只改 style

19.2 招式详解：v-memo —— 手动挡的缓存

<!-- 依赖数组 [item.id, item.selected] 不变 → 整个 <li> 的 vnode 直接复用，diff 跳过 -->
<li v-for="item in list" :key="item.id" v-memo="[item.id, item.selected]">
  <expensive-avatar :id="item.id" />
  <span>{{ item.name }}</span>
</li>

// 编译后的等价逻辑（思想）：
const memo = oldVNode.memo;
if (memo && memo.every((v, i) => v === newDeps[i])) {
  return oldVNode;         // 一模一样的 vnode → patch 处 oldVNode === vnode 短路
}
newVNode.memo = newDeps;

注意边界：v-memo 缓存的是「渲染结果」，依赖数组里漏写的字段变了也不会刷新 —— 它是性能的手术刀，也是正确性的自留地，慎用但好用。

19.3 一个完整的优化案例走查

需求：渲染 5000 行员工表，支持「选中行高亮 + 部门筛选」。烂写法 vs 源码视角写法：

const employees = reactive(fetch5000Rows());   // 5000 行全部深层代理（招式①✗）

const selected = reactive(new Set());          // 响应式 Set 存选中态，行级更新

// 模板里：
// <tr v-for="(emp, i) in employees" :key="i"          ← index 当 key（招式⑥✗）
//    :class="{ active: selected.has(emp) }">
//   <td v-for="col in 20Columns">{{ emp[col] }}</td> <!-- 10 万个动态绑定 -->

// 点击一行 → selected.has 触发 → 所有 5000 行全部重渲染（没有组件边界剪枝）
// 更新路径：5000 行 × 20 列的 patch —— 每次点击 10 万次属性检查
// ① 数据：shallowRef，整体替换（不可变更新）
const employees = shallowRef(fetch5000Rows());
function toggleSelect(id) {
  employees.value = employees.value.map(e =>
    e.id === id ? { ...e, selected: !e.selected } : e);
}

// ② 派生：computed 缓存筛选结果（依赖不变不重算）
const filtered = computed(() => employees.value.filter(e => match(e, keyword)));

// ③ 行组件化：props 是 { emp } 单对象
const Row = {
  props: ["emp"],
  template: `<tr :class="{ active: emp.selected }">…</tr>`,
};

// 模板：<Row v-for="emp in filtered" :key="emp.id" />
//   ↑ 稳定 key + 行级组件边界：shouldUpdateComponent 浅比较 emp 引用
//   → 未变化的行直接跳过（第 17 章的剪枝）

效果对比：点击一行的更新成本从「10 万次属性检查」降到「1 个新数组 + 1~2 行的组件重渲染」。 没有一行代码是玄学 —— 每一步都对应你学过的某一章。

🧠 性能优化的第一性原理
全书所有优化殊途同归于一句话：给「不变的东西」发放免死金牌。
静态提升（vnode 不变）、computed（结果不变）、v-memo（子树不变）、shouldUpdateComponent（props 不变）、 LIS（相对顺序不变）、invoker（监听器壳不变）。框架作者和你玩的是同一个游戏：识别不变量，跳过它。

1. v-for="item in list" 的 list 是 shallowRef，用 list.value.push(x) 后界面没更新 —— 给出两种修复及原理？
2. 为什么「行组件化 + 稳定 key」比「一个大模板渲染全表」快？

答案：

2. 大模板 = 每次更新 patch 整棵 10 万绑定的树；行组件化后每行是独立组件，shouldUpdateComponent 用引用相等短路 —— 未变的行连 render 都不执行（第 17 章），diff 天然按行分治。

🟢 基础篇（答不出建议回炉）

Q1. Vue3 响应式的整体原理？用一句话 + 一张图回答。
要点：Proxy 拦截读写（第 3 章）→ 读时 track、写时 trigger（第 4/5 章）→ effect 重跑驱动视图。 高分画图：WeakMap(target) → Map(key) → Map(effect→trackId) 三层名册。
Q2. reactive 和 ref 的区别？分别什么时候用？
要点：reactive = Proxy 代理对象（只有对象能用，第 3 章）；ref = 带 getter/setter 的盒子（原始值唯一方案，第 7 章）， 内部 toReactive 套娃。选用心法见第 12 章（默认 ref，组合状态 reactive+toRefs）。
Q3. 为什么模板里不用写 .value，script 里要写？
要点：setup 返回值/模板上下文经过 proxyRefs（第 7 章）：get 时自动拆箱 ref.value、set 时自动装箱。两条通道，一套语义。
Q4. Vue2 和 Vue3 响应式的差异？
要点：defineProperty → Proxy（第 3 章对比表）：新增属性/数组索引/删除全支持、惰性深层代理、多属性统一拦截。 附加分：依赖结构从 dep.subs(watcher 数组) 变为三层 Map + trackId 版本号清理（第 6 章）。
Q5. computed 和 watch 的区别与取舍？
要点：computed = 派生值（返回值、有缓存、不能异步，第 8 章脏标记）；watch = 副作用（不返回值、能异步、有 onCleanup 处理竞态，第 9 章）。同源：都是 ReactiveEffect + 自定义 scheduler（第 5 章的表格）。
Q6. v-if 和 v-show 的区别？（要求源码级答案）
要点：不止「销毁 vs display:none」：v-if 改变结构 → 编译期开新 Block、走传统递归 patch（第 18 章）；v-show 编译成 style patchFlag，走快路径。高频切换用 v-show 的深层原因在此。

🟡 进阶篇（拉开差距区）

Q7. 为什么 Proxy 必须配合 Reflect.get(target, key, receiver)？
要点：receiver 矫正 getter 里的 this 指向代理，否则 getter 内部的属性读取不经过代理 → 依赖静默丢失（第 3 章有完整实验）。能举 aliasName 例子 = 满分。
Q8. 分支切换后旧依赖怎么清理？讲讲 Vue 3.4 的优化。
要点：老方案全删重建；3.4 用 _trackId 版本号（本轮新收集识别）+ _depsLength 双指针（原地 diff），只清理真正过期的依赖（第 6 章）。能类比 vnode diff 的「增量更新」哲学 = 加分。
Q9. watch 传对象时为什么要 traverse？直接 watch(() => obj) 为什么不行？
要点：effect 里必须有「属性读取」才有 track；只返回对象引用 = 零收集。traverse 深度遍历 = 逐属性点名（第 9 章）。附加分：seen 集合防循环引用。
Q10. 组件更新流程：父组件数据变了，子组件一定会重渲染吗？
要点：不一定。updateComponent 复用组件实例，shouldUpdateComponent 做 props 浅比较（Object.is），没变则只吃掉新 vnode 跳过重渲染（第 17 章）。子组件内部状态（自己的响应式数据）才会驱动它自身的 update effect。
Q11. 为什么 Vue 的批量更新能合并多次修改？和 nextTick 什么关系？
要点：trigger → scheduler → queueJob（Set 去重）→ 微任务 flushJobs（第 17 章）：同步代码全部跑完后才统一 patch，一组件一次。nextTick = 把回调排到 flushJobs 之后。能画出事件循环时序图 = 加分。
Q12. 为什么列表不能用 index 当 key？讲讲 diff 的 LIS。
要点：key 是身份不是座位（第 16 章）。index 平移 → 身份错位 → 错误复用 + 大面积移动。LIS：newIndexToOldIndex 中最长递增子序列的节点保持不动，其余 insert —— 数学上最少移动。能白板写出五步预处理 = 强。
Q13. props 为什么是 shallowReadonly？子组件改 props 深层属性会怎样？
要点：props 所有权在父组件，锁写 + 不重复代理（第 11 章）。第一层 set 被拦截并告警；深层（shallow 之外）能改成功但强烈不推荐 —— 正确姿势是 emit 事件让父组件改。
Q14. 事件绑定 @click 每次渲染都换新函数，为什么不会频繁 addEventListener？
要点：两层防线：编译期 cacheHandlers 缓存内联函数引用（第 18 章）；运行期 invoker 壳子常驻、只替换 invoker.value（第 13 章）。两层配合 = 事件更新零 DOM 调用。
