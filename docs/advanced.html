ref：给原始值一个家

「为什么要写 .value？」大概是 Vue3 被抱怨最多的问题。 读完本章你会发现：.value 不是麻烦，它是响应式系统能覆盖「数字、字符串」的唯一门票。

7.1 Proxy 的盲区

let num = 18;
const proxyNum = new Proxy(num, {});   // 💥 TypeError: 不能代理原始值

// Proxy 的本质是「拦截对对象的属性访问」
// 数字/字符串/布尔值没有属性访问这个动作 → 无从拦截 → 无法追踪

reactive 只能守护对象。可是 count++ 这种场景天天有，怎么办？ Vue 的答案：既然原始值装不上「门禁」，那就给它盖一座房子（对象），把值锁进 .value 这个房间里 —— 房子是对象，能装门禁了： 

class RefImpl<T = any> {
  _value: T                        // 缓存的值（对象值存的是 reactive 代理）
  private _rawValue: T             // 原始值（比较用，永远是「裸」的）
  dep: Dep = new Dep()             // ⭐ 专属 dep：一个 Dep 实例，不用三层名册
  public readonly [ReactiveFlags.IS_REF] = true
  public readonly [ReactiveFlags.IS_SHALLOW]: boolean = false

  constructor(value: T, isShallow: boolean) {
    this._rawValue = isShallow ? value : toRaw(value)
    this._value = isShallow ? value : toReactive(value)   // 对象值 → 转成 reactive（ref 也能套娃！）
    this[ReactiveFlags.IS_SHALLOW] = isShallow
  }

  get value() {
    this.dep.track()               // 读 .value → 登记到专属 dep（和普通 track 同一套 Link 机制）
    return this._value
  }

  set value(newValue) {
    const oldValue = this._rawValue
    // shallowRef、新值本身是 shallow/readonly → 不做深层转换
    const useDirectValue =
      this[ReactiveFlags.IS_SHALLOW] || isShallow(newValue) || isReadonly(newValue)
    newValue = useDirectValue ? newValue : toRaw(newValue)
    if (hasChanged(newValue, oldValue)) {          // ⭐ Object.is 比较（NaN 安全，5.2）
      this._rawValue = newValue
      this._value = useDirectValue ? newValue : toReactive(newValue)   // ⭐ 新值也要响应式化！
      this.dep.trigger()           // → version++ → notify（5.6 同一条管线）
    }
  }
}

为什么 ref 的 dep 更简单？

reactive 需要三层名册，是因为「一个对象有 N 个属性，每个属性各自有粉丝」。 而 ref 只有一个属性（.value），一个 ref 配一个 dep 就够了， 直接挂在实例上（this.dep），读写都少走两层 Map，性能更好。

💡 比喻时间：储物柜
reactive 对象是一整面储物墙（每个格子 = 一个属性，各有各的登记表，所以要三层索引）； ref 是单个带锁储物柜（就一个格子 .value，登记表直接贴柜门上）。

7.2 toRef / toRefs：解构救星

用 reactive 时有个大坑：解构会丢失响应式 —— 解构相当于把值「抄」出来一份普通变量，和原对象断联。 toRefs 的解法是不抄值，改发「引用卡片」： 

class ObjectRefImpl<T extends object, K extends keyof T> {
  public readonly [ReactiveFlags.IS_REF] = true
  private readonly _raw: T
  private readonly _key: K
  private readonly _shallow: boolean

  constructor(private readonly _object: T, key: K, private readonly _defaultValue?) {
    this._key = key
    this._raw = toRaw(_object)
    // 判断「读到的值要不要自动脱 ref 壳」：沿代理链逐层检查 shallow
    let shallow = true
    let obj = _object
    if (!isArray(_object) || !isIntegerKey(this._key)) {
      do { shallow = !isProxy(obj) || isShallow(obj) } while (shallow && (obj = obj[ReactiveFlags.RAW]))
    }
    this._shallow = shallow
  }

  get value() {
    let val = this._object[this._key]   // 读：实时去原对象拿
    if (this._shallow) val = unref(val) // 浅层代理上的 ref 要手动脱壳
    return (this._value = val === undefined ? this._defaultValue! : val)
  }

  set value(newVal) {
    if (this._shallow && isRef(this._raw[this._key])) {
      const nestedRef = this._object[this._key]   // 写到 ref 头上 → 走 ref 的 setter
      if (isRef(nestedRef)) { nestedRef.value = newVal; return }
    }
    this._object[this._key] = newVal    // 写：实时写回原对象
  }

  get dep(): Dep | undefined {          // 卡片也能被依赖追踪：
    return getDepFromReactive(this._raw, this._key)  // 透传源属性的 dep
  }
}

export function toRefs<T extends object>(object: T) {
  const ret: any = isArray(object) ? new Array(object.length) : {}
  for (const key in object) {
    ret[key] = propertyToRef(object, key)   // 整包对象 → 一沓卡片
  }
  return ret
}

注意 ObjectRefImpl 的 get/set 本质上是转发器 —— 真正的登记发生在 this._object[this._key] 这次「读取原响应式对象」的时候。 它自己的 get dep() 只是帮依赖系统找到「源属性那张名册」—— 卡片和源属性共享同一本账。代理的代理，轻装上阵。

7.3 proxyRefs：模板里为什么不用写 .value

setup 返回的对象会被 proxyRefs 包一层：

const shallowUnwrapHandlers: ProxyHandler<any> = {
  get: (target, key, receiver) =>
    key === ReactiveFlags.RAW
      ? target
      : unref(Reflect.get(target, key, receiver)),   // 读到 ref？自动帮你拆箱！
  set: (target, key, value, receiver) => {
    const oldValue = target[key]
    if (isRef(oldValue) && !isRef(value)) {
      oldValue.value = value                // 写到 ref 身上？自动装箱！
      return true
    } else {
      return Reflect.set(target, key, value, receiver)
    }
  },
}

export function proxyRefs<T extends object>(objectWithRefs: T) {
  return isReactive(objectWithRefs)
    ? objectWithRefs                        // 已经是 reactive：自带脱壳，不重复包
    : new Proxy(objectWithRefs, shallowUnwrapHandlers)
}

所以 count 在模板里直接用，count = 5 直接赋值 —— 不是魔法，是 proxyRefs 在 get/set 里默默帮你 .value 了。 这也是为什么 script 里必须写 .value 而模板里不用：两套访问通道而已。

7.4 官方 ref 的三个工程细节

官方 ref.ts 里有三个值得咀嚼的细节，每一个都对应一类真实 bug：

细节官方做法为什么
dep 的形态3.5 起是一个 Dep 类实例，类字段直接初始化（3.2~3.4 曾是「第一次被 track 才惰性创建」）统一全家的 dep 结构；sc 订阅者计数归零时自动销户，防泄漏
新值的响应式化this._value = toReactive(newValue) —— 每次赋值都过一遍保证 ref(obj).value.x 每次替换后仍是响应式（见 7.5 的坑）
读写分离两本值_rawValue（比较用）与 _value（返回用）分开存比较要在「裸值」上做（代理 !== 原对象），返回要给「代理」—— 一份值两个视图
⚠️ 模板自动脱壳只对「顶层」生效
setupState 被 proxyRefs 包过（7.3），所以模板里 {{ count }} 自动脱壳； 但嵌套对象里的 ref 不脱壳：{{ state.count }}（count 是 ref）会打印出 RefImpl 对象 —— 必须写 {{ state.count.value }}。 原理：proxyRefs 只代理顶层 get；ref 挂在普通对象内部时，读它的是普通 get，没人替你脱壳。 官方文档 Top 3 新手困惑之一 —— 现在你从实现层面理解它了。

7.5 官方 setter 防的那个坑：替换对象值后失去响应

看官方 setter 里那行 this._value = toReactive(newValue) —— 为什么「再过一次 toReactive」值得单独讲？因为少了它就是一个经典 bug：

// 反面教材：set 里直接 this._value = newValue
const r = ref({ name: "a" });
r.value = { name: "b" };
r.value.name = "c";   // 期望页面更新，实际不更新 ✗
// 原因：新的 { name: "b" } 没有被 reactive() 包一层，深层读取不经过 Proxy

// 官方的防御（ref.ts 原文）：
this._value = toReactive(newValue);   // 对象 → 代理；原始值 → 原样
// toReactive 就是 reactive.ts 里那三行：isObject ? reactive(v) : v

这类「替换值之后响应链断裂」的问题，标准防法就是官方这样在 setter 里重新响应式化 —— 配上测试用例才算闭环：

it("should keep reactivity of replaced object value", () => {
  const r = ref({ name: "a" });
  r.value = { name: "b" };
  expect(isReactive(r.value)).toBe(true);   // ⭐ 断言新值仍是响应式
});

7.5 ref 家族的「一行 API」们

RefImpl 本体是全家族唯一的难点，其余 API 几乎都是一行成本的便利层：

API实现用途
isRef(v)!!(v && v.__v_isRef)类型收窄、proxyRefs 的判断依据
unref(v)isRef(v) ? v.value : v「是 ref 就脱壳，不是就原样」—— 组合式函数消费端万能钥匙
toRef(obj, k)ObjectRefImpl（读写直接透传到 obj[k]）把对象属性「变成 ref 视图」，与源属性永远同步
toRefs(obj)遍历逐个 toRef解构不丢响应式（7.2 的场景）
🧠 toRef 和 ref 的本质区别
ref(0) 创建新的存储（值锁在自己柜子里，互不影响）； toRef(obj, 'count') 不创建存储 —— 它是一扇窗户，读写都透传给原对象属性。 所以 toRef 永远和源同步，ref 永远和源无关。判断「要不要同步」就是两者的选型标准。
自测一下：ref 机制

1. ref(obj) 和 reactive(obj) 得到的东西本质区别是什么？
2. const {x} = toRefs(state) 之后 x = 5 为什么不生效？

答案：
1. ref 是「把值装进带 getter/setter 的盒子」，依赖盒子的一个专属 dep；reactive 是「给对象雇 Proxy 管家」，依赖三层名册。ref(obj) 内部其实会调 toReactive，两者对对象会殊途同归。
2. x 是一张 ObjectRefImpl「卡片」（也是个 ref），直接赋值只是在换卡片本身，必须 x.value = 5 才会写回 state.x。

computed：聪明的偷懒

computed 的全部哲学浓缩成四个字：能不算就不算。 它靠「版本号对账」统治了整个缓存王国（2.5 节的记账思想在这里全面展开），而且 —— 你已经认识它的全部零件了。

8.1 比喻先行：冰箱里的牛奶

你想喝牛奶（读取 computed），有两种策略：每喝一次就去超市买一次（每次重新计算），或者看一眼冰箱 —— 牛奶还在保质期（不脏）就直接喝，过期了（脏）才去买新的。 「保质期状态」就是 dirty 标记；「牛奶过期」= 依赖变了。

8.2 源码：ComputedRefImpl —— computed 自己就是「订阅者」

export class ComputedRefImpl<T = any> implements Subscriber {
  _value: any = undefined           // 缓存的结果（牛奶）
  readonly dep: Dep = new Dep(this) // 自己的 dep，并告诉它「我是 computed」
  deps?: Link = undefined           // 我订阅上游的登记线（Link 双向链）
  depsTail?: Link = undefined
  flags: EffectFlags = EffectFlags.DIRTY   // 初始：没算过 = 脏
  globalVersion: number = globalVersion - 1
  isSSR: boolean
  next?: Subscriber = undefined     // batch 队列指针
  effect: this = this               // 兼容旧插件（3.5 起不再包 ReactiveEffect）

  constructor(
    public fn: ComputedGetter<T>,              // 你的 getter
    private readonly setter: ComputedSetter<T> | undefined,
    isSSR: boolean,
  ) {}

  notify(): true | void {           // 上游变了 → 被 dep.notify 叫到
    this.flags |= EffectFlags.DIRTY          // ① 只标脏，绝不重算！
    if (!(this.flags & EffectFlags.NOTIFIED) && activeSub !== this) {
      batch(this, true)                      // ② 登记进「computed 批队列」
      return true                            // ③ 返回 true → 调用方继续传播我的 dep
    }
  }

  get value(): T {
    const link = this.dep.track()      // ① 谁读我，登记谁（和普通 ref 同一套机制）
    refreshComputed(this)              // ② 该算才算（见下）
    if (link) link.version = this.dep.version
    return this._value                 // ③ 没脏 → 直接喝（零计算）
  }

  set value(newValue) {
    if (this.setter) this.setter(newValue)   // 可写 computed（{get,set} 传参那个）
    else if (__DEV__) warn('Write operation failed: computed value is readonly')
  }
}

/*@__NO_SIDE_EFFECTS__*/
export function computed<T>(getterOrOptions, debugOptions?, isSSR = false) {
  let getter: ComputedGetter<T>
  let setter: ComputedSetter<T> | undefined
  if (isFunction(getterOrOptions)) {
    getter = getterOrOptions                      // 只传函数 → 只读
  } else {
    getter = getterOrOptions.get                  // 传 {get,set} → 可写
    setter = getterOrOptions.set
  }
  const cRef = new ComputedRefImpl(getter, setter, isSSR)
  return cRef as any
}

官方 3.5 里 computed 的身份变了：它不再内部包一个 ReactiveEffect，自己就直接实现 Subscriber 接口（deps 链、flags、notify —— 和 ReactiveEffect 同款）。 它既是 dep 的订阅者（订阅上游），又拥有自己的 dep（被下游订阅）—— 双面身份写进了同一个类。 真正的「要不要重算」判决在 refreshComputed： 

export function refreshComputed(computed: ComputedRefImpl): undefined {
  if (computed.flags & TRACKING && !(computed.flags & DIRTY)) return  // 干净 → 秒回
  if (computed.globalVersion === globalVersion) return                // ⭐ 全局快路径：
  computed.globalVersion = globalVersion                              //   世界没变过，谁都别算
  if (!computed.isSSR && computed.flags & EVALUATED && !isDirty(computed)) {
    return                              // 逐条对账：没有一条 link 的版本对不上 → 缓存仍然新鲜
  }
  computed.flags |= RUNNING
  const dep = computed.dep
  const prevSub = activeSub
  activeSub = computed                  // ⭐ getter 执行期间，computed 是「当前订阅者」
  try {
    prepareDeps(computed)               // 旧线置 -1（第 6 章）
    const value = computed.fn(computed._value)   // ⭐ 真正执行你的 getter（全站最懒的一行）
    if (dep.version === 0 || hasChanged(value, computed._value)) {
      computed.flags |= EVALUATED
      computed._value = value           // 缓存新值
      dep.version++                     // ⭐ 值真变了才记账（值没变不涨，下游连重跑都省）
    }
  } finally {
    activeSub = prevSub
    cleanupDeps(computed)
    computed.flags &= ~RUNNING
  }
}

8.3 三方博弈：一次完整的「账单」

computed 同时扮演两个角色，看这张关系图：

count（ref） 被依赖 double = computed(...) 被依赖 effect / 模板
computed 对上是「粉丝」（订阅 count），对下是「偶像」（被 effect 订阅）—— 双面身份

现在推演 count.value++ 会发生什么：

  1. count 的 dep 触发 → notify 沿订阅者链找到 computed → 走到 ComputedRefImpl.notify() → 只标脏（DIRTY）+ 进 batch，绝不重算；notify 返回 true → 继续传播 computed 自己的 dep
  2. 下游 effect 重跑 → 执行渲染 → 过程中读到 double.value
  3. refreshComputed：DIRTY 已标 → 逐条对账 → 真脏 → 此刻才执行 getter （最晚一秒是一秒的懒）→ 缓存新值；值没变就不涨 version
🧠 精妙之处：懒计算的传播链
脏标记像多米诺骨牌一样传播：count 变 → double 标脏 → 下游 effect 重跑 → 读 double → 才触发计算。 如果下游永远不来读，getter 永远不执行。一个 computed 依赖另一个 computed 时同理 —— 骨牌可以无限接力，计算永远推迟到「真正需要」的那一刻。这就是「读取时结账」算法的威力。

8.5 computed 三问三答：写入、级联与 methods 对比

① computed 能被写入吗？能 —— computed({ get, set }) 传对象时， fullName.value = "李 四" 会走 setter（8.2 源码里的 isFunction(getterOrOptions) 分支之外的那条路），setter 里你负责反写上游数据。 只传函数时 setter 是 undefined，写入无效（开发模式警告 readonly）。

② computed 互相依赖会怎样？

price（响应式） → total = computed(price × count) → taxed = computed(total × 1.13)
price 变 → total 标脏 → taxed 标脏（级联记账）。读 taxed 时：taxed 重算 → 读 total → total 重算，一环扣一环但每环只算一次

注意求值顺序是从下游往上游倒推的：真正触发重算的永远是「有人读」，而不是「数据变」—— 这就是脏标记体系的精髓（第 2.5 节）。

③ computed 和普通函数调用（methods）有什么区别？

维度computed普通函数
缓存依赖不变 → 直接复用上次结果每次调用都重新执行
依赖追踪自动收集 getter 里读到的响应式数据无（调用它的渲染 effect 代为收集）
适合由数据派生的值（模板里反复用）事件处理、每次都必须执行的逻辑
💡 一句话选择法
「这个值会不会在多处反复使用、且只在依赖变化时才需要变？」—— 是，用 computed； 「这是一个动作」—— 用函数。把 computed 当函数用（在模板里调用它）是最常见的性能失误： {{ fullName() }} 每次渲染都会重算，{{ fullName }} 才吃缓存。

8.5 computed 的三条使用纪律

  1. getter 必须是纯函数：不写异步请求、不改外部变量。因为「何时重算」由下一次有人读决定 —— 副作用会随机引爆，且丢失重算时机时毫无报错。
  2. 别依赖非响应式来源：computed(() => Date.now() + obj.x) 里， 脏标记只认 obj.x 的变化 —— Date.now() 变了永远不会让缓存失效，每次读到的是「上次结的旧账」。
  3. setter 慎用：v-model 绑 computed 是合法好场景（表单格式化）， 但业务状态流尽量保持「源数据 → computed 派生」单向 —— 可写 computed 会让数据流向难追。

8.6 教学简化版 vs 官方 computed：三点差异

维度教学简化版官方（3.5）
身份computed 内部藏一个 ReactiveEffectComputedRefImpl 自己就是「订阅者」（Subscriber），不再包 effect（保留 effect 字段只为兼容旧插件）
脏判定两档布尔：0 / 4（脏/干净）版本号对账：逐条比对 link.dep.version !== link.version，外加全局 globalVersion 快路径（2.5 节）
重算时机读 .value 时发现脏才重算同款「读取时结账」，且算完值没变就不涨 version（hasChanged 才 +1）—— 下游连重跑都省了
🧠 思想同源，官方把「懒」推到极致
两版的心脏都是同一个：读取时才结账 + 值没变就不打扰下游。 官方多做的一切（链表、版本计数、globalVersion 快路径、job 化）都是在回答同一个问题： 「能不能在保证正确的前提下，更少地做一件事」。这是所有性能优化的元问题。

再往下钻一层：computed 套 computed 时的求值顺序（面试偶尔追问）——

读 total（C2） → C2.dirty？是 → 跑 C2.effect → C2 的 getter 里读 C1.value → C1.dirty？是 → 跑 C1.effect → 读源 → track
深度优先、按需求值：上游永远「被下游拽着算」，没有任何一步提前算

结合 2.5 的版本号记账理解官方行为：C1 的 getter 重算后值真变了，它的 dep.version 才 +1， 才会把 C2 标脏；真正读 C2 时 isDirty 再逐条对账 —— 若 C1 只是「被标脏」但重算后值没变， version 不增长，C2 直接复用缓存，连整条链的重算都省了（这正是 3.5 修掉的 「computed 值未变仍触发下游」顽疾）。教学简化版两档脏标记在链式场景会多算一次，但主干正确。

⚠️ 一条红线：computed 里不要改自己依赖的数据
computed 的求值期间也是「当前订阅者」（refreshComputed 里 activeSub = computed）。getter 里写 count.value++ 就是「读的途中改」—— notify 的 RUNNING 防线拦得住直接死循环， 但仍会触发「算一次改一次」的隐式循环，并最终撞上第 23 章的 100 层递归上限警告。 纪律一句话：getter 纯函数，一切变更放事件/回调里。

9.1 三种形态，归一为 getter

watch 的 source 可以是响应式对象、ref、函数。官方 watch.ts（3.5 起从 apiWatch.ts 改名并移入 reactivity 包）第一步就是把它们统一成 getter：

export function watch(source, cb?, options: WatchOptions = EMPTY_OBJ): WatchHandle {
  const { immediate, deep, once, scheduler, augmentJob, call } = options

  const reactiveGetter = (source: object) => {
    if (deep) return source                                  // deep=true → 后面 traverse 全量点名
    if (isShallow(source) || deep === false || deep === 0)
      return traverse(source, 1)                             // 浅层：只点名第一层
    return traverse(source)                                  // 默认：深度点名（见 9.2）
  }

  let getter: () => any
  let forceTrigger = false
  if (isRef(source)) {
    getter = () => source.value                    // 形态① ref → 直接读 .value
    forceTrigger = isShallow(source)               // shallowRef：引用没变也可能内容变了
  } else if (isReactive(source)) {
    getter = () => reactiveGetter(source)          // 形态② 响应式对象 → 遍历它
    forceTrigger = true                            // 遍历拿到的是同一个对象 → 靠 forceTrigger 强制比较
  } else if (isArray(source)) {
    // 形态③ 多源数组 → getter 返回「各自取值」的数组
    getter = () => source.map(s => isRef(s) ? s.value : isReactive(s) ? reactiveGetter(s) : s())
  } else if (isFunction(source)) {
    // 形态④ 函数：有 cb 就是纯 getter；没 cb（watchEffect）→ 包一层清理/指针管理
    getter = cb ? source : () => { /* 清理 + 切 activeWatcher + source(boundCleanup) */ }
  }

  if (cb && deep) {
    const baseGetter = getter
    const depth = deep === true ? Infinity : deep  // deep: 3 → 只点 3 层
    getter = () => traverse(baseGetter(), depth)
  }
  ...
}

9.2 traverse：为什么要「摸一遍」对象？

watch(obj, cb) 时，如果 getter 只返回 obj 本身，effect 里根本没有发生任何属性读取 —— 不读属性就没有 track，那改任何属性都不会触发回调！traverse 的作用就是把对象每个属性都读一遍， 人为制造 track： 

export function traverse(value: unknown, depth = Infinity, seen?: Map<unknown, number>) {
  if (depth <= 0 || !isObject(value) || (value as any)[ReactiveFlags.SKIP]) {
    return value
  }
  seen = seen || new Map()
  if ((seen.get(value) || 0) >= depth) return value   // 防循环引用：摸过的不再摸
  seen.set(value, depth)
  depth--
  if (isRef(value)) {
    traverse(value.value, depth, seen)
  } else if (isArray(value)) {
    for (let i = 0; i < value.length; i++) traverse(value[i], depth, seen)
  } else if (isSet(value) || isMap(value)) {
    value.forEach((v) => traverse(v, depth, seen))
  } else if (isPlainObject(value)) {
    for (const key in value) traverse(value[key], depth, seen)
    for (const key of Object.getOwnPropertySymbols(value)) {
      if (Object.prototype.propertyIsEnumerable.call(value, key)) traverse(value[key], depth, seen)
    }
  }
  return value
}
💡 一句话记住
watch 响应式对象 = 「先把全家福每个人都点一遍名，以后谁动了都通知我」。 traverse 就是点名册。seen 集合防止 obj.self = obj 这种环把点名变成死循环 （官方用 Map 记「每个对象摸到第几层」，比教学简化版的 Set 更精确）。

9.3 job：回调的三个入场券

const job = (immediateFirstRun?: boolean) => {
  if (
    !(effect.flags & EffectFlags.ACTIVE) ||      // 已停止 → 不再触发
    (!effect.dirty && !immediateFirstRun)        // ⭐ 脏检查：依赖没变直接跳过
  ) {
    return
  }
  if (cb) {
    // watch(source, cb)
    const newValue = effect.run()                // 重新执行 getter 拿新值
    if (
      immediateFirstRun || deep || forceTrigger ||
      (isMultiSource
        ? (newValue as any[]).some((v, i) => hasChanged(v, oldValue[i]))
        : hasChanged(newValue, oldValue))
    ) {
      if (cleanup) cleanup()                     // 先清理上一轮注册的钩子
      const currentWatcher = activeWatcher
      activeWatcher = effect                     // ⭐ 回调执行期间：activeWatcher = 自己

        cb!(newValue, oldValue, boundCleanup)    // 把新旧值交给用户
      } finally {
        activeWatcher = currentWatcher
      }
      oldValue = newValue                        // 滚动更新
    }
  } else {
    effect.run()                                 // watchEffect：没有回调，直接跑
  }
}

effect = new ReactiveEffect(getter)
effect.scheduler = scheduler ? () => scheduler(job, false) : job   // ⭐ scheduler = job
boundCleanup = fn => onWatcherCleanup(fn, false, effect)           // 注册进 cleanupMap
cleanup = effect.onStop = () => { /* stop 时统一执行 cleanupMap 里的钩子 */ }

  if (immediate) job(true)                     // immediate：先斩后奏，立刻执行一次

} else {
  effect.run()
}

注意 watch 的 scheduler 是 job —— 数据变了不是重跑 getter 就完了， 而是先过 effect.dirty 脏检查，再执行你的回调。 这就是第 5 章那张 scheduler 表格里 watch 那一行的落地。

9.4 onCleanup：解决「过时响应」竞态

经典场景：搜索框输入 "ab"，请求 A 发出；马上又输入 "abc"， 请求 B 发出。如果 A 比 B 后返回，页面就会显示旧结果 —— 竞态 bug。onCleanup 的解法：

watch(keyword, async (newVal, oldVal, onCleanup) => {
  let expired = false;

  const result = await api.search(newVal);
  if (!expired) renderList(result);         // 过期了就丢弃，只有最新一轮能上屏
});

effect 嵌套与 effectScope

组件里面还有组件，effect 里面还有 effect。当它们层层嵌套时， 全局唯一的 activeSub 指针会不会乱套？ 本章回答这个问题，并顺手学会 Vue 生态里批量清理的神器 effectScope。

10.1 问题：嵌套 effect 的「身份错乱」

想象组件树：父组件渲染时跑 outer effect，渲染到子组件时又要跑 inner effect：

effect(() => {            // outer：父组件渲染
  renderParent();
  effect(() => {          // inner：子组件渲染（在 outer 执行期间创建）
    renderChild();
  });                     // ⚠️ inner 结束后，outer 还没跑完！
  renderParentRest();     // 这些读取应该算在 outer 头上
});

如果 activeSub 是「设置后不管」的普通全局变量，inner 跑完把它设成了自己， 之后 outer 剩余代码的依赖就会全部错误地登记到 inner 名下 —— 数据一变，错的 effect 重跑。

10.2 解法：暂存-还原（隐式借用了函数调用栈）

回看第 2 章 run() 的代码，答案早已埋下：

run(): T {
  ...
  const prevEffect = activeSub;    // ① 暂存「上一层」是谁（压栈）
  const prevShouldTrack = shouldTrack;
  activeSub = this;                // ② 指针换成自己
  shouldTrack = true;
  try {
    return this.fn();              // ③ 执行（里面可能再嵌套下一层）
  } finally {
    cleanupDeps(this);             //    ...
    activeSub = prevEffect;        // ④ 还原（弹栈）
    shouldTrack = prevShouldTrack;
  }
}

①④ 配合就是一次手动压栈/弹栈 —— 只是借用了 JS 函数调用栈本身的递归结构来保存 prevEffect， 不需要真的维护一个数组。嵌套多深都没关系：每层 run 都会保存/恢复自己的「上一层」。

🧠 源码演进八卦
Vue 3.0 ~ 3.3 时代，源码里真的有一个 effectStack 数组（push/pop）； 到 3.4 重构时发现「暂存局部变量 + finally 还原」完全等价且更少一次数组操作，就换成了现在这种写法 —— 教学简化版采用的正是 3.4 版。读源码时见到两种写法不要慌，它们是同一思想的不同年代版本。

10.4 effectScope：给 effect 们发一个「团长」

一个组件会创建大量 effect：渲染 effect、N 个 watch、M 个 computed。 组件卸载时要一个个 stop 吗？太蠢了。Vue 3.2 引入 effectScope： 「作用域内的 effect 我统一记账，一声令下集体退休」。官方实现（3.5）： 

export let activeEffectScope: EffectScope | undefined   // ⭐ 全局指针（activeSub 的兄弟）

export class EffectScope {
  private _active = true
  effects: ReactiveEffect[] = []        // 记账本：本作用域内创建的所有 effect
  cleanups: (() => void)[] = []         // onScopeDispose 注册的钩子
  parent: EffectScope | undefined       // 只有关心的父 scope 才有
  scopes: EffectScope[] | undefined     // 收编的子 scope
  private index: number | undefined     // 在父 scopes 里的位置（O(1) 摘除用）

  constructor(public detached = false) {
    if (!detached && activeEffectScope) {
      if (activeEffectScope.active) {
        this.parent = activeEffectScope
        this.index = (activeEffectScope.scopes || (activeEffectScope.scopes = [])).push(this) - 1
      } else {
        this._active = false            // 父作用域已停：孩子出生即退休，不许变「孤儿作用域」
      }
    }
  }

  run<T>(fn: () => T): T | undefined {
    if (this._active) {
      const currentEffectScope = activeEffectScope   // 又见「暂存-还原」！第 5 次了
      try {
        activeEffectScope = this
        return fn()                     // 期间创建的 effect 会自动来团长这里登记
      } finally {
        activeEffectScope = currentEffectScope
      }
    } else if (__DEV__) {
      warn(`cannot run an inactive effect scope.`)
    }
  }

  stop(fromParent?: boolean): void {
    if (this._active) {
      this._active = false
      for (const e of this.effects) e.stop()       // 团长点名：全连解散
      this.effects.length = 0
      for (const fn of this.cleanups) fn()         // onScopeDispose 的钩子逐个执行
      this.cleanups.length = 0
      for (const s of this.scopes ?? []) s.stop(true)   // 子团也解散（递归）
      if (!this.detached && this.parent && !fromParent) {
        const last = this.parent.scopes!.pop()     // ⭐ 从父名册 O(1) 摘除自己：
        if (last && last !== this) {               //   队尾顶替 + index 回填，不用 splice
          this.parent.scopes![this.index!] = last
          last.index = this.index!
        }
      }
      this.parent = undefined
    }
  }
}

// ReactiveEffect 构造时（第 2 章你已见过）：
//   if (activeEffectScope.active) activeEffectScope.effects.push(this)
//   ↑ 这就是「自动记账」：effect 出生时看一眼当前团长是谁

使用方式（也是 Composition API 中 stop 的底层原理）：

const scope = effectScope();

scope.run(() => {
  const state = reactive({ count: 0 });
  watch(() => state.count, cb);         // 被记账
  computed(() => state.count * 2);      // 被记账
  effect(() => state.count);            // 被记账
});

scope.stop();                           // 💥 上面三个全部停止，一行搞定
💡 在哪见过它？
Vue 组件的 setup 就运行在一个 effectScope 里 —— 组件卸载时调 scope.stop()， 该组件所有的 watch/computed/渲染 effect 一次性停干净。VueUse 的 createEventHook、 tryOnScopeDispose 也基于它。你写的每个组合式函数，都活在一个 scope 里。

10.5 官方细节：on()/off()、pause/resume 与 detached

10.4 已经是官方主干了，这里补三个只有翻源码才能看到的细节。

// ① on()/off()：手动「进入作用域」—— 为 async setup 的恢复场景设计
private _on = 0                       // 计数器：支持嵌套 on 多次
prevScope: EffectScope | undefined

on(): void {
  if (++this._on === 1) {
    this.prevScope = activeEffectScope
    activeEffectScope = this          // 又见「全局指针切换」，第 6 次
  }
}
off(): void {
  if (this._on > 0 && --this._on === 0) {
    // 快路径：正常 LIFO 直接还原；乱序时沿链摘除（withAsyncContext 的交错恢复）
    if (activeEffectScope === this) activeEffectScope = this.prevScope
    ...
    this.prevScope = undefined
  }
}

// ② pause()/resume()：3.5 新增 —— 与 watch 的暂停同一套 PAUSED 旗标（9.9 节）
pause(): void { ... this.effects[i].pause() ... }   // 递归暂停子 scope

组件卸载时的自动清理：instance.scope = effectScope() → 卸载时 scope.stop() —— 这就是「组件销毁，里面所有 watch/computed 自动停止」的机关。

🧠 detached 是给谁用的？
effectScope(true) 创建「脱离体」：里面注册的 effect 不随组件卸载而停止。 典型场景是全局单例——比如一个模块级的 store 初始化，它不属于任何组件的生命周期。 反过来，组件内正常写的 watch/computed 都被自动收进 instance.scope，这就是「组合式函数 在 setup 里用完不用手动清理」的根本原因：组件就是最后一个团长，散场时全带走了。

10.5′ 官方演进：从显式 effectStack 到「暂存还原」

本项目的 run() 用 lastEffect = activeEffect 暂存再还原 —— 巧妙地借用了函数调用栈当栈。有趣的是官方走过两条路：3.0~3.3 是显式数组， 3.4 重构后反而和本项目殊途同归： 

// ── 老版：显式 effectStack 数组 ──
const effectStack: ReactiveEffect[] = [];
effectStack.push(this);
activeEffect = this;
try { return this.fn(); }
finally {
  effectStack.pop();
  activeEffect = effectStack[effectStack.length - 1];   // 恢复为栈顶
}

// ── 现行 3.4+：暂存还原，和本项目同款！（指针已改名 activeSub）──
run() {
  ...
  const prevEffect = activeSub;          // ① 暂存上一层
  const prevShouldTrack = shouldTrack;
  activeSub = this;
  shouldTrack = true;
  try { return this.fn(); }
  finally {
    activeSub = prevEffect;              // ② finally 还原
    shouldTrack = prevShouldTrack;
  }
}
老版：显式栈现行：暂存-还原（本项目同款）
原理数组 + push/pop，肉眼可见的栈嵌套调用天然形成栈帧，局部变量就是栈帧变量
可调试性effectStack 可直接 watch，层级一目了然断点里看不到「栈」整体
现状已在 3.4 移除官方现行方案 —— 教学版直接对齐了最新源码
🧠 什么时候单指针真的会出事？
computed 求值嵌套：A.run() 执行中读 B.value → B.run() → B 结束还原 → A 继续 —— 「暂存-还原」在这种严格嵌套下永远正确（栈帧天然配对）。 官方早年保留显式栈，更多是为了防御未来：一旦出现「A 未结束就恢复 B」的交叉场景 （调度器、异步边界），显式栈能立刻暴露乱序。3.4 重构保证了严格嵌套之后， 官方也换成了更省的暂存还原 —— 两种写法是同一思想的年代版本，读老资料时别慌。

10.6 getCurrentScope / onScopeDispose：组合式函数的清理钩子

export function getCurrentScope() {
  return activeEffectScope;          // 老朋友：全局指针模式第 N 次出现
}
export function onScopeDispose(fn) {
  if (activeEffectScope) {
    activeEffectScope.cleanups.push(fn);   // 登记进 scope 的清理队列
  }
}
// scope.stop() 时：effects 逐个 stop + cleanups 逐个调用

它解决的是 9.7 留下的问题：effectScope 能自动停 watch/computed， 但 setInterval、addEventListener、WebSocket 这些非 effect 资源它够不着 —— onScopeDispose 给了它们一个随作用域销毁的钩子。 教学简化版没实现这个 API，动手补齐只需要：scope 里加一个 cleanups: []， stop 时 cleanups.forEach(fn => fn()) —— 十行以内的事，适合作为练手。

10.7 组合式函数设计范式：从「会调」到「会写」

组合式函数（useXxx）不是什么 API，而是一套约定：把响应式 effect 封装进作用域的功能单元。 用你已经学过的机制，可以直接推出官方规范的全部条款： 

export function useUser(id) {
  // ① 输入兼容：传 ref / getter / 原始值都行 —— toValue 一行搞定（unref 的 getter 版）
  const userId = computed(() => toValue(id));
  const user = ref(null);

  // ② 副作用全部包进 effect —— 自动随组件作用域销毁（10.6 补非 effect 资源）
  watchEffect(async () => {
    user.value = await fetchUser(userId.value);
  });

  // ③ 只返回 refs —— 调用方解构不丢响应式（7.2 toRefs 是同一思想的输出端）
  return { user, userId };
}

// 调用方（组件 setup 里）：
const { user } = useUser(() => props.id);

🧠 一句话本质
组合式函数 = 「作用域内的一次性 effect 工厂」：createApp 是宇宙级工厂，组件实例是页面级工厂， 组合式函数是功能级工厂 —— 三层工厂共用同一套「创建时登记、销毁时统一回收」的生命周期模型， effectScope 就是这条模型在代码里的实体。VueUse 全家桶不过是这条范式的两百次复写。

答案：

11.2 官方是怎么用一个函数工厂生产四兄弟的

教学简化版的 reactive 写死了 mutableHandlers。官方源码用「处理器组合 + 工厂」批量生产 —— 这是值得学习的代码组织方式： 

// 四种 baseHandler 的差异只体现在两个维度：是否递归（get），是否可写（set）
function createGetter(isReadonly = false, shallow = false) {
  return function get(target, key, receiver) {
    if (key === ReactiveFlags.IS_REACTIVE) return !isReadonly;
    const res = Reflect.get(target, key, receiver);
    if (!isReadonly) track(target, key);          // 只读也 track！（只读也能驱动 watch）
    if (shallow) return res;                       // shallow：到此为止，不递归
    if (isObject(res)) return isReadonly ? readonly(res) : reactive(res);
    return res;
  };
}

function createSetter(shallow = false) {
  return function set(target, key, value, receiver) {
    const oldValue = target[key];
    const result = Reflect.set(target, key, value, receiver);
    if (!shallow && oldValue !== value) trigger(target, key);
    return result;
  };
}

// 四兄弟 = 四种组合
const mutableHandlers    = { get: createGetter(), set: createSetter() };
const shallowHandlers    = { get: createGetter(false, true), set: createSetter() };
const readonlyHandlers   = { get: createGetter(true) };   // 没有 set！改就报错
const shallowReadonlyHandlers = { get: createGetter(true, true) };

// 一个工厂生产所有 reactive 家族
function createActiveObject(target, baseHandlers) {
  return new Proxy(target, baseHandlers);
}
🧠 为什么 props 是 shallowReadonly？
props 由父组件下发，子组件不该改它（只读），且深层转响应式是父组件的事 （避免重复代理、保证同一份数据只有一个代理源）—— 所以 Vue 给 props 的默认包装是 shallowReadonly。 你在子组件里改 props.obj.inner.x 能成功（第一层之外没锁）但会被警告， 这正是 shallow 的边界。现在你不仅知道「不能改」，还知道「为什么锁在这一层」。

11.3 shallowRef 与 triggerRef：大对象的省电模式

// 渲染一个 10 万行的表格数据：我只关心「整个数组换没换」，不关心第 5000 行

11.4 customRef：手动挡的 ref

ref 的 track（读时登记）和 trigger（写时通知）都是自动的。 customRef 把这两个时机的控制权交给你 —— 经典应用：防抖。 

import { customRef } from "vue";

function debouncedRef(value, delay = 200) {
  let timer;
  return customRef((track, trigger) => ({
    get() {
      track();                        // 读：登记（自动挡改手动挡，但一般照常登记）
      return value;
    },
    set(newValue) {
      clearTimeout(timer);
      timer = setTimeout(() => {      // 写：先攒着，攒够 200ms 才通知
        value = newValue;
        trigger();                    // 通知时才触发界面更新
      }, delay);
    },
  }));
}

11.5 toRaw 与 markRaw：进出的两扇后门

// 官方不做「反查表」—— 代理身上直接带着 __v_raw 属性指向原对象，递归脱壳即可

11.6 一棵决策树：面对数据，到底选哪个 API

全家桶学完了，实战里最容易犯的是「选择困难」。一棵决策树走到底：

原始值（数字/字符串/布尔）？ → ref()（无脑选） ｜ 不想被深度代理的大列表？ → shallowRef + triggerRef
对象/数组，需要深层响应？ → reactive() ｜ 只读配置 / 跨团队共享数据？ → readonly()（顺带免疫误写）
想要自定义「什么时候才算变了」？ → customRef（防抖/节流/撤销） ｜ 第三方类实例 / 巨型不可变对象？ → markRaw() 或 shallow 处理
从 reactive 解构就用 toRefs；要「引用上游某属性」用 toRef；传进深层组件又想保留响应性，本身就别解构
⚠️ markRaw 的真实成本
markRaw(obj) 只是在对象上盖一个 __v_skip 戳，get 拦截器看到戳就跳过 reactive()。 它是永久豁免：盖了戳的对象永远进不了响应式世界 —— 第三方图表实例、 富文本编辑器实例（它们有自己的内部状态机，被 Proxy 包一层轻则失效重则报错）。 记住口诀：「类实例，markRaw」。

11.6 markRaw / toRaw：一行成本，两个方向

export function markRaw(value) {
  def(value, "__v_skip" /* ReactiveFlags.SKIP */, true);  // 打个标
  return value;
}
// get 拦截器开头的身份暗号检查里：
//   if (key === ReactiveFlags.SKIP) return true;  → isReactive 标记为 false
//   且 createGetter 在递归代理前会检查 target.__v_skip → 直接返回原始值

export function toRaw(observed) {
  return observed && observed.__v_raw;   // 第 3.6 节的 RAW 暗号：proxy.__v_raw === 原对象
}
场景该用哪个
第三方图表实例 / 编辑器实例（ECharts、Monaco）markRaw —— 这类对象自带内部状态机，被代理可能直接坏功能，且白白吃掉代理开销
大型不可变配置（地图瓦片参数、词库）markRaw 或 shallowRef —— 不会变的东西别付订阅费
diff / 上报时需要「原始对象」比对toRaw —— 代理和原对象 === 不相等，集合里查重要用原身

12.2 Bug 案例一：「数据改了页面不动」——解构惹的祸

const state = reactive({ count: 0, list: [] });

// 经典翻车：解构 = 拷贝值，断开与代理的连接

// 姿势二：要解构就发「引用卡片」（第 7 章 ObjectRefImpl）

12.4 Bug 案例三：「放进 Set/Map 之后响应式消失了」

const state = reactive({ id: 1 });
const set = new Set();

set.add(state);           // 存进去的是代理 ✓
set.has(state);           // true ✓（同一个代理）

// 但是……从别处再 reactive 一次？不，真正的坑在这：
set.add(state);
const again = reactive({ id: 1 });  // 不同对象，没坑
set.has(again);           // false —— 语义上应该相等！

// 最坑的版本：存原始对象，再拿代理去查
const raw = { id: 1 };
set.add(raw);
set.has(reactive(raw));   // false ❌ 代理 !== 原对象，Set 按 === 判等

原理定位：代理 ≠ 原对象（proxy !== target）。 Vue 官方的终极解法是「集合代理」：对 Set/Map 做一层方法劫持，内部存时统一转原始对象（toRaw），查时也先 toRaw —— 所以在 Vue 模板里 reactive(new Set()) 能正常工作。但原生 Set 里请始终只存一种形态，或干脆用 toRaw 统一。

⚠️ 一图流判断口诀
改了没反应？先问三个问题：① 改的是代理本体吗（解构/传参/原生集合陷阱）→ ② 是在 effect/watch/computed 上下文里读的吗（第 4 章 track 的前提）→ ③ 值真的变了吗（Object.is，第 5 章 NaN 彩蛋）。90% 的「不响应」都倒在问题①。

watch(() => obj.a, cb)只有 a 变精确制导，推荐

12.6 一分钟排错：数据变了，页面为什么没更新

把本章三个案例的排查思路浓缩成一棵可直接照做的决策树 —— 遇到 bug 从上往下走：

① 数据是 ref 吗？ → JS 里改的是 .value 吗？模板/代理环境才自动脱壳
② 是 reactive 但被解构了？ → toRefs 或不解构（第 12.2 节）
③ 数据来自 props 解构？ → 改用 props.xxx 或 toRef(props, 'xxx')（12.3 节）
④ 放进了 Set/Map/普通变量？ → 检查引用是否逃出响应式（12.4 节）
⑤ shallowRef 改了深层？ → 整体替换 .value 或 triggerRef（11.3 节）
五个问题覆盖 90% 的「响应式失灵」。每一个都指向同一个根因：读取时 track 没发生，或写入时 trigger 找错了人
🧠 为什么这棵树总是有效
回忆第 4.5 节的 9 步时序：响应式生效的唯一条件是「读取发生在 effect 上下文里」。 上面五个分支本质上都在检查同一件事 —— 「读」和「写」有没有落在同一张名册上。 解构丢了代理、shallow 没登记、普通对象没名册…… 全是「名册对不上」的变体。 排错时盯着名册想，比背案例有效得多。

12.6 「数据变了页面不动」五步诊断法

把前面所有坑串成一条标准排查流水线，遇到失灵照着走：

步动作对应原理
①console.log(isReactive(data), isRef(data))对象是不是被 JSON.parse(JSON.stringify())、接口返回值替换过？换过的就不是代理了（第 3 章）
②检查有没有解构 / 展开 props 或 state解构脱壳 → toRefs 救场（7.2）
③检查修改方式：数组下标、length、Set/Map官方有 instrumentations 兜底；mini 版没实现（第 5.5 节）
④检查读取位置：是不是在 effect 外 / setTimeout 宏任务里读的activeSub 无主 → track 白读（4.5 第 ⑤ 步）
⑤vue-devtools 打开组件 → Dependencies 面板依赖列表里没有它 = track 没发生，回到 ①~④；有它但没更新 = trigger 没发生，检查修改路径
💡 为什么这套方法百试百灵
响应式系统只有「track 成功 → trigger 成功 → 重跑」三个环节， 页面不动 = 三者之一断了。五步法就是按依赖收集的物理顺序逐环排查 —— 懂原理的人排错，是在系统里走流程；不懂的人排错，是在玄学里抽卡。
自测一下：毕业考试

1. const { list } = toRefs(state) 后 list.value.push(1) 页面会更新吗？
2. const r = ref({a:1}); watch(r, cb)，执行 r.value.a = 2，cb 触发吗？为什么？

答案：
1. 会。list.value 是 state.list 的实时引用；如果它是数组/对象，ref 内部 toReactive 已把它转成深层代理，push 被拦截并 trigger。（若当初 state.list 是原始值则 push 不存在，会报错。）
2. 不触发。watch(ref) 的 getter 只读 r.value（浅层），深层属性 .a 的变化没被点名；ref 包对象时替换 r.value = {...} 才触发。要监听深层：加 {deep: true}（traverse 深度点名）。
