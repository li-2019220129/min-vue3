effect：万物的起点

在 Vue 里，你写的每一行模板、每一个 computed、每一个 watch，最后都会变成一个 effect（副作用）。它是整个响应式大厦的地基。这一章我们把地基砸开看看。

2.1 什么是「副作用」？

先别管 Vue，看一段最普通的代码：

const state = { name: "张三", age: 18 };

function renderTitle() {
  document.title = state.name;   // 读了 name，还顺手改了页面标题
}

renderTitle 除了返回值，还对外面的世界产生了影响（改了标题）—— 这种「影响」就叫副作用（side effect）。

现在问题来了：

如果有人改了 state.name，renderTitle 怎么才能自动重新执行？

Vue 要做的事情，本质上就一句话：在一个函数「读」数据时记住它，在数据「变」时重新喊它。 围绕这句话，产生了两个核心动作 —— 你将在这本书里反复遇到它们：

读取时登记
track（依赖收集） ＋ 修改时通知
trigger（派发更新） ＝ 响应式 ✨

2.2 ReactiveEffect：给函数发一张「身份证」

要「记住」一个函数，光有函数本身不够 —— 函数是匿名的，没法当 key 存进 Map。 所以源码包了一个类 ReactiveEffect，把函数变成对象， 对象就有身份、能被登记了。来看官方 3.5 源码（有删节，保留主干）： 

export let activeSub: Subscriber | undefined  // ⭐ 全局指针：当前正在执行的「订阅者」

export enum EffectFlags {
  ACTIVE       = 1 << 0,   // 活着（stop 后摘掉）
  RUNNING      = 1 << 1,   // fn 正在执行
  TRACKING     = 1 << 2,   // 依赖收集开启
  NOTIFIED     = 1 << 3,   // 已进本次 batch 队列（防重复登记）
  DIRTY        = 1 << 4,   // 脏了（computed 用，第 8 章）
  ALLOW_RECURSE = 1 << 5,  // 允许递归触发（渲染 job 用，第 23 章）
  PAUSED       = 1 << 6,   // 被暂停（watch 的 pause/resume，第 9 章）
  EVALUATED    = 1 << 7,   // computed 至少求值过一次
}

export class ReactiveEffect<T = any> implements Subscriber {
  deps?: Link = undefined      // ⭐ 反向登记簿：一条 Link 双向链（我读过哪些 dep，第 6 章主角）
  depsTail?: Link = undefined  // 链尾指针
  flags: EffectFlags = EffectFlags.ACTIVE | EffectFlags.TRACKING
  next?: Subscriber = undefined // batch 队列的串联指针（第 5 章）
  cleanup?: () => void = undefined // onEffectCleanup 注册的清理函数

  constructor(public fn: () => T) {
    if (activeEffectScope) {
      if (activeEffectScope.active) {
        activeEffectScope.effects.push(this)   // 出生即登记进当前作用域（第 10 章）
      } else {
        this.flags &= ~EffectFlags.ACTIVE      // 作用域已停止：直接出生即退休
      }
    }
  }

  run(): T {
    if (!(this.flags & EffectFlags.ACTIVE)) return this.fn()  // 已停止：普通调用，不收集

    this.flags |= EffectFlags.RUNNING
    cleanupEffect(this)              // ① 先执行上一轮注册的清理函数
    prepareDeps(this)                // ② 旧依赖全部标记「待观察」（第 6 章）
    const prevEffect = activeSub
    const prevShouldTrack = shouldTrack
    activeSub = this                 // ③ ⭐ 把全局指针指向自己
    shouldTrack = true
    try {
      return this.fn()               // ④ 真正执行函数 → 里面的读取会触发 track
    } finally {
      cleanupDeps(this)              // ⑤ 摘除仍「待观察」的过期依赖（第 6 章）
      activeSub = prevEffect         // ⑥ 还原全局指针
      shouldTrack = prevShouldTrack
      this.flags &= ~EffectFlags.RUNNING
    }
  }
}

逐行解读最关键的 ③④ 两步

  • ③ activeSub = this：在函数执行前，把自己挂到全局变量上。这样函数体里每读一个属性，track 都能通过 activeSub 知道「现在是谁在读」—— 没有这一步，依赖收集根本无从谈起。
  • ④ this.fn()：执行函数本体。函数里所有对响应式数据的读取，都会被 Proxy 拦截（下一章），进而查到 activeSub，完成登记。这就是 Vue 的「读取即收集」。
💡 比喻时间：追踪器
把 activeSub 想象成特工电影里的追踪器： 特工（effect）潜入目标家（执行 fn）之前，指挥部先给他别上追踪器（activeSub = this）。 他在屋里碰过的每一样东西（读过的每个属性）都会被记录（track）。 任务结束后追踪器收回（activeSub = prevEffect），下一批特工再来。
追踪器上岗：effect 执行期间读过的每个属性，都会被 track 记录在案

try/finally 的讲究（⑥ 为什么放 finally）

如果 this.fn() 中途抛异常，没有 finally 的话 activeSub 会永远停留在「我」身上，后续无关代码的读取会被错误地收集到我名下。 finally 保证指针无论成功还是炸了都会还原 —— 响应式系统的健壮性就藏在这些细节里。

2.3 effect()：对外的大门

export function effect<T = any>(fn: () => T, options?: ReactiveEffectOptions): ReactiveEffectRunner<T> {
  if ((fn as ReactiveEffectRunner).effect instanceof ReactiveEffect) {
    fn = (fn as ReactiveEffectRunner).effect.fn       // 传进来的是 runner → 解包复用
  }

  const e = new ReactiveEffect(fn)
  if (options) extend(e, options)      // scheduler / allowRecurse / onStop / onTrack... 全部注入
  try {
    e.run()                            // ⭐ 立即执行一次（首次收集依赖）
  } catch (err) {
    e.stop()                           // 首跑就炸：当场退休，不留半死不活的 effect
    throw err
  }
  const runner = e.run.bind(e) as ReactiveEffectRunner
  runner.effect = e                    // 返回可调用函数，还携带 effect 本体
  return runner
}

三件事：

  1. 立即执行一次 —— 依赖收集不是凭空来的，必须先跑一遍函数才知道它读了什么；
  2. 可注入 scheduler —— 数据变了不直接重跑，先走 scheduler。computed 和 watch 全靠这个口子实现各自的脾气（第 8、9 章）；
  3. 返回 runner —— 拿到它就像拿到一个「手动挡」的 effect，可以随时自己再跑；配套的 stop(runner) 一行退休。
💡 官方配套小工具：shouldTrack 的暂停开关
run() 里的 shouldTrack 是个全局开关。官方为它配了三件套： pauseTracking() / enableTracking() / resetTracking()（内部是个栈）—— 遍历大对象、执行用户清理函数等「不想触发收集」的场景就靠它临时关闸。 读源码看到这三个函数，指的就是这个开关。

2.4 Effect 全字段速查 + 一次完整的「心跳周期」

读源码时最需要的一张表 —— ReactiveEffect（订阅者）的核心成员，每个都值得认识：

成员类型作用谁在用
fn函数副作用本体（渲染函数 / getter / 回调）run()
scheduler函数数据变了之后「怎么办」的决定者trigger()（第 5 章）
deps / depsTailLink 链反向登记簿：我读过哪些 dep（双向链表）prepareDeps / cleanupDeps（第 6 章）
flags位旗标ACTIVE / RUNNING / TRACKING / NOTIFIED / PAUSED… 一个数管所有状态全流程
cleanup函数onEffectCleanup 注册的清理钩子cleanupEffect：下轮 run 前 / stop 时执行
next指针batch 通知队列的串联指针batch() / endBatch()（第 5 章）
activeSub全局指针（模块级）当前正在执行的订阅者track 的登记依据（第 4 章）

把成员放进时间轴，就是一个 effect 的「心跳周期」—— 创建、待命、触发、死亡：

new ReactiveEffect(fn) → run()：清理旧账 → prepareDeps → activeSub = 自己 → fn 执行：读数据 → track 登记（Link 挂两条链）
……待命（Link 链在手）…… 数据变化 dep.trigger：version++ → notify → batch → endBatch → trigger()：scheduler ? scheduler() : runIfDirty()
runner.effect.stop() → 沿 deps 链逐条 removeSub 注销 + cleanupEffect → 此后 run() 只是普通调用，不再登记
watch 的返回值（unwatch）就是第三行：effect.stop —— 第 9 章的「停止侦听」由此而来

2.5 脏检查：版本号记账

effect 重跑前要先回答一个问题：「我的依赖真的变了吗？」官方 3.5 的答案简洁漂亮 —— 版本号记账。每个 dep 自带账本，每条登记线快照版本，读取时对账： 

export class Dep {
  version = 0;                 // 每次 trigger（写入）+1
}
export class Link {
  version: number;             // 登记那一刻，快照下 dep 的 version
}
trigger(debugInfo?) {
  this.version++;              // 写入 = 记一笔账
  globalVersion++;             // 全局账本也 +1（computed 的快路径）
  this.notify();
}
function isDirty(sub) {        // 读取时对账
  for (let link = sub.deps; link; link = link.nextDep) {
    if (link.dep.version !== link.version) return true;  // 有账对不上 → 脏
  }
  return false;
}

一句话：trigger 只把 dep 的 version +1（记账），读取时逐条比对 version（结账）。 computed 还有一条全局 globalVersion 快路径 —— 只要全局账本号没动过， 连逐条对账都省了。理解这句话，第 8 章 computed 的「偷懒」就毫不神秘了， 完整展开在第 14 章官方精读。

顺带一段演进史：3.2~3.3 用一个布尔 dirty；3.4 曾扩展成四档脏标记 （MaybeDirty 系列，做「也许脏 → 校验上游 → 判定真脏」的三级闸门）； 到了 3.5，四档被整个删掉，换成了上面这套版本号。本仓库的教学简化实现用的是 0/4 两档布尔（constants.ts），主干思想一致 —— 动手时对照着看即可。

🧠 为什么 stop() 还要再清理一次？
停止一个 effect 不仅要挡住未来（摘掉 ACTIVE 旗标），还要清掉过去（沿 deps 链逐条 removeSub 注销登记 + 执行 cleanupEffect）—— 否则数据变化仍会白白走进这个 effect 的 dep 分支。「清理逻辑只写一遍」的复用典范。
自测一下：effect 基础

1. 为什么 effect(fn) 必须立即执行一次 fn？
2. 如果在 effect 里写 state.count = state.count + 1 会发生什么？源码靠什么机制兜底？

答案：
1. 因为依赖收集是「运行时」行为 —— 不跑一遍函数，系统根本不知道它读了哪些属性。首次执行 = 首次登记。
2. 会触发「自己更新自己依赖的数据」：官方的防线在 notify() —— 若 flags 带 RUNNING 且不带 ALLOW_RECURSE，这次通知直接被吞掉，运行中的 effect 不会再触发自己，避免无限递归死循环 （渲染 job 和 watch 回调会带 ALLOW_RECURSE，因为它们允许「自己触发自己」直到收敛，第 23 章）。

reactive：Proxy 的魔法

上一章我们知道了「谁在读」—— activeSub。但数据是死的， 它怎么知道「自己被读了」？答案是把普通对象换成替身：Proxy 代理。 本章还埋着一个高频面试陷阱题：Reflect 和 receiver。

3.1 一句话理解 Proxy

Proxy 就是你给对象雇的一个万能管家：任何人想读属性、写属性，都必须先过管家这一关：

const raw = { name: "张三" };

const proxy = new Proxy(raw, {
  get(target, key) {
    console.log("有人读了", key);        // 拦截到了！
    return target[key];
  },
  set(target, key, value) {
    console.log("有人把", key, "改成了", value);
    target[key] = value;
    return true;
  },
});

proxy.name;        // 控制台：有人读了 name
proxy.name = "李四"; // 控制台：有人把 name 改成了 李四

「读/写都能被拦截」—— 这正是响应式的命门。 Vue2 用的 Object.defineProperty 只能在初始化时给已知属性装监控， 而 Proxy 是全对象、全时段的管家：

痛点Vue2 definePropertyVue3 Proxy
新增属性 obj.newKey = 1❌ 监控不到（要靠 $set）✅ set 拦截器直接捕获
数组下标 arr[0] = 9❌ 要劫持七个数组方法绕路✅ 一视同仁
删除属性 delete obj.key❌ 监控不到（要靠 $delete）✅ deleteProperty 拦截
惰性深层代理❌ 初始化时递归整个对象✅ 取到时才代理下一层
Proxy 玻璃房：懒代理管家 —— 你读到哪层，他才包到哪层

3.2 源码：createReactiveObject 的五道关卡

export const reactiveMap: WeakMap<Target, any> = new WeakMap()  // 原对象 → 代理（缓存）

export function reactive(target) {
  if (isReadonly(target)) return target   // 对 readonly 代理再 reactive → 原样返回
  return createReactiveObject(target, false, mutableHandlers,
                              mutableCollectionHandlers, reactiveMap)
}

function createReactiveObject(target, isReadonly, baseHandlers, collectionHandlers, proxyMap) {
  if (!isObject(target)) {
    return target                          // ① 原始值直接返回：数字/字符串没法被 Proxy
  }
  if (
    target[ReactiveFlags.RAW] &&
    !(isReadonly && target[ReactiveFlags.IS_REACTIVE])
  ) {
    return target                          // ② 已经是代理了，别再包一层
  }
  if (target[ReactiveFlags.SKIP] || !Object.isExtensible(target)) {
    return target                          // ③ markRaw 盖过章的 / 冻结对象：放行
  }
  const existingProxy = proxyMap.get(target)
  if (existingProxy) {
    return existingProxy                   // ④ 缓存命中：reactive(obj) === reactive(obj)
  }
  const targetType = targetTypeMap(toRawType(target))  // COMMON / COLLECTION / INVALID
  if (targetType === TargetType.INVALID) {
    return target                          // ⑤ Date / RegExp / DOM 节点等：不代理
  }
  const proxy = new Proxy(
    target,
    targetType === TargetType.COLLECTION ? collectionHandlers : baseHandlers,
  )                                        // ⭐ Map/Set 走另一套 handler（第 13 章伏笔）
  proxyMap.set(target, proxy)
  return proxy
}

五道关卡，各有深意

  • 非对象直接返回：reactive(18) 是无效操作（Proxy 只能代理对象）。 这正是 ref 存在的理由 —— 第 7 章。
  • target[ReactiveFlags.RAW]：注意！读这个 key 会触发代理的 get 拦截器， 拦截器看到这个特殊 key 就把原始对象还回去 —— 一个属性同时实现「识别身份」和「防重复包装」两个功能，很巧。
  • SKIP / 不可扩展：markRaw(obj) 就是在对象上盖 __v_skip 章（第 11 章）；被 Object.freeze 的对象也直接放行。
  • WeakMap 缓存：保证 reactive(obj) === reactive(obj)， 否则两个代理互不相认，数据会「精神分裂」。
  • TargetType 分流：普通对象/数组 → baseHandlers； Map/Set/WeakMap/WeakSet → collectionHandlers（第 13 章的主角）。

3.3 baseHandlers：管家的工作手册

function createGetter(isReadonly = false, shallow = false) {
  return function get(target, key, receiver) {
    if (key === ReactiveFlags.IS_REACTIVE) return !isReadonly   // 身份暗号
    else if (key === ReactiveFlags.RAW) return target           // __v_raw → toRaw 的原理

    const targetIsArray = isArray(target)
    if (targetIsArray && hasOwn(arrayInstrumentations, key)) {
      return arrayInstrumentations[key]   // 数组方法拦截器：重写 push/includes 等（5.5）
    }

    const res = Reflect.get(target, key, receiver)   // ⭐ receiver 把 getter 的 this 矫正成代理（3.4）
    if (isSymbol(key) ? builtinSymbolKeys.has(key) : isSpecialIntegerKey(key)) {
      return res                               // 内部 Symbol key：不用 track
    }

    if (!isReadonly) {
      track(target, TrackOpTypes.GET, key)     // ⭐ 读取登记（第 4 章）
    }

    if (isRef(res) && !isReadonly && !shallow) {
      return res.value                         // ref 值自动脱壳（第 7 章伏笔）
    }

    if (isObject(res)) {
      // ⭐ 惰性深层代理：取到对象才继续包；shallow 到此为止
      return isReadonly ? readonly(res) : shallow ? res : reactive(res)
    }
    return res
  }
}

function createSetter(shallow = false) {
  return function set(target, key, value, receiver) {
    let oldValue = (target as any)[key]
    if (!shallow && !isReadonly(value)) {
      oldValue = toRaw(oldValue)               // 旧值若是代理，先脱壳再比较
      value = toRaw(value)
    }
    if (!hasChanged(value, oldValue)) {
      return true                              // ⭐ 值没变就不折腾（Object.is 比较，5.2）
    }
    const result = Reflect.set(target, key, value, receiver)
    trigger(target, TriggerOpTypes.SET, key, value, oldValue)   // ⭐ 通知（第 5 章）
    return result
  }
}

export const mutableHandlers: ProxyHandler<any> = {
  get: createGetter(false, false),
  set: createSetter(false),
  deleteProperty,       // delete obj.k → trigger DELETE
  has,                  // 'k' in obj → track HAS
  ownKeys,              // for...in → track ITERATE_KEY（5.5 的哨兵）
}
🧠 惰性代理：性能的小心思
注意 get 里的 return reactive(res)：嵌套对象不是在 reactive(obj) 时一次性递归代理的，而是被访问到的那一刻才转成代理。 一个巨大的对象只用一个字段时，其他 99 层结构根本不会被代理 —— 按需付费。

3.4 ⚠️ 高频陷阱：为什么必须用 Reflect.get + receiver？

这是本章压轴题，也是源码注释里作者特意强调的点。看这个对象：

const obj = {
  name: "张三",
  get aliasName() {          // aliasName 是个 getter
    return this.name + "（别名）";   // ⚠️ 注意 this 指向谁？
  },
};

当我们用代理去读 proxy.aliasName 时：

  1. 代理的 get 拦截器被触发，track(obj, 'aliasName') ✅（aliasName 被登记）
  2. 拦截器内部去执行真正的 getter，getter 里写了 this.name —— this 指向谁，name 就在谁身上被读；
  3. 如果用 target[key] 取值：this = 原始对象 obj → 读 name 不经过代理 → track(obj, 'name') 永远不会发生 ❌
  4. 如果用 Reflect.get(target, key, receiver)：this = 代理 proxy → 读 name 经过代理 → name 正常登记 ✅

一句话总结：

Reflect.get 的第三个参数 receiver，作用是把 getter 里的 this 矫正成代理， 保证 getter 内部的属性读取也能被拦截、被收集。少了它，依赖会静默丢失，页面莫名不更新。
🧪 实验：有 receiver vs 没 receiver亲手制造一次「依赖丢失」

3.5 懒代理展开全过程：一次深层读取到底发生了什么

把「惰性深层代理」的每一个动作摊开 —— 以 state.user.address.city 为例：

effect 里读 state.user → get('user') 拦截 → track + Reflect.get → res 是对象 → reactive(res) 转代理
接着读 .address（在 user 的代理上） → get('address') 拦截 → track + Reflect.get → 又是对象 → reactive(res)
最后读 .city → get('city') 拦截 → track + 返回原始值 "杭州" → 原始值不可再代理，链条终止
一条点号链 = 3 次 get 拦截、3 次 track、2 次按需转代理 —— 没被读过的层级零成本

对比 Vue2：defineProperty 必须在初始化时递归整棵对象给每个属性装 getter/setter —— 数据多大，启动就多慢。Vue3 的懒代理把成本摊到了「实际访问」上： 一个 1 万个字段的对象只用了 3 个字段，其余 9997 个字段根本不会被代理。 这也是第 11 章「大对象用 shallowRef」的理论根基 —— 浅层版连这一步展开都省了。

3.6 官方没细讲的暗号本：ReactiveFlags 全家 + handlers 四象限

4.1 需要一本什么样的名册？

先自己推演一下需求。要支持「改 name 时只通知关注 name 的 effect」，名册必须能回答：

哪个对象？ → 哪个属性？ → 哪些订阅者在等它？

三层名册开册：WeakMap 记对象、Map 记 key、Dep 记下每一位读者

4.2 源码：三层结构的诞生地

// 第③层登场：每个属性一个 Dep 实例（不再是裸 Map！）
export class Dep {
  version = 0;             // 账本：每次 trigger +1（2.5 节）
  subs?: Link;             // 订阅者双向链的「尾」
  activeLink?: Link;       // 当前正在 track 本 dep 的那条线（复用判断用）
  map?: KeyToDepMap;       // 回指所属名册 ┐ 订阅者归零时自动销户：
  key?: unknown;           // 回指自己的属性名 ┘ removeSub 里 map.delete(key)
  sc: number = 0;          // 订阅者计数（subscriber count）
}

type KeyToDepMap = Map<any, Dep>    // 第②层：key → Dep
export const targetMap: WeakMap<object, KeyToDepMap> = new WeakMap()  // 第①层

export function track(target, type, key) {
  if (shouldTrack && activeSub) {            // ⭐ 没人在读 / 收集被暂停 → 不登记
    let depsMap = targetMap.get(target)      // 第①层：找对象的登记表
    if (!depsMap) {
      targetMap.set(target, (depsMap = new Map()))
    }
    let dep = depsMap.get(key)
    if (!dep) {
      depsMap.set(key, (dep = new Dep()))    // 第③层：建档
      dep.map = depsMap
      dep.key = key
    }
    dep.track()                              // → 建立登记线（见下）
  }
}

从「Map 当 dep」到「Dep 类」：官方这一步换来了什么

早期版本（含本仓库教学简化版）的 dep 就是个普通 Map，往上面挂 cleanup/name 属性凑合用。 官方 3.5 把它升级成了 Dep 类：自带 version 账本（脏检查的根基）、 subs 订阅者链、sc 订阅者计数。 职责独立成类后，前面两层的 Map 只负责「查找到它」，登记本身全权交给 Dep 和 Link —— 名册的「户头」从一张哈希表变成了一个有行为、有账本的对象。

4.3 Dep.track()：双向奔赴的登记

track(debugInfo?): Link | undefined {
  if (!activeSub || !shouldTrack || activeSub === this.computed) return

  let link = this.activeLink
  if (link === undefined || link.sub !== activeSub) {
    // ① 没有可复用的线 → 新建一条 Link，同时挂两条双向链
    link = this.activeLink = new Link(activeSub, this)
    if (!activeSub.deps) {
      activeSub.deps = activeSub.depsTail = link        // 订阅者侧：挂到 deps 链尾
    } else {
      link.prevDep = activeSub.depsTail
      activeSub.depsTail!.nextDep = link
      activeSub.depsTail = link
    }
    addSub(link)                                         // dep 侧：挂到订阅者链尾（sc++）
  } else if (link.version === -1) {
    // ② 上一轮的旧线还在（run 前被置了 -1）→ 直接复用，同步版本即复活（第 6 章）
    link.version = this.version
  }
  return link
}

function addSub(link: Link) {
  link.dep.sc++                                          // 订阅者计数
  if (link.sub.flags & EffectFlags.TRACKING) {
    const currentTail = link.dep.subs                    // 尾插：subs 永远指向最后登记的人
    if (currentTail !== link) {
      link.prevSub = currentTail
      if (currentTail) currentTail.nextSub = link
    }
    link.dep.subs = link
  }
}

注意「双向奔赴」：一条 Link 同时挂在两条双向链上 —— 订阅者沿 deps 链能找回自己读过的所有 dep， dep 沿 subs 链能找到所有订阅它的 effect。 为什么要反向记？—— 为了第 6 章的依赖清理：双向链让「摘除一条过期登记」只需两次指针赋值。 而去重不再需要 Map 查询：dep.activeLink 一眼看到「本 dep 当前活跃的那条线」。

💡 比喻时间：小区门禁
targetMap = 整个小区的花名册；depsMap = 某栋楼的住户表； Dep = 某个门牌号自己的「粉丝群」（自带账本 version 和群成员链 subs）； Link = 一张「粉丝证」，同时登记在粉丝群名册和粉丝自己的证件包里。 track 就是发证：「effect#1 加入了 name 的粉丝群」，两边各留一份凭证，撕证（清理）时两边同时销账。
🧠 为什么最外层是 WeakMap？
WeakMap 的 key 是弱引用：当原对象在别处被销毁（比如组件卸载），它和整个名册的登记会被垃圾回收器自动带走， 不需要手动清理、也不会内存泄漏。如果换成 Map，key 永远被强引用着，对象就永远「阴魂不散」。

5.2 细节一：hasChanged 与 NaN 的坑

官方 set 拦截器用 hasChanged(value, oldValue)（内部就是 !Object.is）判断值有没有变。为什么不用 !==？ 看这个教科书级的历史悬案： 

NaN === NaN      // false ！（NaN 不等于任何值，包括自己）
NaN !== NaN      // true

state.name = NaN;   // oldValue="张三"，!== 判定变了 → 触发 ✓（该触发）
state.name = NaN;   // NaN !== NaN 恒为 true → 又触发了！✗（其实值没变）

// hasChanged = !Object.is：Object.is(NaN, NaN) === true
// → 第二次赋值被正确识别为「没变化」，静默跳过 ✓

差一个字符的严谨性，就是「能跑」和「正确」的距离。 顺带一提：set 拦截器还会先把新旧值 toRaw 脱壳再比较 —— 代理和原对象 !==，不脱壳的话「存原对象、读代理」会被误判成变化。

5.3 细节二：递归防护 —— 谁能触发自己？

  state.count = state.count + 1;   // 读了 count，又写了 count
});
// 若无保护：跑 effect → 读 count（登记）→ 写 count（trigger 自己）→
//          重跑 effect → 写 count → 重跑 effect → …… 栈溢出 💥

官方的防线在 notify()：effect 执行期间带 RUNNING 旗标， 此时再被 trigger，notify() 看到旗标直接吞掉这次通知 —— 死循环斩断。唯一的例外是带 ALLOW_RECURSE 旗标的订阅者（渲染 job 和 watch 回调）： 它们允许触发自己直到状态收敛（如「props 变了导致 pre-watch 改 state」）， 是否失控由调度器的 100 层递归上限兜底（第 23 章）。

5.4 细节三：scheduler —— 一颗埋好的种子

注意 dep 的通知最终走到 ReactiveEffect.trigger()，它并不直接 run()，而是把决定权交给 scheduler：

  if (type === TriggerOpTypes.CLEAR) {
    depsMap.forEach(run);                      // 集合 clear：全体通知
  } else if (isArray(target) && key === 'length') {
    // ① 数组 length 变短 → 被截掉的元素也要通知
    const newLength = Number(newValue);
    depsMap.forEach((dep, dk) => {
      if (
        dk === 'length' || dk === ARRAY_ITERATE_KEY ||
        (!isSymbol(dk) && dk >= newLength)
      ) run(dep);
    });
  } else {
    // ② key 自己的 dep（新增时可能不存在，存不存在都 run，undefined 会被过滤）
    if (key !== void 0 || depsMap.has(void 0)) run(depsMap.get(key));
    if (isArrayIndex) run(depsMap.get(ARRAY_ITERATE_KEY));  // ③ 下标变化 → 数组迭代依赖
    switch (type) {
      case TriggerOpTypes.ADD:                 // ④ 新增属性
        if (!isArray(target)) {
          run(depsMap.get(ITERATE_KEY));       //   for...in 要知道
          if (isMap(target)) run(depsMap.get(MAP_KEY_ITERATE_KEY));
        } else {
          run(depsMap.get('length'));          //   新增下标 → length 也变
        }
        break;
      case TriggerOpTypes.DELETE:              // ⑤ 删除属性
        if (!isArray(target)) run(depsMap.get(ITERATE_KEY));
        break;
      case TriggerOpTypes.SET: break;          // ⑥ 普通赋值：只通知 key 自己
    }
  }
  endBatch();
}
💡 ITERATE_KEY 是个什么哨兵？
你写 for (const k in obj) 时，Proxy 的 ownKeys 拦截器触发 —— 但 ownKeys 没有「具体 key」可登记。官方就用一个 Symbol 哨兵（ITERATE_KEY）充当属性名。 对象增删属性必然改变「迭代结果」，所以增删时必须顺带触发它的 dep。 面试问「for...in 为什么也能响应式」，答案就是这个哨兵。

5.6 官方 3.5 的通知管线：先收集，后执行

// dep.trigger() 的完整故事：
trigger(debugInfo?) {
  this.version++;        // ① 自己的账本 +1（下游 isDirty 靠它对账）
  globalVersion++;       // ② 全局账本 +1（computed 的快路径）
  this.notify(debugInfo);
}
notify(debugInfo?) {
  startBatch();          // ③ 批次开始（batchDepth 计数，支持嵌套）
  for (let link = this.subs; link; link = link.prevSub) {
    if (link.sub.notify()) {                       // ④ 只「登记」每个订阅者，不执行！
      (link.sub as ComputedRefImpl).dep.notify();  //   返回 true 说明是 computed → 继续传播
    }
  }
  endBatch();            // ⑤ 批次结束 → 统一按顺序执行所有被登记的 effect
}

注意 ④⑤ 的分工：遍历名册期间只把订阅者挂进一条临时队列 （batch() 借用 sub.next 指针把订阅者串成链表）， 等整本名册走完、endBatch() 才逐个 trigger() 执行。 为什么不边遍历边执行？因为 effect 执行本身会读/写响应式数据，甚至回头增删 正在遍历的这条名册 —— 边走边改名单，后面的人就会漏掉或重复。 先全体登记、再统一执行，遍历期间名册结构稳定。

🧠 教学简化版为什么敢边遍历边执行？
教学简化版的 computed scheduler 只做两件事：把自己标脏 + 通知下游 —— 绝不在循环内同步求值（求值被推迟到「下次有人读 .value」，第 8 章）。 危险边界已经被设计挡住了，所以一遍循环也安全。简化不是偷懒，是想清楚了边界之后的裁剪 —— 这也是读「教学版源码」的正确姿势：看到简化，去官方找它省掉了什么。

5.7 Set/Map 的响应式：另一套拦截器（collectionHandlers）

到这里为止，track/trigger 都建立在「读写属性会被 get/set 拦截」上。 但 Map / Set 压根不这么工作：map.set(k, v) 是方法调用， 不是属性赋值 —— Proxy 的 set 拦截器根本不触发。第 12 章「放进 Set/Map 响应式消失」的病根就在这： 

const m = reactive(new Map());
m.set("a", 1);   // 读 m.set（get 拦截：拿到一个函数）→ 再调用它
//                ⚠️ set 拦截器全程没参与 —— track/trigger 一个都没发生

官方解法：get 拦截时认出集合，返回「重写过的方法」，把 track/trigger 手动埋进方法体：

function createInstrumentations() {
  const inst = {};
  // 重写「读方法」：方法体里手动 track
  ["get", "has", "forEach", "keys", "values", "entries"].forEach(key => {
    inst[key] = function (...args) {
      track(target, ITERATE_KEY);              // 迭代类依赖 ITERATE_KEY 哨兵（5.5）
      return Reflect.get(target, key, ...args); // 注意 this 必须是原始 target！
    };
  });
  // size 是 accessor 不是方法，要用 getOwnPropertyDescriptor 特殊取 —— 源码里那段"怪代码"就是干这个
  // 重写「写方法」：方法体里手动 trigger
  ["set", "add", "delete", "clear"].forEach(key => {
    inst[key] = function (...args) {
      const had = target.has(args[0]);
      const res = target[key](...args);        // 先真正执行
      if (!had) trigger(target, ITERATE_KEY);  // 新增 → ADD + 迭代依赖
      else trigger(target, key);               // SET / DELETE
      return res;
    };
  });
  return inst;
}
// baseHandlers 的 get 开头加一条：
if (isCollection(target) && hasOwn(inst, key)) {
  track(target, key);
  return Reflect.get(inst, key);   // ⭐ 返回重写版方法（不是原始方法）
}
🧠 两个值得咀嚼的细节
① 集合方法的 this 必须是原始 target —— Map 的内部槽位不认代理，所以这里故意不把 receiver 转发进去。和 3.4「必须用 receiver」正好相反：万事万物看场景，没有放之四海皆准的写法。
② map.get(k) 拿到的如果是对象，官方还会包一层 reactive —— 集合的「深响应」在方法返回值里补齐。

动手作业：教学仓库还没实现集合拦截器 —— 这是性价比最高的一题：把 5.7 的骨架补进 baseHandler.ts，官方 reactivity 的最后一块拼图就齐了。

答案：

依赖清理：分支切换之谜

这是整个 reactivity 里最烧脑、也最有含金量的一章 —— 从 3.4 开始，官方用「增量清理」 替换了沿用多年的「全删重建」方案（先有「版本号 + 双指针」，3.5 起演进为「双向链表 + 版本计数」）。 看懂它，你就超过了 90% 的「Vue 使用者」。别怕，我们有一整个动画实验室帮你。

6.1 问题：分支切换会让依赖「过期」

effect(() => {
  app.textContent = state.flag
    ? state.name      // flag=true：本轮只登记 flag、name
    : state.age;      // flag=false：本轮只登记 flag、age
});

推演一遍：

  1. flag 为 true，effect 跑完，名册里：flag → [effect]、name → [effect]
  2. 有人把 flag 改成 false → effect 重跑 → 这次只读 flag 和 age
  3. 问题来了：名册里 name → [effect] 这条记录过期了！ 现在页面显示的是 age，name 已经和我无关
  4. 如果不清理：以后每次改 name（哪怕一万次），effect 都会白白重跑 → 性能浪费 + 逻辑错误
保洁时间到：分支切换后，version 快照对不上的旧依赖被请出名册

6.2 老方案（Vue 3.0~3.3）：全删重建

老版本的思路很朴素：每次 effect 重跑之前，把它 deps 里登记的所有 dep 全部清空，跑完重新收集。 正确性没问题，但代价是：哪怕依赖一点没变（绝大多数情况），也要做一轮「全部删除 + 全部登记」的无用功。

6.3 官方 3.5 的方案：version 快照 + 「先挂起，再清算」

核心思想一句话：「每轮收集前全部标记待观察，谁被重新读到谁复活，跑完仍是待观察的才注销」 —— 像极了虚拟 DOM 的 diff。三个角色：

角色作用
link.version（快照）登记那一刻快照的 dep.version。run 前统一置 -1（待观察）；被 track 重新读到就同步成新值（复活）
prepareDeps / cleanupDepsrun 前挂起全部旧线，run 后清算仍是 -1 的线
effect.deps（Link 双向链）effect 反向记录自己登记过的所有 dep（第 4 章埋的伏笔）

    link.version = -1;                       // ⭐ -1 = 待观察：不算数，但先留着

    link.dep.activeLink = link;              // 告诉每个 dep「本轮可能轮到你」

function cleanupDeps(sub) {
  let head, tail = sub.depsTail, link = tail;
  while (link) {
    const prev = link.prevDep;
    if (link.version === -1) {
      removeSub(link);                       // 从 dep 的订阅者链上摘掉
      removeDep(link);                       // 从 effect 的 deps 链上摘掉
    } else {
      head = link;                           // 复用过的线：留下
    }
    link.dep.activeLink = link.prevActiveLink;
    link = prev;
  }
  sub.deps = head; sub.depsTail = tail;
}

6.5 教学简化版对照：「版本号 + 双指针」

官方的「待定章 + 链上清算」烧脑在指针。教学简化版（也是 4.7 心跳实验室演示的模型） 用更熟悉的数据结构演绎同一个思想 —— Map 名册 + 数组 + 双指针： 

// ① run() 开头：本轮收集开始
function preCleanEffect(effect) {
  effect._depsLength = 0;   // 写指针归零：本轮从头登记
  effect._trackId++;        // 场次号 +1：旧记录全部「作废」
}

// ② trackEffect 里：登记即 diff
function trackEffect(effect, dep) {
  if (dep.get(effect) !== effect._trackId) {     // 不是本轮登记的？
    dep.set(effect, effect._trackId);            //   → 写入本轮场次号
    const oldDep = effect.deps[effect._depsLength];
    if (oldDep && oldDep !== dep) {
      cleanDepEffect(oldDep, effect);            //   → 写指针位置上还坐着旧 dep？它过期了，删！
    }
    effect.deps[effect._depsLength++] = dep;     // 写入新 dep，指针 +1
  }
}

// ③ run() 结尾：清尾巴
function postCleanEffect(effect) {
  if (effect.deps.length > effect._depsLength) {
    for (let i = effect._depsLength; i < effect.deps.length; i++) {
      cleanDepEffect(effect.deps[i], effect);    // 多出来的全是过期依赖，逐一注销
    }
    effect.deps.length = effect._depsLength;
  }
}
