Set/Map 响应式：另一套 Handler

第 5.7 节揭了病根：Map/Set 的增删查是方法调用，Proxy 的 set 拦截器全程缺席。 本章把官方 collectionHandlers 完整实现一遍 —— 这是官方 reactivity 里 与 baseHandlers 并列的另一座山，也是 mini-vue3 的最后一块拼图。

13.1 全景：两种对象，两套拦截策略

普通对象/数组Map / Set / WeakMap / WeakSet
操作形式属性读写 obj.k = v方法调用 map.set(k, v)
可拦截点get / set / deleteProperty / has / ownKeys只有 get（拦截「取方法」这个动作）
策略拦截器里顺手 track/triggerget 返回重写过的方法，track/trigger 埋在方法体里
官方文件baseHandlers.tscollectionHandlers.ts（~450 行）
🧠 为什么只能靠 get？
Proxy 的拦截 Trap 是按「语法动作」划分的：map.set(...) 在语法上只有一次 属性读取（读 set 成员）+ 一次函数调用。函数调用本身不在 Proxy 的管辖范围 —— 所以唯一的机会是 get：返回一个「我们改写过的 set 方法」，调用方的代码一行没变，行为已经被换走了。
两套便当：普通对象拦属性，Set/Map 把 track/trigger 埋进方法体

13.2 instrumentations：把 track/trigger 埋进方法体

export function createInstrumentations() {
  const instrumentations: any = {};
  // ── 读方法：方法体里 track ──
  ["get", "has", "forEach"].forEach(key => {
    instrumentations[key] = function (this: any, ...args: any[]) {
      const target = this.__v_raw;            // 从代理拿回原始对象
      const raw = toRaw(target);
      const targetIsMap = isMap(raw);
      track(raw, key);                        // key 本身也要登记（如 map.get 的 key 变化）
      track(raw, ITERATE_KEY);                // 简化版：粗粒度全登记
      return Reflect.get(
        targetMapOrSelf(target), key, ...args // this 必须是原始 target（内部槽位不认代理）
      );
    };
  });
  // ── 写方法：方法体里 trigger ──
  ["set", "add", "delete", "clear"].forEach(key => {
    instrumentations[key] = function (this: any, ...args: any[]) {
      const target = toRaw(this);
      const had = isMap(target) ? target.has(args[0]) : target.has(args[0]);
      const prev = key === "set" ? target.get(args[0]) : undefined;
      const res = target[key](...args);       // 先真正执行
      if (!had) trigger(target, "add", args[0]);
      else if (key === "set" && hasChanged(args[0], prev)) trigger(target, "set", args[0]);
      if (key === "delete" && had) trigger(target, "delete", args[0]);
      return res;
    };
  });
  return instrumentations;
}

13.3 接线：get 拦截器认出集合

function createGetter(isReadonly = false, shallow = false) {
  return function get(target, key, receiver) {
    if (key === ReactiveFlags.IS_REACTIVE) return true;
    // ⭐ 集合分支：get/has/forEach/size... 命中重写表 → 返回重写方法
    if (isCollection(target) && hasOwn(instrumentations, key)) {
      track(target, key);
      return Reflect.get(instrumentations, key);   // 注意：不传 receiver
    }
    ... // 原有普通对象逻辑
  };
}

13.4 三个魔鬼细节

细节原因
方法内 this 必须是原始 targetMap 的内部槽位（[[Entries]]）不认代理 —— 把 proxy 传进去会静默失败或死循环
size 是 accessor 不是方法要用 Object.getOwnPropertyDescriptor 取 getter 再手动 track + call

💡 验收标准
实现完成后，这三段代码必须全绿：map.set 后视图更新、 map.delete 后视图更新、forEach 依赖在新增键时更新 —— 和第 44 章的渲染器验收一样，写测试再动手。
自测一下：集合拦截器

1. 为什么重写方法时 this 不能传 receiver？
2. reactive(new Map()) 后 map.size++ 这类操作存在吗？

答案：
1. Map/Set 的数据存在内部槽位里，方法内部访问槽位时要求 this 是真实 Map 实例； 代理没有这些槽位，传 receiver 会让方法查不到数据。
2. 不存在 —— size 是只读 accessor。改集合只能走 set/add/delete/clear 这些方法， 而它们全被 instrumentations 接管了，这就是「全覆盖」的含义。

第 14 章 · 响应式源码精读

官方 3.5 版 reactivity 精读

教学版的「Map + 数组 + 双指针」是思想的教学化。官方从 3.4 起用双向链表重写了整个依赖系统， 3.5 又补上了版本计数这最后一块拼图（并删掉了四档脏标记）—— 这是读 vuejs/core 真源码时 最大的阅读障碍。本章当你的字典，逐行对照教学版把 3.5 的正版走通 （至于 3.6 的 alien-signals 重写，见第 51 章展望）。

14.1 Dep 与 Link：两个类打天下

export class Dep {
  version = 0;             // ⭐ 每次 trigger +1 —— 「对账」的依据
  activeLink?: Link;       // 当前正在 track 本 dep 的那条线（复用判断用）
  subs?: Link;             // 订阅者双向链的「尾」指针
  map?: KeyToDepMap;       // 回指所属名册 ┐ 订阅者归零时自动销户：
  key?: unknown;           // 回指自己的属性名 ┘ removeSub 里 map.delete(key)
  sc: number = 0;          // 订阅者计数（subscriber count）
  computed?: ComputedRefImpl; // 这个 dep 属于哪个 computed（可没有）
}

export class Link {
  sub: Subscriber;         // 这条线连着谁（effect 或 computed —— 都是「订阅者」）
  dep: Dep;                //   连着哪个 dep
  version: number;         // ⭐ 登记时快照的 dep.version —— 去重 + 过期判定
  nextDep?: Link;  prevDep?: Link;   // effect 侧双向链（= 教学版 effect.deps 数组）
  nextSub?: Link;  prevSub?: Link;   // dep 侧双向链（订阅者名单）
  prevActiveLink?: Link;   // Link 复用时的暂存位
}
🧠 为什么是两个类，而不是 Map？
dep 与订阅者是多对多关系：一个 effect 读 N 个属性，一个属性被 N 个 effect 读。 教学版用「Map + 反向数组」表达；官方把每一条「谁订阅了谁」的关系做成一个 Link 对象， 让它同时挂在两条双向链上 —— dep 沿它遍历订阅者，订阅者沿它遍历自己的依赖。 结构即索引，不再需要哈希表这一层间接。
dep.subs（尾） ⇄ Link#1(effect-渲染) ⇄ Link#2(effect-watch) ⇄ Link#3(computed) = 链头
一条 dep 挂一串 Link（新订阅的接到尾部）；每个 Link 同时挂在 effect 侧的另一条双向链上（nextDep/prevDep）
dep 与 sub 的每一次相遇，都记成一节双向链 —— 摘除只需 O(1)

14.2 Dep.track()：登记线的完整生命

track(debugInfo?): Link | undefined {
  // 没人订阅、tracking 被关、自己 track 自己（computed 求值）→ 不登记
  if (!activeSub || !shouldTrack || activeSub === this.computed) return;

  let link = this.activeLink;
  if (link === undefined || link.sub !== activeSub) {
    // ① 没有可复用的线 → 新建一条
    link = this.activeLink = new Link(activeSub, this);
    //    挂到 activeSub 的 deps 双向链「尾」（对应教学版 deps[_depsLength++] = dep）
    if (!activeSub.deps) {
      activeSub.deps = activeSub.depsTail = link;
    } else {
      link.prevDep = activeSub.depsTail;
      activeSub.depsTail!.nextDep = link;
      activeSub.depsTail = link;
    }
    addSub(link);              // 再挂到本 dep 的订阅者链（subs 尾插，sc++）
  } else if (link.version === -1) {
    // ② 上一轮的旧线还在（run 前被 prepareDeps 置了 -1）→ 直接复用！
    link.version = this.version;          // 同步版本号 = 重新生效
    if (link.nextDep) { /* 已不在链尾 → 摘下来重接尾部，维持「本轮读取顺序」 */ }
  }
  return link;
}

function addSub(link: Link) {
  link.dep.sc++;                           // 订阅者计数
  if (link.sub.flags & EffectFlags.TRACKING) {
    const computed = link.dep.computed;
    // ⭐ computed 迎来第一个订阅者：把 computed 也「懒激活」地订阅到它自己的依赖上
    if (computed && !link.dep.subs) {
      computed.flags |= EffectFlags.TRACKING | EffectFlags.DIRTY;
      for (let l = computed.deps; l; l = l.nextDep) addSub(l);
    }
    const currentTail = link.dep.subs;     // 尾插：subs 永远指向最后一个订阅者
    if (currentTail !== link) {
      link.prevSub = currentTail;
      if (currentTail) currentTail.nextSub = link;
    }
    link.dep.subs = link;
  }
}

和教学版逐行对上：①新建 Link = 「dep.set(effect, trackId) + deps[_depsLength++] = dep」； ②复用旧线 = 「dep.get(effect) === trackId 则跳过」。官方比教学版省的是： 复用一条线不用动 Map，连对象都不用新建 —— 上轮的 Link 换个版本号就再上岗。

14.3 触发：version++ → notify → batch

trigger(debugInfo?) {
  this.version++;            // ① 账本 +1（所有持有快照的 Link 瞬间「过期」）
  globalVersion++;           // ② 全局账本 +1（computed 快路径）
  this.notify(debugInfo);
}
notify(debugInfo?) {
  startBatch();
  for (let link = this.subs; link; link = link.prevSub) {
    // ③ 从「尾」向「头」遍历 = 按登记顺序正序通知；只登记不执行
    if (link.sub.notify()) {
      (link.sub as ComputedRefImpl).dep.notify();  // computed 返回 true → 继续向上传播
    }
  }
  endBatch();                // ④ 批次收口：统一执行所有被登记的 effect（第 5.6 节）
}
操作教学版官方 3.5
登记去重dep.get(effect) !== _trackId（Map 查询）activeLink 一眼看到「本 dep 当前活跃的线」，对象指针直查
注销过期依赖从 _depsLength 起遍历数组 + dep.delete沿 deps 链摘节点：prevDep.nextDep = nextDep —— 每条线 O(1)
触发全部订阅遍历 Map 再拷贝数组防污染从 subs（尾）沿 prevSub 遍历 —— 天然「登记顺序」，无拷贝
🧠 通知顺序为什么是「从尾向头」？
新订阅者永远接到链尾（subs 指向尾）。从尾向头遍历 = 按登记的先后顺序触发 —— 先来的人先响应，与组件的创建/订阅顺序一致，「父先子后」的稳定性由此维持。 5.6 节的 batch 队列会再把它摆回正序执行，两道工序合起来就是「登记序 = 执行序」。

14.4 清理与脏检查：version=-1 与 globalVersion

// ── 每次 run 前后的一对钩子 ──
function prepareDeps(sub) {
  for (let link = sub.deps; link; link = link.nextDep) {
    link.version = -1;                 // ⭐ 全部旧线标记「待观察」：不算数，但先留着
    link.prevActiveLink = link.dep.activeLink;
    link.dep.activeLink = link;        // 告诉每个 dep「本轮可能轮到你」
  }
}
function cleanupDeps(sub) {
  let head, tail = sub.depsTail, link = tail;
  while (link) {
    const prev = link.prevDep;
    if (link.version === -1) {         // 跑完还是 -1 → 本轮真没读它 → 过期
      removeSub(link);                 //   从 dep 的订阅者链上摘掉
      removeDep(link);                 //   从 effect 的 deps 链上摘掉
    } else head = link;                // 复用过的线：留下
    link.dep.activeLink = link.prevActiveLink;
    link = prev;
  }
  sub.deps = head; sub.depsTail = tail;
}
// ── 脏检查：版本号逐条对账 ──
function isDirty(sub) {
  for (let link = sub.deps; link; link = link.nextDep) {
    if (
      link.dep.version !== link.version ||
      (link.dep.computed &&
        (refreshComputed(link.dep.computed) || link.dep.version !== link.version))
    ) return true;
  }
  return false;
}

教学版的清理是「数组截断」：写指针之后的全是垃圾。官方改成「先挂起，再清算」： run 前把所有旧线的 version 置 -1，fn 跑的过程中 track 到谁谁复活（version 同步成新值）， 跑完仍是 -1 的才被 cleanupDeps 摘除。换来一个教学版没有的能力： 复用的线连对象都不用新建 —— 分支没变的轮次里，一次对象分配都不发生。

而 isDirty 就是 2.5 节「版本号记账」的落地：逐条比对 link.dep.version !== link.version；遇到 computed 依赖则递归 refreshComputed —— 内部先查全局 globalVersion 快路径（世界根本没变过 → 秒回），重算后值没变就不涨 version，下游连重跑都省了 （第 8 章差异表在这里落地）。3.5 还顺手做了 dep 级 GC： removeSub 里 --dep.sc === 0 时执行 dep.map.delete(dep.key) —— 没有粉丝的名册条目直接销户， 大对象的部分属性不再被死死挂着。

自测一下：官方 3.5 精读

1. prepareDeps 为什么把 link.version 置 -1，而不是直接删掉旧登记？
2. globalVersion 和 dep.version 各管什么？为什么 computed 能靠它「秒回」？

答案：
1. -1 是「待观察」标记：本轮 fn 如果又读到了同一属性，track 发现 version=-1 的旧线直接复用 （不新建对象、不重新挂链）；跑完仍是 -1 的线才是真过期，cleanupDeps 统一摘除。 「先挂起，再清算」让未变化的轮次零分配。
2. globalVersion 是全局账本：任何一次写入都 +1，供 computed 粗查「世界变过了吗」—— 没变过连逐条对账都免了；dep.version 只在对应属性被写时 +1，供 isDirty 精确对账。 粗查挡住 99% 的空转，精查保证正确性。
